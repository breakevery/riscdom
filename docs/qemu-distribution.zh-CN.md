# 把 QEMU 送到用户手上：捆绑还是一次下载（v0.4 #4）

> **状态：决定已记录于 §5；本批次不写代码。** §4 只列出**许可证事实**以及许可证文本对"分发者"施加的
> 义务；**它不是法律意见。** §5 定下的是**分发模式**，不是许可证问题的结论。

## 1. 现状

- **QEMU 由用户自己安装。** 应用负责探测 —— `RISCDOM_QEMU` / `QEMU_SYSTEM_RISCV64` → 常见安装位置 →
  `PATH` —— 或由你在「设置 → 工具链」指向具体二进制，路径记在 `settings.json`。见
  `docs/qemu-setup.md`。
- **预检会验证它真的能用**（v0.4 批次 3）：GCC 能跑并编译四行 guest、QEMU 能跑、guest 能启动并回显
  banner。这覆盖了"在不在、这套能不能跑"，包括大家真会踩的坑（过长/含空格的路径、坏掉的二进制）。
- **没有覆盖的**：没有任何东西会下载 QEMU；除了"实测 11.1.0"，也没有告诉用户该装哪个版本；更没有版本
  兼容矩阵（这是**有意**的 —— 批次 3 说明了原因：本仓库没有可依据的矩阵）。

## 2. 我们在 GCC 上已有的模式

v0.3.0 发布的 `host/src/toolchain_download.rs` 是一套完整、可复用的模板：

- **钉住的上游版本**（`XPACK_RISCV_GCC_VERSION = "15.2.0-1"`）与钉住的 release 基址；
- **按平台**的资产名与**钉住的 SHA-256**（win32-x64、darwin-x64、darwin-arm64、linux-x64、linux-arm64）；
- 归档按平台格式处理（Windows zip、其他 tar.gz）、**防 Zip Slip** 解压、可取消、有进度事件、重复执行幂等；
- 安装到应用数据目录，然后把结果采纳为当前工具链。

QEMU 若走**下载**路线，所需的只是这个文件的变体：另一个钉住的版本、另一组按平台 URL 与摘要、同样的
防护。这是关于代码库的事实，也是 §5 推荐的主要依据。

## 3. 两种方案的技术对比

| | 把 QEMU 打进安装包 | 运行时下载 |
|---|---|---|
| **安装包体积** | 每个我们发布的平台都增加对应 QEMU 构建的体积。具体数字必须按构建实测；它远大于我们现在的几 MB（应用内描述 GCC 下载约 200 MB，那是今天**可选**载荷的量级）。 | 不变。载荷在用户主动要求时从上游取。 |
| **首次体验** | 开箱即用、可离线；无需安装任何东西。 | 第一次启动前需要一次下载（联网）；在那之前应用照旧说明缺什么。 |
| **离线 / 内网** | 最好。 | 需要一次性下载（或手动安装 —— 今天支持，且会继续支持）。 |
| **更新速度** | 换 QEMU 版本＝发一次新应用版本（且每个平台都要出包）。 | 换 QEMU 版本＝改我们代码里钉住的版本与摘要；同样要发版，但不必重新打包二进制。 |
| **平台覆盖** | 每个平台的 QEMU 构建都得进安装包；我们目前只支持 Windows。 | 覆盖问题相同，但载荷是按平台在取用时决定的。 |
| **我们分发了什么** | 一个 GPL-2.0 二进制（见 §4）。 | 我们自己的代码；二进制由上游直接到用户机器。 |
| **失败模式** | 安装包里坏掉/不匹配的 QEMU 会变成**我们的** bug 报告。 | 上游可用性与校验和漂移成为失败模式；两者都由"钉住 + 校验"处理，GCC 下载已经这么做。 |

## 4. 许可证事实（不含结论）

以下每条在行动前都应对**具体构建**核实：

- **QEMU 以 GPL-2.0 分发**，其中部分组件采用其它许可证（对某个构建而言，以它自带的
  `COPYING`/`LICENSE` 为准）。
- **GPL-2.0 把义务加在"分发该二进制的人"身上。** 就"原样分发二进制"而言，许可证文本自身的要求（作为
  文本事实）包括：随附许可证文本与显著声明；随二进制提供**对应源码**（或提供源码的书面承诺）；不得
  对接收方在该许可证下的权利附加额外限制；以及免责/责任限制条款。若分发的是**修改过**的 QEMU，还要求
  这些修改同样以 GPL 授权。
- **若我们捆绑 QEMU，我们的安装包里就含有该二进制**，于是上述义务会附在"分发我们的安装包"这一行为上。
  具体问题 —— 对 Windows 构建而言什么算"对应源码"、捆绑如何与我们 Apache-2.0 的应用许可证互动、
  "独立进程调用（非链接）"如何定性 —— 本文不回答。
- **若改为运行时下载**，我们的安装包里不含任何 QEMU 比特：二进制由上游直接到用户机器。这是否构成"由我们
  分发"、从而是否附带上文义务，是**法律定性**问题，不是技术问题。
- **我们当前的状态**：仓库为 Apache-2.0（`LICENSE`），应用不链接任何 QEMU 代码，QEMU 以独立进程运行、
  我们通过 stdio/TCP 与它对话。当前仓库里**没有**第三方声明文件，也**没有**任何地方提到 QEMU（或那份
  下载来的 GCC）的许可证 —— 无论选哪条路，这个缺口都值得补。

## 5. 决定

**运行时下载。不捆绑 QEMU，也不自建镜像：从上游官方 release 拉取归档。**

理由按权重排列：

1. 机制已经存在并已在此项目验证（§2）—— 捆绑意味着为一份**不属于我们**的载荷，在每个平台上做新的打包
   工作。
2. 安装包保持小；首次体验保持诚实：应用已经明确告诉用户缺什么、并提供手动路径，随后由预检验证。
3. 捆绑会让我们成为 GPL-2.0 二进制的分发者，那是一组必须**主动承担**的义务（§4）；下载则让我们交付的
   产物仍是我们自己的。
4. QEMU 版本迭代比我们的发版节奏快；下载路线只需改一个常量就能跟上钉住的版本。
5. **不自建镜像。** 由我们自己分发归档，会让我们成为这份我们并未构建的二进制的分发者与发布者。从上游
   官方 release 取，保证上游与用户之间只隔一方；而 GCC 下载已经在依赖的那个保证 —— 钉住的 URL 加钉住的
   SHA-256 —— 正是让这次拉取可信的东西。若上游撤下某个资产，下载会明确失败（§3 末行），手动安装路径
   不受影响。

捆绑与镜像都不在计划内。只有某些分发渠道使联网拉取不可行（例如禁止联网的应用商店）且经过许可证复核后，
才重新考虑捆绑。

## 6. 分阶段

1. **现在（已完成）：** 自动探测 + 手动路径 + 环境预检。已经装了 QEMU 的用户被完整服务。
2. **下一步（v0.4 #4，本批次实现）：** 一份钉住的 QEMU **下载**规格，镜像 GCC 那份 —— 版本、按平台 URL
   + SHA-256、防 Zip Slip、可取消、有进度、装进应用数据目录，然后像手动路径一样采纳（并让预检确认）。
   第三方许可证声明随它一起交付。
3. **不在计划内：** 把 QEMU 打进安装包，以及自建归档镜像。
