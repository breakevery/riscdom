**本文是什么。** 把第二层的规则（[roadmap §4](roadmap-v1.0.zh-CN.md)）写下来，好让它们**在被实现之前

是 §2 与 §3 背后的决策；[security-model.md](security-model.zh-CN.md) §1 说每份机密住在哪；

## 2. 节点身份

- **[已定]** **一个节点的密码学身份是一对 Ed25519 密钥**（[decisions §13](decisions.zh-CN.md)）：一把它用来签的私钥、一把同侪用来验的公钥。没有一样是自造的 —— 曲线与编码都是标准，项目只在容器上**加一个字段**，而不是自造一个格式。
- **[已定]** **住在哪**：默认 `<data-dir>/node.key`，**可选**放 OS keyring（[decisions §13](decisions.zh-CN.md)、[security-model.md](security-model.zh-CN.md) §2）。文件权限 **`600`**（Windows 上是仅属主 ACL）；权限限制不了的文件会被**拒绝**而不是被使用 —— 与 bearer token 已经遵循的规矩一致（[security-model.md](security-model.zh-CN.md) §2）。
- **[已定]** **文件是一个 JWK**（[RFC 7517](https://www.rfc-editor.org/rfc/rfc7517) / [8037](https://www.rfc-editor.org/rfc/rfc8037) 的 `OKP`/`Ed25519`），JSON、UTF-8、**无 BOM**，另带一个 JWK 规范没有定义、而我们要求**排第一**的成员：

  ```json
  {
    "schema_version": 1,
    "kty": "OKP",
    "crv": "Ed25519",
    "x": "<base64url 公钥，32 字节>",
    "d": "<base64url 私钥，32 字节>"
  }
  ```

  **为什么是 JWK 而不是 PEM**：[decisions §13](decisions.zh-CN.md) 两者都允许，而 [decisions §11](decisions.zh-CN.md) 要求每个持久化格式把 `schema_version` 带在**首字段**。PEM 的首字段是它的 `BEGIN` 行，所以带版本的 PEM 需要一个容器 —— 那就是第二个格式。JWK 是标准的、本来就与项目写的其他文件一样是 JSON，而且规范允许增补成员：`schema_version` 就是那个成员，不认识它的读者**必须忽略**它。
- **[已定]** **首字段就是首字段**：`schema_version` 是写入的第一个成员、也是读取的第一个。**更新**的 `schema_version` 被拒（`data_too_new`，不读、不写）；更旧的按 [api-compatibility.md](api-compatibility.zh-CN.md) §6 在**打开时**迁移。
- **[已定]** **首次启动时生成，读绝不生成。** 没有密钥的节点在**配置了联网之后第一次启动**时铸一把 —— bearer token 已经遵循的规矩（[`server/src/token.rs`](../server/src/token.rs)、[security-model.md](security-model.zh-CN.md) §2：「读一份凭据绝不创建一份凭据」）。没配联网的节点什么都不铸。
- **[已定]** **密钥不是节点的名字，也不是进程 id。** `agent::identity` 给每个进程铸一个 `<device>-<pid>-<seq>` 的 `AgentId`，其中的 **device 部分就是节点的名字**（默认 `local`；由连接层设置，[roadmap §4](roadmap-v1.0.zh-CN.md)）。密钥对是一份**独立的、活得更久**的身份：它活过每一次重启、每一个 pid、每一次改名。同侪在 `peers.json` 的 `node_id` 里存的是**设备名**，用来验的也是那个名字的公钥。

**冻结**：Ed25519；文件、路径与权限；JWK 形状与排第一的 `schema_version` 成员；配了联网时首次启动
生成；以及「密钥对 / 设备名 / 进程 `AgentId`」三者的分离。**未冻结**：`node.key` 是否在任何部署里都能
住 keyring（[security-model.md](security-model.zh-CN.md) §8 已把它列为 open），以及设备名怎么选、怎么改。

## 3. 签名 `@`

- **[已定]** **`@` 意味着地址 *加* 签名**（[decisions §7](decisions.zh-CN.md)）：以 `@` 寻址的消息由它点名的密钥签名。本节定的是**签什么**，不是消息怎么走。
- **[已定]** **被签的是五成员序言的规范 JSON** —— `{"v", "from", "to", "ts", "body"}` —— 用与 `audit` 的链同一套规范纪律序列化（[`audit::canonical_json`](../audit/src/lib.rs)：对象键固定顺序、无无意义空白）。签名就是对这些字节的 Ed25519。

  | 成员 | 是什么 | 为什么它在签名里 |
  |---|---|---|
  | `v` | 协议大版本 | 签名无法被重放进入另一个协议版本 |
  | `from` | 发送方的 `node_id`（设备名） | 一个有效签名无法被改归他人 |
  | `to` | 接收方的 `node_id`，或所寻址的房间 | 一条签名消息无法被改投另一个节点 |
  | `ts` | epoch 毫秒，发送方的钟 | 接收方的窗口可以被执行 |
  | `body` | 负载 | 负载无法被改动 |

- **[已定]** **签名与消息同行**，放在名为 `sig` 的成员里，序言也随行（接收方需要 `from` 与 `ts` 才能验，也需要与所签**逐字节相同**的 `body`）。
- **[已定]** **验证按此顺序，遇首个失败即停：**
  1. 接收方**认识发送方** —— `from` 在它自己的 `peers.json` 里（或该消息所属的房间，M4c）；
  2. **签名验证通过** —— 用该条目的公钥，对上面那些规范字节；
  3. **`v` 是接收方会说的协议版本** —— 更新的 major 被拒，不猜（[api-compatibility.md](api-compatibility.zh-CN.md) §6）；
  4. **`to` 是本节点**（或它在的房间）；
  5. **`ts` 在接收方的窗口内** —— 窗口外**拒绝**，不排队；
  6. **不是重放** —— 该窗口内已见过的 `(from, ts, body-hash)` 被拒。
  任何一步失败都是一个**应答**，绝不是静默丢弃：理由映射到 [error-model.md](error-model.zh-CN.md) 的分类（发送方未知或重放 → `refused`；签名损坏或版本不符 → `invalid`；时间戳过旧或来自未来 → `network`）。
- **[已定]** **签名是 bearer token *之上*的一层，不是替代品。** bearer token 是**本地**控制平面的门 —— 一台机器、一份盘上的机密（[security-model.md](security-model.zh-CN.md) §3）—— 它**绝不**发给同侪：两个节点不共享机密，只共享公钥。所以节点到节点的消息带的是**签名**，本地调用带的是 **token**，两者刻意由不同的代码检查。同时跑控制平面的节点仍以 token 应答本地调用；签名在那里不加什么、也不改什么。
- **[已定]** **签名是认证；capability 是授权。** 验签说的是**谁**发的。那个节点能不能做这件事，是既有的 capability 问题（[security-model.md](security-model.zh-CN.md) §4），由与其他各处同一套模型回答 —— 一条签名正确、但声明能力里不含该动作的消息会被**拒绝**，正如今天一个有效但 capability 不够的 token 会被拒绝。

**冻结**：`@` 的含义；五成员序言与签名所依据的规范编码；`sig` 成员；六个验证步骤及其顺序；错误映射；
「签名与 token 并存」；「认证在这边、授权在那边」。它的两个开放项在下面关闭 —— 传输见 **§3.1**，重放
防护见 **§3.2**。**未冻结**：端口号与超时（§3.1）；重放记录的数据结构、以及它是否曾被持久化（§3.2）；
`to` 的房间形态（M4c）；线上协议里的密钥轮换与撤销（[decisions §13](decisions.zh-CN.md) 定的是它们的
*形状* —— 并行轮换、广播的撤销列表 —— 而 M4d 是它们行走的地方）；以及一条消息能否被多把密钥签名。

### 3.1 传输

- **[已定]** **一条签名消息以一行 JSON 走一条 TCP 连接** —— `worker` 与 [plugin-interface.md](plugin-interface.zh-CN.md) 已经在用的流纪律：一行一个 JSON 对象、UTF-8、`\n` 结尾、无内嵌换行。TCP 是 [decisions §7](decisions.zh-CN.md) 为「派发给同侪」点名的东西，而行分隔的帧是项目其余部分**不需要第二套语法**就能解析的东西。
- **[已定]** **先直连、后 relay。** 发送方先试同侪自己的地址（它 `peers.json` 条目里的 `addresses[]`，或 M4b 发现到的）。若失败 —— 连接被拒、不可达或超时 —— 消息发给 **relay**，而 relay 是**主路径**、不是例外（[roadmap §4](roadmap-v1.0.zh-CN.md)、[decisions §7](decisions.zh-CN.md)）。RiscDom **不自建打洞**：relay 是两边都向外拨的桥。
- **[已定]** **直连与经 relay 的帧**逐字节相同。这正是让 relay **无状态**的东西：它转发一行它无法有效改动的行，因为签名覆盖了 `from`、`to`、`v` 与 `ts`（§3）。改写帧的 relay 会破坏签名，所以 relay 对消息没有任何权威。
- **[已定]** **连接是明文 TCP，它的完整来自签名而不是来自传输。** 本项目在这条路上不发 TLS（[security-model.md](security-model.zh-CN.md) §3）：机密性是部署者的事（私有网络或 TLS 终止），而*谁*与*未被改动*是签名的事。同侪**绝不**被发 bearer token —— 两个同侪不共享机密（[§3](#3-签名-)）。
- **[已定]** **没有单独的传输握手。** 连接上的第一帧就是一条消息；在读取超时内没有交付一条完整、成形的帧的连接会被关闭。协议版本**逐消息**检查（`v`，§3 步骤 3），而不是协商一次，因为一条连接承载的是消息，而每一条都自己站得住。
- **[已定]** **字节去哪里，以及不去哪里。** 本节定的是帧，以及它在**两个彼此可达的节点**之间怎么移动 —— 直连，或交给一个它够得到的 relay。**M4d**（[§6](#6-跨区域服务器--deferred-m4d)）定 relay 自己的规矩：它收到一帧后怎么路由、谁可以请它这么做、以及一个节点怎么知道它在哪。两者不重叠 —— 这里不说 relay 拿一行做什么，那里不改那一行。

**传输失败映射到 [error-model.md](error-model.zh-CN.md) 的分类，而这里不用 `partial`** —— 它描述的是一批，而一帧就是一条消息：

| 发生了什么 | 分类 | 可重试 |
|---|---|---|
| 连不上，或读/写超时 | `network` | 是（[error-model.md](error-model.zh-CN.md) §4） |
| 连接在一条完整帧到达之前结束 | `network` | 是 |
| 一条完整帧解析不了、它的 `v` 更新、签名损坏、或 `to` 不是本方 | `invalid` | 否 |
| 发送方未知，或消息是重放 | `refused` | 否 |
| 同侪以一次显式拒绝作答 | `refused` | 否 |

**冻结**：一条消息一行 JSON、走 TCP；先直连后 relay；两条路径上帧逐字节相同、因而 relay 无状态；明文加
签名、同侪之间不发 token；没有单独握手、`v` 逐消息检查；与 M4d 的边界；以及上面的错误映射。**未冻结**：
节点监听或 relay 使用的**端口号**（一个节点的地址属发现的职责，M4b）；连接/读/写**超时**；一条连接承载
多条消息还是一条一条；以及任何传输层压缩或批处理。

### 3.2 重放防护

- **[已定]** **窗口是向后五分钟、向前一分钟** —— 早于 *now − 5 min* 或晚于 *now + 1 min* 的 `ts` 被**拒绝**而不是排队（§3 步骤 5）。向后一侧由这个设计自己记录的最长延迟定尺：[decisions §33](decisions.zh-CN.md) 允许 **30 s – 2 min** 的静默重试期才开始升级，而一个合法重试可能掉出去的窗口，会拒绝本项目依赖的重试。向前一侧存在是因为钟会差 —— 一分钟足够容偏，也短得藏不住一个伪造的未来。
- **[已定]** **记录是按同侪、在内存里，且是一个高水位加一个小集合。** 对每个同侪，接收方保留**它已接受过的最高 `ts`**，以及**在那个同一 `ts` 上接受过的 body 哈希**集合 —— 一条消息与它的应答、或同一毫秒铸出的两条消息，共享一个 `ts`，且两者都合法。一条消息是重放，当它的 `ts` **早于**高水位，或**等于**它而它的 `(from, ts, body-hash)` 已在集合里。**更新的** `ts` 被接受，记录随之推进。
- **[已定]** **清理不需要定时器。** 推进高水位就**丢弃那个集合**：那些哈希处在一个窗口本就会拒绝的 `ts` 上。什么都不堆积、什么都不扫 —— 记录的大小被「一个同侪在一个时间戳上的一批消息」封顶。
- **[已定]** **记录不持久化，而且这是说出来的、不是藏起来的。** 重启会忘掉每一个高水位，所以一条仍在五分钟窗口内的消息可以**跨重启重放一次**。暴露面被窗口封顶，且随流量重新推进记录而缩小。后批是否持久化它 —— 那会是一个**新的盘上格式**，与其他格式一样登记在 [api-compatibility.md](api-compatibility.zh-CN.md) §6 —— 留在下面标为开放。
- **[已定]** **记录属于同侪，不属于密钥。** 密钥轮换并行跑几把密钥（[decisions §13](decisions.zh-CN.md)），所以步骤 2 对该同侪条目当前携带的**所有**公钥验签 —— 而轮换**不得**重置记录，否则重放的消息会在新密钥出现的那一刻又被接受。**撤销**把一把密钥从集合里移除，此后用它的消息以「发送方未知」被 `refused`；投递撤销是 M4d 的事，M4a 不携带。

**冻结**：窗口（−5 min / +1 min）与定它的那个论证；每同侪、内存里的「高水位 + 集合」记录；推进即丢弃的
清理；记录属于同侪、且挺过轮换；以及「重启就丢」这一诚实限度。**未冻结**：记录的内存数据结构；后批是否
持久化它（新格式，需登记）；某个部署可能想要的偏差容限；以及撤销怎么被投递的任何东西（M4d）。

## 4. 发现

**两个来源，按此权威顺序**：**内网服务器**把「本网络上有谁」的表下发给节点（[roadmap §4](roadmap-v1.0.zh-CN.md)、agreement B —— 这个网络不是一张只有对等节点的平网），而 **UDP 广播**让一个在两次下发之间出现的节点能自己报名（[decisions §7](decisions.zh-CN.md) 已点名 UDP 广播 + 房间隔离为补充）。§3.1 已经说了帧**怎么移动**；本节说的是**地址从哪来**。

### 4.1 内网服务器下发的表

- **[已定]** **内网服务器是一个带角色的节点**，不是一种新的进程 —— 同一个内核，按部署区分（[decisions §33](decisions.zh-CN.md)）。本节只用那个角色的一部分：它持有本网络的节点表并把它下发。其余部分（§33 的中心、§6 的跨区域服务器）不是本节的事。
- **[已定]** **一条条目恰好就是一条 `peers.json` 条目** —— `{node_id, addresses[], public_key, capabilities, rooms[]}`，即 [decisions §13](decisions.zh-CN.md) 定下、[§2](#2-节点身份) 已经在读的形状。一个形状、一套语法：一张表就是**一串条目**，于是「我被配置的同侪」与「我被告知的同侪」之间不需要任何翻译。
- **[已定]** **表是来源，不是权威。** 节点把被告知的东西**并入**自己的视图；**它自己的 `peers.json` 对自己仍是权威**，而冲突 —— 同一个 `node_id` 配不同的密钥或不同的地址 —— 会被**报告、绝不静默解决**，即 [plugin-interface.md](plugin-interface.zh-CN.md) §6 对 manifest 来源已经写下的那条规矩。表过期、有错或不存在时，节点照常工作。
- **[已定]** **服务器的表从哪来**：它自己的 `peers.json`（部署者写的）加上它自己从报名里接受过的条目（§4.2）。它选择发布什么是部署者的策略，不是本文的。
- **[已定]** **何时下发**：节点在**启动时**（身份已存在且配了联网之后）与**每次重连**服务器时索取，而服务器在自己的表变化时**推送**一张新表。每张表带一个 **generation**（单调整数），于是节点能看出手里那份是否最新。没有轮询循环，也没有固定的刷新间隔。
- **[已定]** **下发是一条消息，不是新协议。** 它作为一个签名帧走 §3.1 已冻结的传输 —— 节点连服务器就像连任何同侪 —— 而它的 `body` 携带 generation 与条目。§3 的验证原样适用，服务器只是一个节点已知其密钥的同侪。

### 4.2 UDP 广播，那个补充

- **[已定]** **一个数据报携带一个签名帧，而它唯一被允许的效果是提供一个地址。** 报名消息的 `body` 是发送方**自己的条目**（§4.1 的形状）加上它为哪些房间报名。它是一个**信标**：不期待应答、尽力而为，接收方只能拿它考虑一个候选条目。§3 中要紧的部分 —— 签名、窗口、重放记录 —— 对它与其他任何帧完全一样地适用。
- **[已定]** **它不是对等传输。** §3.1 管的是**两个彼此可达的节点**之间的路；广播是另一种、单向的载体，而且是本协议里**唯一**走 UDP 的东西 —— 没有请求、没有应答、也没有下发用它。
- **[已定]** **报名消息能刷新地址；它无法引入密钥。** 一个**已被认识**的节点（在自己的 `peers.json` 或下发的表里）可以由报名刷新它的 `addresses[]`；而接收方**不认识**的节点会被**报告**给部署者去添加，绝不凭报名自身的权威被采纳。这保住了 §9「在被认识之前不被信任」那条规矩，而不让**首次使用即信任**从发现这里绕进来。**内网服务器**才是那个可以把一条未知的报名采纳进它所下发的表的一方，在部署者的策略之下 —— 那正是它那个角色的用途。
- **[已定]** **房间隔离是一个带有安全默认的过滤器。** 报名消息会点名它为哪些房间报名；接收方**只有在该消息点名的房间与接收方被配置的房间相交时**才采纳，而**没有配置任何房间的节点什么都不采纳** —— 项目其余部分在用的默认拒绝（[security-model.md](security-model.zh-CN.md) §4）。成员表本身是 `rooms.json`，其**形状属 M4c**（[§5](#5-房间--deferred-m4c)）：本节定的是**过滤器**，不是那个文件。
- **[已定]** **隔离是过滤器，不是墙，而签名是让它够用的东西。** 广播到达链路上的每一台机器，所以谁都能**读到**一个数据报；他们做不到的是**使用**一个本不属于自己的。载荷是**签名**过的（§3），所以一个节点无法把自己报名成另一个，也无法报名一把它不持有的密钥所对应的地址。因此**不声称载荷机密性** —— 需要它的部署就不要在那个网段开广播。
- **[已定]** **跨区域服务器不在这里。** 发现发的是**本地**地址、在一个节点所在的网络上；一个节点有没有跨区域服务器、它在哪里，来自那个节点自己的配置（[§6](#6-跨区域服务器--deferred-m4d)）。发现既不知道它，也不下发它。

### 4.3 端口

- **[已定]** **一个节点的对等端口是配置，而每一条被报出的地址带的是那个为真的端口。** 该端口是节点自己**网络设置**里的一个字段 —— 即内网接入那项工作已经引入的设置段 —— 而同侪记录的是节点报出的 `addresses[]`，所以一个绑 `0.0.0.0` 的节点报出的是一个同侪真能拨到的地址。因为这个端口是**既有设置文件里的一个字段** —— 加法式、`SETTINGS_VERSION` 不变 —— **不需要新的持久化格式，也不需要新的版本标记行**。
- **[已定]** **广播端口是固定的：一个协议常量，不是设置项。** 广播必须到达一个什么都还不知道的节点，所以它自己无法被发现；而一个**可配置**的广播端口会让同一链路上的两个节点静默地互相看不见。因此它是一个众所周知的 UDP 端口，每个节点都一样；它的**号码**属实现，在实现它的地方记录。

**冻结**：两个来源及其顺序；条目就是 `peers.json` 的形状；表是来源而非权威、冲突会被报告；启动/重连/变更时下发并带
 generation；下发是一个 §3.1 帧；报名消息是一个签名数据报、其唯一效果是提供一个地址；「刷新地址、绝不引入密钥」；
房间过滤器及其默认拒绝；对等端口是配置且不需新格式；以及广播端口是固定的。**未冻结**：报名间隔与一个节点持续报名多久；
一张表可被缓存多久后节点再问一次；服务器的发布策略；端口**号码**本身；以及重试、退避、或一个部署究竟怎么开广播。

## 5. 房间

**一个房间 = 一张成员表加上它的规则**，落点是 `rooms.json`（[roadmap §4](roadmap-v1.0.zh-CN.md)、[decisions §7](decisions.zh-CN.md)）。§4.2 已经冻结了读「房间集合」的发现**过滤器**；本节冻结那个过滤器读的**文件**，以及房间对一条消息**要求**什么。

### 5.1 文件

- **[已定]** **一个 JSON 文件，`schema_version` 排第一**，完全照 [`node.key`](connection.zh-CN.md) 与 `peers.json` 的做法（[§2](#2-节点身份)）：

  ```json
  {
    "schema_version": 1,
    "rooms": [
      {
        "name": "lab",
        "members": ["dev-a", "dev-b"],
        "rules": { "rate": { "messages": 60, "window_seconds": 60 },
                   "mention": "members",
                   "require_signature": true }
      }
    ]
  }
  ```

- **[已定]** **一个成员就是一个 `node_id`** —— `peers.json` 已经在用的那个**设备名**（[§2](#2-节点身份)），不是密钥、不是地址。一个事实一个家：**房间说「谁」；`peers.json` 说一个节点「是什么」。** 所以成员条目不带密钥，带了就会多出一个密钥可能的来源。
- **[已定]** **`rooms.json` 与 `peers.json` 是两个文件，不是一个。** `peers.json` 条目里的 `rooms[]` 是那个节点**关于自己的宣告**（§4.2）；房间的 `members[]` 是**本地部署者**对「谁在里面」的说法。两者是来自不同作者的不同主张，互不覆盖：宣告那条路只能**刷新地址**（§4.2），而成员文件只能决定**谁可以寻址这个房间**（§5.2）。
- **[已定]** **`peers.json` 不认识的成员会被报告，不会被采纳** —— 即 §4.2 对报名消息适用的那条规矩，也是 [plugin-interface.md](plugin-interface.zh-CN.md) §6 对 manifest 来源的那条。成员关系从不引入密钥，所以也引入不了信任。

### 5.2 规则

- **[已定]** **`rate` 是 `{messages, window_seconds}`，而且是按成员的。** 每个成员有自己的每窗口消息预算，因为一个房间级的预算会让一个成员把其他成员饿死。超限是 **`refused`** —— [error-model.md](error-model.zh-CN.md) §4 已经把那个分类给了「部署者定的策略」与队列已满，所以**不需要新分类**，也没有新加。
- **[已定]** **`mention` 是 `"members"` 或 `"nobody"`**，管的是**房间内一个成员对另一个成员**的 `@`。它**默认 `"nobody"`**：不另外声明的房间禁止 `@`，即项目其余部分在用的默认拒绝（[security-model.md](security-model.zh-CN.md) §4）。寻址一个非成员根本不是房间行为，它由成员关系而非 `mention` 拒绝。
- **[已定]** **`require_signature` 记录 [roadmap §4](roadmap-v1.0.zh-CN.md) 的第三条规则，而它不能降低 §3 设下的底线。** §3 让签名在**对等路径上普遍成立** —— 验证步骤 2 会拒绝签不过的帧 —— 所以在 v1.0 里 `true` 是一个文件唯一可以携带的值，`false` 在**加载时就被拒**。字段之所以保留，是因为纲领点名了它，也因为将来某个想允许房内无签名流量的版本必须在**这里、在一条决策里**说出来，而不是悄悄改一个开关。
- **[已定]** **规则在这里是机制、在那里是取值。** 内核负责执行速率、`@` 权限与签名底线；**数值与取舍是部署者的**（[decisions §7](decisions.zh-CN.md)：速率、房间与 `@` 权限在内核是机制、在调用方是策略）。本节不选任何默认速率。
- **[已定]** **成员关系是配置，而 v1.0 没有加入协议。** 房间的成员就是部署者写在文件里的那些；没有线路上的加入请求，一个节点也无法把自己加进去。动态成员关系协议会是一个新机制、带着它自己的权威问题 —— 那是 [decisions §33](decisions.zh-CN.md) 的领土 —— 所以**不在这里发明**，留在下面开放。

### 5.3 发现过滤器怎么读它

- **[已定]** **「被配置为某个房间」同时意味两件事**：`rooms.json` **点名**了那个房间，**且**那个房间的 `members[]` 列着**本节点自己的 `node_id`**。§4.2 的过滤器只在报名点名的房间与接收方被配置的房间相交时才采纳 —— 一个只是被**列在旁边**的房间不是它在的房间，也不会放宽它会采纳什么。
- **[已定]** **默认拒绝是具体的**：没有 `rooms.json`、`rooms` 数组为空、或者房间都没列出本节点，都意味着这个节点**没有**被配置为任何房间，于是它**不采纳任何报名**，只依靠下发的表工作（§4.1）。所以发现在任何房间存在之前就可用了 —— 这正是 §4.2 能先被冻结的原因。

**冻结**：文件及其「`schema_version` 排第一」的形状；成员是一个 `node_id`；`rooms.json` 与 `peers.json` 是两个文件、
两位作者、互不覆盖；未知成员被报告；`rate` 形状是按成员、其拒绝是 `refused`；`mention` 的两个取值及其 `"nobody"`
默认；`require_signature` 无法降低 §3 的底线；成员关系是配置、无加入协议；以及过滤器对「被配置为」的读法。**未冻结**：
某个部署选择的速率**数值**；一个房间日后是否可以有更多种类的规则；将来动态成员关系要走的线上流程；成员被加入
时如何被**通知**；以及成本计量（[decisions §7](decisions.zh-CN.md) 把它与速率并列点名，它不是本节的事）。

## 6. 跨区域服务器

**同一套软件的、由部署者运行的专用部署，服务两个节点自己搬不动的流量**（[roadmap §4](roadmap-v1.0.zh-CN.md)、[decisions §7](decisions.zh-CN.md)、[§33](decisions.zh-CN.md)）。本节冻结**它是什么、以及一帧怎么经过它**；它收集的 digest 是 §7 的事。

### 6.1 它是什么，谁运行它

- **[已定]** **项目不运行它；部署者运行。** 仓库发布软件；里面没有任何东西会启动一个服务器、提供端点、或指向一个项目运营的实例。一个节点使用跨区域服务器，**是因为它自己的部署者配了一个**（§6.4）；一个什么都没配的部署丢的只是广域网那条道 —— §2–§5 的每一条本地规则照常工作。
- **[已定]** **它是一种部署，不是第二种进程。** 一套代码，按部署区分（[decisions §33](decisions.zh-CN.md)）；让它成为**专用**的，是它**自己的机器、自己的进程、在每个 workgroup 之外** —— 不是内网服务器兼职做桥（[roadmap §4](roadmap-v1.0.zh-CN.md)）。两个角色、两种部署、一套软件。
- **[已定]** **v1.0 一台机器。** 多台是商业化层的事，不属于这个模型（[roadmap §4](roadmap-v1.0.zh-CN.md)、[decisions §33](decisions.zh-CN.md)）；本节不假设存在第二个实例，也不禁止日后有。

### 6.2 四个角色

- **[已定]** **signalling —— 「谁在哪」。** 它从节点告诉它的东西里回答一个 `node_id` 能被拨到哪、在哪个网络上。它知道的是**地址**，从不是负载：一帧的 `body` 不是它的事，也没有理由让它能读。
- **[已定]** **relay —— 搬两个节点自己搬不动的。** 它把收到的一帧转发给那一帧点名的 `node_id`（§6.3）。它搬的是它无法有效改动的字节（§3.1 让帧在两条路径上逐字节相同）。
- **[已定]** **management —— 注册表与房间定义。** 它可以**发布**一张节点表与一些房间定义。**它是来源、不是权威**，而这就是把 §4.1 那条规矩往外推一层：节点把被告知的并入视图，它自己的 `peers.json` 与 `rooms.json` 对自己仍是权威，冲突**被报告、绝不静默解决**。所以服务器永远不是真相居住的地方 —— 这也正是让这个角色不会被读成「一项服务」的东西（§6.5）。
- **[已定]** **audit aggregation —— 收集链的 digest。** 本节只定**这个角色的形状与它坐的位置**：这个部署四个角色之一，与其他角色以同样方式抵达，持有的是 digest 而不是消息。**digest 是什么、怎么分批是 §7 的事** —— 已经写在那里，且已获授权（[decisions §127](decisions.zh-CN.md)）。

### 6.3 路由与授权

- **[已定]** **一帧按它的 `to` 字段转发，且只按它。** 发送方点名目的 `node_id`；服务器在 signalling 角色维护的知识里查到它，再把帧递过去。它**从不打开、改写或代答 body** —— 它也**做不到**：`to` 在签名之内（§3），所以一个改动了「这帧去哪」的 relay 会破坏签名，接收方会拒收它。
- **[已定]** **谁可以请：服务器认识、且签名验证通过的那个节点。** 授权就是 §3 的模型，别的什么都不是 —— **没有新凭证、没有新 capability**：发送方必须是服务器持有其 `node_id` 与公钥的节点（于是 §3 步骤 1 成立），且签名必须验证通过（步骤 2）。被一个它不认识的节点请求时，服务器拒绝；它不会凭一个地址就转发。
- **[已定]** **它也只会转发给它同样认识的收方。** 一帧点名的目的地在服务器那里落不了位就是**拒绝**，不是广播：一个把帧撒给自己认识的每个节点的 relay，会把一个发送方的失误变成所有人的流量。
- **[已定]** **「无状态」说的是**内容**。** 服务器**不存消息** —— 转发完就忘，对任何负载没有任何权威。它确实保留两样东西，而说出来比自称「没有内存」更诚实：**谁在哪**（signalling 角色自己的数据）与 §3.2 给每个接收方的**每同侪重放记录**。两者都是关于传输的，都不是任何人历史的副本。
- **[已定]** **直连会把数据路径带离 relay。** 两个节点一旦直连说话，就不再为那一对把帧交给服务器；剩下的只是**管理平面** —— 地址知识与房间定义（[roadmap §4](roadmap-v1.0.zh-CN.md)）。所以「离开数据路径」就真的只指那件事：那一对不再有帧经过服务器，而两个节点自己的规则什么都不变。
- **[已定]** **服务器从不拨向节点。** 它监听、等着被拨，这正是本项目**不需要打洞**的原因（[roadmap §4](roadmap-v1.0.zh-CN.md)、[decisions §7](decisions.zh-CN.md)）：两边都**向外**拨，所以谁都不需要一条穿过 NAT 的入站路径。§3.1 已经定了发送方的行为 —— 先试同侪自己的地址，失败便把帧交给 relay；这里说的是另一半：relay 就站在那儿等着收。

### 6.4 节点怎么知道它的地址

- **[已定]** **跨区域服务器是一个同侪，也照同侪的方式配置。** 它的 `node_id` 与公钥住在节点自己的 `peers.json` 里（[§2](#2-节点身份)、[decisions §13](decisions.zh-CN.md)）—— 这正是 §3 的验证能双向成立的原因 —— 而它的地址就是那条目的 `addresses[]`。
- **[已定]** **节点的网络设置点名哪个同侪是它的跨区域服务器。** 这是策略的那一半：*要不要*用一个、用*哪一个*，是部署者的选择，所以它是节点已有设置段里的一个字段 —— **加法式、`SETTINGS_VERSION` 不变，因此不需要新的持久化格式、也不需要新的版本标记行**。
- **[已定]** **发现仍然对此一无所知。** §4.2 的规矩继续成立：没有任何报名携带跨区域服务器，下发的表也不提供它，而没有它的节点就是没有广域网那条道。

### 6.5 这会被读成「项目在运营一项服务」吗？

**[已定]** **不会，而且理由是**可检验的**。** [roadmap §1](roadmap-v1.0.zh-CN.md) 禁止官方运营的服务，而本节正是可能破坏它的那一节：

- **运行者被写明**：§6.1 说部署者运行它，而项目发布的是软件、不是服务。
- **没有项目端点**：本节不点名任何地址、主机名或默认值。一个节点能到某台服务器，只因为它自己的部署者把它放进了自己的 `peers.json` 与设置。
- **四个角色是机制**：路由、发布、收集 —— 四个都是部署者自己机器上的动作，而它们携带的每一个*选择*（要不要用服务器、用哪个、发布什么）都是部署者的（[decisions §7](decisions.zh-CN.md)）。
- **那个最像服务的角色被压在「来源而非权威」上**（§6.2），所以服务器永远不是真相居住的地方：部署者可以跑一台、停掉它、或从来都没有，而每个节点仍握有自己的历史与自己的成员关系。
- **它不发放任何凭证**：§6.3 用签名授权，所以服务器不授予任何访问、不交出任何机密；跑着它的部署可以随时把它撤掉，而不必重新签发任何东西。

同一场检验适用于 §4.1 的内网服务器，而它在那里也因同样的理由通过。

**冻结**：部署者运行它、项目不；它是同一套软件的专用部署、v1.0 一台机器；四个角色及各自知道与不知道什么；按签名内的 `to`、且只按它路由；授权是 §3 模型（已知的 `node_id` + 验证通过的签名）而**不是**新凭证或新 capability；relay 只向它认识的目的地转发；「无状态」的含义与不含；直连把数据路径带离 relay；服务器从不拨向节点；配置形状 = 一条 `peers.json` 条目 + 一个设置字段、无新格式；§6.5 的红线回答；同一模型的**上报半边** —— §6.6 的注册、心跳与在线状态表，且两个方向彼此分开；以及 §6.7 的**活性判定** —— 一个关于可达性的事实，要求在剩下的见证者中**全体一致**，且永远不是移除。**未冻结**：路由算法的数据结构与服务器的**容量上限**；一个部署如何向自己的用户公布地址；aggregation 角色拿一份 digest 除了持有最新那一份之外还做什么（那是 §7 的事，也已写在那里）；多台服务器怎么一起跑（商业化层的事）；§6.6 为 v1.0 冻下的**数值**（15 秒与 45 秒是与 §3.1 的超时同类的默认值）；以及 §6.6 的表存在哪里。

### 6.6 向上报：注册与心跳

**[已定]** **节点告诉服务器它在这里，并且一直告诉下去。** §6.2 的四个角色是服务器*做什么*；本小节是另一个方向 —— **节点报什么**。它是**同一套机制的两个层级**：节点对它被配置的那台服务器，以及内网服务器对上层的跨区域服务器。这里没有新的帧*类型*：注册是一个普通的、发给服务器自己的 §3 帧，心跳也是。

**[已定]** **注册帧** —— 节点连上来时发一次，且它必须是服务器**已经认识**的节点（§6.3 的授权）：

```json
{
  "v": 1, "from": "dev-a", "to": "<the server's node_id>", "ts": 1737970000000,
  "body": {
    "register": 1,
    "addresses": ["10.0.0.7:47821"],
    "capabilities": [],
    "rooms": ["lab"]
  },
  "sig": "…"
}
```

- **`from` 就是「谁在说话」**，服务器把那一行绑在它上面：身份在序言里、不在体里，所以一次注册无法冒用别人。
- **`addresses`** 是节点说自己能被拨到哪里 —— **空是合法的**（一个只能经 relay 到达的节点什么都不报）。**`capabilities`** 与 **`rooms`** 是节点*关于自己的宣告*：与 `peers.json` 同名字段、同样地位 —— **是宣告，不是事实**。
- **注册里不走密钥。** 服务器本来就持有该节点的公钥 —— 它在服务器自己的 `peers.json` 里，那正是 §3 第 1 步得以通过的原因。密钥只经配置到来、从不经帧到来，于是 §4.2 那条规矩（「报名能刷新地址、无法引入密钥」）在这里**由构造保证**：服务器不认识的节点根本注册不了。
- 服务器按它验证一切的方式验证它 —— §3 的六步：认识发送者、签名验证通过、`v` 是它说的版本、`to` 是它自己、`ts` 在窗口内、且不是重放 —— 然后记下表里那一行。注册是**幂等**的：发两次不是错，第二次什么都不改。

**[已定]** **心跳帧** —— 节点能说的最小的话：

```json
{ "v": 1, "from": "dev-a", "to": "<the server's node_id>", "ts": 1737970015000,
  "body": { "heartbeat": 1 }, "sig": "…" }
```

- **每 15 秒一次**，而这个数是*默认*、不是法则。丢一拍没有代价：15 秒后下一拍到，那一行就被刷新。
- **为什么是 15 秒**：它稳稳落在 §3.2 的后向窗口（五分钟）之内，所以迟到的拍仍然是拍、不会是 `stale` 帧；它也不至于快到让一支部队的心跳成为链路上最忙的东西；而它比下面的离线阈值小三倍，这正是让那个阈值能扛过一拍丢失与一次慢往返的原因。
- **心跳不是会话开启帧。** `{"hello": 1}` 绑定一条 socket（那是传输的事）；心跳是一个 **signalling** 事实 —— 它说一个节点还*在*，这与「socket 开着没有」是不同的问题，而一个节点可以握着会话却已经不在。把两者绑在一起，就会让传输去回答一个存在性问题，而读这张表做活性判断的那个批次（V-proto-2）不能继承这一点。

**[已定]** **在线状态表** —— 服务器为它认识的每个节点保留：

| 字段 | 含义 |
|---|---|
| `node_id` | 键，也是那一行唯一的身份 |
| `addresses[]` | 节点**最后一次报的**地址（它没报就是空） |
| `last_heartbeat_ms` | 最后一次心跳到达的时刻 —— 或那次注册，它算作一次 |
| `state` | 当 `now − last_heartbeat_ms ≤ 45 s` 时为 `online`，之后为 `offline` |

- **离线规则是那个倍数关系，45 秒是 v1.0 的值**：错过三拍。两者都写在这里，好让活性那件事拿到的是一个数值、不是猜。
- **一行由注册创建、由心跳刷新，且**永不**因为离线而被删除。** 删掉它会让「离线」与「从未注册过」变得无法区分，而*谁曾在这里*正是活性判断要的东西。重启会忘掉整张表 —— 与 §3.2 的记录做的是同一笔交易 —— 节点重连时会重新注册。
- **这张表是 signalling 角色的数据**（§6.2）：一个节点**此刻**在哪。它**不装任何负载**，里面没有一样东西是消息。
- **宣告是来源，文件仍是权威。** 节点报上来的东西作为**来源**供给服务器可能发布的注册表（§6.2 的 management）：部署者的 `peers.json` 与 `rooms.json` 对自己那个节点仍然权威，而分歧**被报告、绝不静默解决** —— §4.1 与 §6.2 的规矩，一字未改。一个节点无法靠注册变得「被认识」，也无法靠注册获得密钥。
- **[已定]** **那一行也保留节点宣告了什么。** 除上面四个字段外，一行还带着它注册时的宣告 —— `capabilities` 与 `rooms` —— 因为 §6.7 的兄弟集就是从它们读出来的（内网服务器声明 `"server"` 这条宣告；§6.7 说明它是什么、给什么、不给什么）。它们和其它宣告一样：是**来源**、绝不是权威；一个节点列上它并不持有的东西，也不会因列上而得到什么。

**[已定]** **同一套机制，两个层级。** 上述帧在「节点对它的内网服务器」与「内网服务器对上层的跨区域服务器」时是同一套：同样的 §3 帧、同样的表、同样的数值。不同的只有*谁是那个节点*与*谁持有那张表* —— 同一个内核、按部署分化（§6.1）。形状只有一种，所以两个层级无法彼此漂移。

**[已定]** **内网服务器注册的是*它自己*，不是「它自己 + 下面的节点」。** 它的帧点的是自己的 `node_id`、报的是自己的地址；它下面的节点**不**向上披露。三个理由，第一个是结构性的：

- **密钥无法经帧到来。** 为了让 §3 第 1 步通过，跨区域服务器必须在*它自己的* `peers.json` 里持有内网服务器的密钥。如果那个帧同时点名下面的节点，上层服务器就被要求去认识「经消息而不是经配置到来」的身份 —— 正是 §4.2 与 §9 禁止的事 —— 于是它一个都验证不了。
- **下面的地址从上面够不到。** 内网服务器背后的节点持有的是局域网地址；把它公布给远端同侪，是一次什么都换不回来的拓扑泄露。让级联成立的是内网服务器**自己的**地址可达：**一个公网端点就够了**，这正是本节所依据的模型。
- **身份在这里也和在别处一样，来自配置。** 如果部署者想让上层服务器认识下面的节点，它们就进*那台*服务器的 `peers.json` —— 带外地、由部署者做，这也正是一个新节点加入的方式。

**[已定]** **新节点靠配置加入，不靠请求。** 管理员先把该节点加进服务器的 `peers.json`，它才可能注册；**没有自动审批**，也没有任何「节点发一次就能让自己被认识」的请求。这是把 §5.2 那条规矩（「成员关系是配置；v1.0 没有加入协议」）用到服务器的节点表上 —— 而*动态*加入该在哪一层被决定，是 [decisions §33](decisions.zh-CN.md) 的地盘，交给 M6/M7，不在这里定。

**冻结**：节点先注册、随后持续心跳；两者都是发给服务器自己的普通 §3 帧、按 §3 的六步验证；注册体的成员（`register`、`addresses`、`capabilities`、`rooms`）以及**没有任何密钥经帧旅行**；心跳的体（`heartbeat`）以及它与会话开启帧的区别；在线状态表的字段 —— 那四个（`node_id`、`addresses[]`、`last_heartbeat_ms`、`state`）**加上注册带来的宣告**（`capabilities`、`rooms`）—— 以及一行**永不**因离线而被删除；离线规则（错过三个间隔）与 v1.0 的数值（15 秒、45 秒）；两个层级共用一种形状；内网服务器注册的是它自己；加入是配置且没有自动审批。**未冻结**：数值本身（15 秒与 45 秒是 v1.0 的默认值，与 §3.1 的超时同类）；表存在哪里（「只在内存」是本节对 §6.3 的读法，不是一个格式）；服务器怎么*发布*它持有的东西（那是 §6.2 的 management，未改）；部署者对已被判定为不在的同侪**做什么**（§6.7 —— 判定在那里冻结，动作没有）；以及这张表是否会被裁剪。

### 6.7 活性：谁来决定一个节点已经不在了

**[已定]** **§6.6 给每个节点一份*报告*；本小节给部署一个*判定*。** 这是两个不同的事实，不能混为一谈：一行变成 `offline` 说的是**服务器不再听到某个节点** —— 一个观察者、一次沉默；而一个**判定**说的是**所有还能碰到它的节点都说碰不到了** —— 只有这个陈述强到可以据此行动。与 §6.6 一样，这里也没有新的帧类型：探测是一个普通的 §3 帧，报告也是。

**[已定]** **谁判定谁，在哪一层。** 两个层级，形状与 §6.6 相同：

- **一个节点的同级就是它自己的 workgroup** —— 与它共用同一台内网服务器的那些同侪，这正是「服务器自己的知识*就是*成员关系」的原因（[roadmap §4](roadmap-v1.0.zh-CN.md)：一个 workgroup 是一个 LAN 加上它的服务器）。节点问的是**它的同级**；内网服务器判定的是**它认识的那些节点**。
- **一台服务器的同级是它的兄弟服务器** —— 注册到同一台跨区域服务器的其它内网服务器。**服务器在注册里说出来**：内网服务器在它的 §6.6 注册的 `capabilities` 列表里声明普通宣告 **`"server"`**（那一行会保留它，§6.6），而跨区域服务器的兄弟就是**那些宣告里含 `"server"` 的行**。兄弟问的是**它的兄弟**；跨区域服务器判定的是**它认识的那些服务器**。

**[已定]** **`"server"` 是一条宣告，不是 capability。** 它是注册的 `capabilities` 列表里的一个普通字符串 —— 就是 §6.6 本就携带的那份宣告列表 —— 而**不是**控制平面 capability 词表的成员（[decisions §83](decisions.zh-CN.md)）：声明它不授予任何东西、不给任何列表加词、也不让节点做任何它此前做不了的动作（§3 的签名是认证；授权是 capability 模型的事，[security-model.md §4](security-model.zh-CN.md)）。它买到的恰好一件事：声明它的节点会**被当作兄弟来探**，而如果它不再应答，就由兄弟们的全体一致来判定。一个谎称自己是服务器的节点，只是招来它不会应答的探测 —— 最坏的结果是关于它自己的一次判定，而那已由下面的规则管着。

**[已定]** **探测 —— 一个有回答的问题，先直连。**

```json
{ "v": 1, "from": "dev-a", "to": "dev-b", "ts": 1737970030000,
  "body": { "probe": 1 }, "sig": "…" }
```

- 同侪回 **`{"alive": 1}`**，发回去、由它自己签名 —— 所以探测者拿到的是**关于同侪密钥持有者与它时钟的证据**，而不只是一个开着的 socket。一个卡死的进程照样接受连接；只有一个回答能说它背后的节点还在干活。
- **先直连、失败交 relay** —— §3.1 的普通规矩，未改。这也正是探测能穿过 NAT 的原因：探测就是一个普通帧。
- **每 15 秒一次** —— 与 §6.6 的心跳同一间隔 —— 而**连续三拍无应答（45 秒）**就是探测者得出**「我碰不到它」**的根据。数值故意沿用 §6.6：节点自己的证据与服务器那张表必须在同一时刻跨过同一条线，否则判定的两半会对「45 秒过去了没有」各说各话。
- 探测者保留的是**它自己的视图** —— 每个同侪：最后一次应答何时到达、连续多少拍没答、以及它现在把对方算作*可达*还是*不可达*。它是**运行时状态**：只在内存，与服务器的表（§6.6）和 §3.2 的记录一样 —— 且**不写链**，因为「怀疑」不是一个事件（下面最后一条说为什么）。

**[已定]** **报告：探测者告诉它的服务器什么，多久一次。**

```json
{ "v": 1, "from": "dev-a", "to": "<server>", "ts": 1737970030000,
  "body": { "unreachable": "dev-b" }, "sig": "…" }
```

- 视图翻向不可达时发 **`{"unreachable": "<node_id>"}`**，翻回来时发 **`{"reachable": "<node_id>"}`**。只要视图不变，探测者**每拍（15 秒）重报一次**，所以报告是一个*脉冲*而不是一次性消息：沉默下来的见证者就不再是见证者。
- 一条报告**只在新鲜期内算数** —— 同样在 45 秒内 —— 所以一句过期的「我碰不到它」无法活过产生它的那个视图。

**[已定]** **门槛：在剩下的见证者中全体一致。** 一个节点被判为不在，当且仅当**（1）**至少有一个**见证者** —— 本服务器认识的另一个节点、它自己此刻可达、且不是被判定者 —— 且**（2）**每一个见证者都（新鲜地）报了它不可达。

- **一个「活着」的见证者拥有一票否决。** 只要有一个节点能碰到它，就是它*活着*的证明；而一次失败总有清白的解释（路由断了、端口被挡、队列满了），一次成功却没有。所以失败从不是证明、成功总是：规则只能是「失败者全体一致」。
- **多数会在最要紧的地方出错。** 在一次分区里，半个 workgroup 能碰到它、另一半不能；多数会把一个**活着的**节点判成不在 —— 这是这套机制能犯的最坏的错。全体一致只说「我们这些在场的人碰不到它」，而这是真的。
- **见证者集合是这条规则不空转的原因**，也是问题不是「多少人报了」的原因。自己已经挂掉的节点报不了；自己就不可达的节点不能被算作见证者，因为它无法作证。所以门槛是**还能说话的**人里全体一致 —— 而一个**独自**在一个 workgroup 里的节点永远不会被判（没人能作证）：这是诚实的答案。
- **判定是关于可达性的，不碰身份。** 被判为不在的节点仍在 `peers.json` 里、仍在服务器的表里、仍持有它的密钥（§6.6：一行永不被删）。被判为不在不吊销任何东西。

**[已定]** **内网服务器自己的失联由它的兄弟确认，不由下级节点确认。** 一台不再可达的服务器由**其它内网服务器**判定，由它们报给上层的跨区域服务器 —— 而下面那些节点做不到的理由是物理的：**它们和它们的服务器共用同一个 LAN 与同一条供电，会和它一起死。** 一次把见证者也包括在内的沉默，不是证据。

- **兄弟怎么知道**：它用同一个探测、同样的数值去探它知道的兄弟 —— 那些向上层服务器声明了 `"server"` 的服务器（§6.6），而探测者在**它自己的 `peers.json`** 里找到它们，公钥也在那里；密钥经配置到来、从不经帧（§4.2），所以同一个文件既是兄弟集、也是它们的密钥；躲在 NAT 后面的兄弟经跨区域服务器的 relay 抵达 —— 因为探测是 §3.1 帧，而 relay 正是用来搬一条直连搬不动的帧的。
- **它怎么报**：同样两个体，只是发给跨区域服务器而不是内网服务器。第二层没有第二套词汇。
- **跨区域服务器怎么判**：同一条规则、一字不改 —— 在剩下的兄弟见证者中全体一致。它**汇总而不探测**，且这不是选择：§6.3 的「服务器从不拨出」也适用于它，所以它自己的证据就是它已经有的（§6.6 的心跳）加上兄弟们告诉它的。

**[已定]** **判定之后：记下来，把动作留给部署者。**

- **那一行多一个字段** `judged_at_ms`：门槛首次成立的时刻，再次听到该节点时清空。§6.6 的四个字段含义**未变** —— `state` 仍只因沉默而为 `offline`，而 `judged_at_ms` 是更强的、集体的事实。两者刻意分开：一个节点可以是 `offline`（心跳停了）而同侪仍能碰到它，这与「没人碰得到」是两种处境。
- **两个审计名，每次转变一个**（词表新增，记在 [decisions §102](decisions.zh-CN.md)）：达成判定时写 **`host.connection.peer_offline`**，带 `{peer, witnesses, reports}`；再次听到该节点时写 **`host.connection.peer_recovered`**，带 `{peer, method}` —— `method` 是 `heartbeat` 或 `probe`。两者都由**判定它的那台服务器**写，也就是持有那张表的那台：节点层是内网服务器，服务器层是跨区域服务器。
- **探测者不写任何行。** 它的视图是运行时状态，而怀疑不是事实：为每个节点记「我碰不到 X」会让一次分区在半个链上写下*「X 不在了」* —— 正是本设计明确拒绝信任的那种证据。链记的是**判定**，它是唯一强到可以据此行动的陈述。
- **协议不定义移除。** 没有自动踢、没有驱逐帧、也没有「被判定的节点会被丢掉」这条规矩：内核给的是机制 —— 判定、那一行、那个事件 —— 而**部署拿它做什么是部署者的策略**（踢掉、忽略、叫人来）。那是 [roadmap §1](roadmap-v1.0.zh-CN.md) 的红线：内核给机制，不给策略。部署者的工具已经存在且未变 —— 成员关系是配置（§5.2），节点靠被写进 `peers.json` 而入（§6.6），也以同样方式离开。

**[已定]** **恢复是被听到，不是被重新接纳。** 被判过不在了的节点回来时会被听到 —— 一次心跳或一次被应答的探测会清空 `judged_at_ms`、把 `state` 恢复为 `online`、并写下 `host.connection.peer_recovered`。什么都没被恢复，因为什么都没被拿走：身份从未被吊销，那一行也从未被删除（§6.6）。重启的节点重新注册（§6.6，幂等），而它的行还是它原来那一行。

**冻结**：判定与 §6.6 的 `offline` 是两个不同的事实；两层的范围（节点的 workgroup；服务器的兄弟）；兄弟**怎么**表明自己是兄弟（注册里的 `"server"` 宣告，它是宣告而不是 capability）；探测（`{"probe": 1}` / `{"alive": 1}`、先直连后 relay、每 15 秒、连失三拍 = 探测者自己的*不可达*）；报告（`{"unreachable": …}` / `{"reachable": …}`、视图不变期间每拍重发、只在新鲜期内计）；门槛（**在剩下的见证者中全体一致**、「活着」的见证者一票否决、被判定者从不判自己）；独自的节点永不被判；判定不碰身份、不碰成员关系、不碰密钥；服务器自身的失联由**兄弟**确认，以及下级不能做的理由；判定记在判定服务器的行上（`judged_at_ms`）与两个审计名里；探测者不写行；协议**不定义移除**；恢复是被听到而不是被重新接纳。**未冻结**：探测在传输上的超时与重传细节；探测是否错开以避免大 workgroup 同步探测；新鲜期的数值（45 秒是 v1.0 的、§6.6 的）；**房间**日后是否会缩窄同级范围（它是策略分组，不是传输分组）；部署者在判定之后做什么、以及任何踢的 API 形状（V-3 或更后）；报告是否批量；以及**分区**在部署层怎么被解决 —— 那是 [decisions §33](decisions.zh-CN.md) 的压制机制，它就是**下面的 §6.8**。

### 6.8 抑制：代行之前的三层

**[已定]** **没有任何东西会在一个节点的怀疑上开火**（[decisions §33](decisions.zh-CN.md)，由 [decisions §127](decisions.zh-CN.md) 第 4 条授权）。在一个节点可以代行它的中心之前，它必须通过**三层，缺一不可**：

1. **等待期** —— 本节点联系不上中心，**静默重试 60 秒**（§33 的 30 秒 – 2 分钟，取默认值）。它**有意长于 §6.6 的 45 秒 online 窗口**：一个正在等的节点，若中心那边仍会叫它 online，那它等的是一个对方尚未到达的事实。
2. **全局确认** —— 等待期满，且群体一致认为中心不见了。这就是**§6.7 的规则作用于中心**：在剩下的见证者中全体一致，「活着」的见证者一票否决。§6.7 里已经论证过——*多数决恰恰在最重要的地方会出错*。
3. **退避 + 顺位** —— 第一顺位等待一个 **0–30 秒的随机退避**，并在**一看到接管广播的当下退让**。「第一顺位」在 v1.0 是 **`node_id` 序**（不加注册帧字段），而退避由 `(node_id, now)` 导出，所以同一毫秒确认的两个节点仍会抽出不同的延迟。

**[已定]** **这三层所说的「中心」**，是本节点知道的**内网服务器** —— 那个声明了 server 宣告（§6.6/§6.7）、且不是其上跨区域服务器的同侪。它和其它任何东西一样是一个 `node_id`，这正是 §6.7 的表能对它作判的原因。

**[已定]** **状态机是本地的，且不在链上。** 它的相位（`candidate` / `waiting` / `confirming` / `backing-off` / `standing-in`）活在内存里，与 §6.6 的表、§6.7 的记录一样：怀疑不是一个事件。

**尚不在此。** 一个节点跨过退避之后*做什么* —— 代行，以及第三层所反应的那条接管广播 —— 是 **M5-3b**；把群体关于中心的报告送达的那套交换也是 M5-3b 的：本节是规则与状态机。

**[已定]** **报告在同侪之间走**（M5-3b-1）。一个节点把 §6.7 向上发的那对 `{"unreachable": …}` / `{"reachable": …}` 发给它的邻居 —— **横向**寻址，因为中心正是那个不作答的节点 —— 而每个节点保留**自己的一份**见证表，**主语是中心**，于是 §6.7 的规则就地判。这是**一张表、两个主语**（向上是某同侪的可达性，这里是把中心），且**对跨区域服务器一无所求**：§6 的四个角色未变。

**[已定]** **接管广播是它自己的 body**，且同样只在同侪之间走：`{ "takeover": 1, "centre": <node_id>, "by": <node_id>, "at_ms": <ms> }`。听到它的节点**退让** —— §33 的第三层，一帧之内。

**[已定]** **代行是一个动作，含三件事**（M5-3b-2）。跨过退避、且**是第一顺位**时，一个节点：把接管广播发给**它的每一个**同侪；在自己的链上开一个**临时段**（`segments` 行与它的 `segment_opened` 事件 —— 段的*文件*是以后的事）；并把这一动作记为 **`host.connection.takeover_declared`**，其 detail 载明段、中心、节点与时刻。一个在代行中**听到**广播的节点记下 **`host.connection.stood_down`**。两行都是 `host.connection.*` 族里的**新名字**，都不是链的流事件。**链照旧被这样写**：§33 之后才把临时段折回主链，所以代行一条写入都不改道（owner 第 4 点）。

**[已定]** **回归是一个触发，且它在节点退让之前先完成**（M5-3c-1）。一个看到中心重新可达的代行者，会**关掉它开过的段**（`AuditStore::close_segment` —— 行变为 `closed` 并追加 `host.audit.segment_closed`），并记下 **`host.connection.centre_returned`**（`{segment_id, centre, at_ms}`），**然后**才回到 `candidate`。没有这个顺序，`observe(true)` 会立刻把它移到 `candidate`，使段永远开着：这个收窄是有意的，而且它在定时器里，因为 `net::Suppression::observe` 仍是它一直以来的纯相位函数。**关段失败**会被报出，且不会把节点囚在一个它已无权维持的代行里；`centre_returned` 行只在关段成功时写下。

**[已定]** **送达就是那条流**（M5-3c-2）。一个关闭的段的事件**在同侪之间**走到中心 —— 每事件一帧 §3 帧，最后一帧结束这条流。区间是段*自己*的事件，即它的开启行与关闭行之间的那些行、绝不是那两行；每帧载着事件自己的 `ts` / `actor` / `action` / `agent_id` / `detail`，因为中心要用它们重建段的储存。代行者记下 `host.connection.segment_delivered`。**中心**以段到达时的名字收养那一行、写下 `audit-segments/<id>.db`、**原样**调用 `merge_segment`，并记下 `host.connection.segment_rebuilt`。**对跨区域服务器一无所求**，而旧张力的两半如今是同一个故事：段在被送达中心之前是其主人链上的一段区间，到了中心才是它自己的储存（[decisions §139](decisions.zh-CN.md)）。

**尚不在此。** **跨链核对** —— 一个被合并的段是否真的承接了它所声称的锚点 —— 是 **M6**。
## 7. 审计 digest —— M4e-1

**[已定]** **digest 是对链上某一点的一份承诺**，仅此而已：链的**头哈希**与通向它的**事件数**。它*不是*第二个哈希，也*不是*整条链 —— 它是验证者可以据以比对的东西，并且由链已经住在其中的那个储存里读出（`audit` 的最后哈希与事件计数）。**链的公式不动**：本节扩展的是*传输的东西*，绝不是 `compute_hash` 或 `verify_chain`（[decisions §127](decisions.zh-CN.md) 第 2 条）。

**[已定]** **线上的形状**是一帧普通的 §3 帧 —— 一条寻址到服务器本身、已签名的消息，与 §6.6 的注册和心跳同一机理 —— 其 body 为：

```json
{
  "digest": 1,
  "chain": "…64 个十六进制字符，空链时为 null…",
  "length": 1024
}
```

- **`chain`** 是头哈希（小写十六进制），空链时为 `null`；**`length`** 是事件数，那时为 `0`。两个事实都上报，从不隐去。
- **身份在序言（preamble）的 `from` 里**（§3），所以 body 不指名任何人：如同心跳，digest 是一句**陈述**，服务器对它不作任何回答。

**[已定]** **服务器按节点持有最新的 digest** —— 在**内存**里，与会话表、重放记录一样。§6.2 的 aggregation 角色「持有的是 digest 而不是消息」：这里不会成为任何人历史的第二份拷贝，也不会把任何关于它的事写进服务器自己的链。

**[已定]** **按 30 秒定时器分批，而那个数字是默认值。** 节点每 30 秒上报一次；间隔由实现配置，其意义与 §6.6 的 15 秒相同。定时器**读本节点自己的链并上报** —— 它不写任何东西。

**[已定]** **关键事件在发生的当下推送**（M4e-2）。帧是一条寻址到服务器本身的普通 §3 帧，与 digest 一样 —— 但**每事件一帧**，因为事件本身就是新闻，没有什么可批的。其 body 为：

```json
{
  "key_event": 1,
  "at_ms": 1700000000000,
  "action": "host.audit.segment_forked",
  "detail": { "segment_id": "seg-dev-a-1", "from": "dev-a", "reason": "conflicts …" }
}
```

- **身份是前言的 `from`**（§3），所以 body 谁也不点名：与一次心跳一样，关键事件是一份**陈述**，服务器以「什么也不答」回应。
- **`action` 照链的拼法**，所以读的人能找到这条事件所描述的那一行。

**[已定]** **服务器持有它们的**有界日志，而不是最新值。** digest 幂等（最新覆盖上一份），但关键事件是**事实**，所以 aggregation 角色**在内存里**为每个节点保留最新的 **256** 条 —— 与 digest 表一样。不需要更多：一次 fork 需要一个冲突段，一次接管需要一次 60 秒的代行。

**[已定]** **按 `(action, at_ms)` 去重，且不承诺全序。** 重推的事实就是同一个事实，所以第二份会被丢掉；两个节点的日志互相独立，这里没有任何东西说谁的事件先发生 —— 与 digest 一样没有全序，理由也一样：每个节点只为自己说话。

**[已定]** **三个触发器里有两个已经存在，而且批次照跑。** **fork**（`host.audit.segment_forked`）由合并了那个冲突段的节点推送，**接管**（`host.connection.takeover_declared`）由代行的那个节点推送 —— 两者都从事件被写下的那个地方、用与心跳和 digest 同一个客户端发出，且**非致命**：一次没送到的推送是「没送到的一份报告」，而不是「没发生过的一次写入」。**第三个触发器 —— 逐出 —— 还没有生产者**：机制已就位，事件在等那个能造出它的定义。30 秒批次不受影响：它是「什么都没发生时」一个节点仍要说的话。

**冻结**：关键事件就是上面那个 body；服务器在内存里每节点保留最新 256 条；去重为 `(action, at_ms)`；不承诺全序；推送即时且非致命，批次未变。**未冻结**：逐出*是什么*（没有生产者），以及这份日志日后是否会长出消费者。

**不是 M4 的。** 临时中心、`provisional` 与 `fork` 属 M5/M6。

**[已定]** **段的语义不在这里。** 一个临时段*是什么*、它段首的跨段引用、以及 roadmap §7 仍开着的问题，都在 [docs/audit-v2.md](audit-v2.zh-CN.md) —— 审计子系统的规范。本节只是 digest 的传输：对某一点的一份承诺，向上报告。

**冻结**：digest 是头哈希与事件数；上面的线上形状；服务器按节点在内存里持有最新一份；30 秒批次作为*默认值*；以及定时器只读不写。**未冻结**：aggregation 角色拿一份 digest 除了持有最新那一份之外还做什么；多台服务器怎么一起跑（商业化层的事）。

**[已定]** **报告另一侧的节点可以把它记下来（v1.0 M6-5-4）。** 服务器持有每节点最新的 digest；而一个**跑服务器角色且持有链的节点**把它被告知的东西写成一条 `host.audit.digest_received` 行（`{node_id, chain, length}`），**按变化记** —— 重复自己的报告什么也不写。独立 `riscdom-relay` 没有链、不装 sink，与它不为 §6.7 的判断装 sink 完全一致。这条记录是部署者**自己链上的一行**，绝不是第二条链。

## 8. 架构无关

- **[已定]** **身份层不对 guest 做任何假设。** §2 与 §3 不点名任何机器、指令集或模拟器：节点的密钥签的是*消息*，不是二进制，而消息体对承载它的那一层是不透明的。这里不得生长出任何只对一种架构才有意义的字段（[roadmap §4](roadmap-v1.0.zh-CN.md)、[decisions §2](decisions.zh-CN.md)）。
- **[已定]** **这与插件接口不冲突。** [decisions §3](decisions.zh-CN.md) 把**沙箱**放到进程外，[plugin-interface.md](plugin-interface.zh-CN.md) 冻结那道缝；本文讲的是**节点**。两者不在任何地方相遇：插件进程没有密钥、什么都不签、也从不是同侪。

**冻结**：这条约束，以及与插件缝的分离。**未冻结**：两层中任何一层在内部增补的东西。

## 9. 信任模型

- **[已定]** **身份是签名层，不是授权层。** 验签确立的是*谁*；它什么都不授予（[§3](#3-签名-)）。每一个权限决定仍归 capability 模型（[security-model.md](security-model.zh-CN.md) §4），所以一个节点无法靠持有一把密钥获得权力 —— 只能靠被授予 capabilities。
- **[已定]** **私钥绝不离开节点。** 它被读来签名；它从不被发送、从不被记日志、从不进消息、从不进命令行参数（[security-model.md](security-model.zh-CN.md) §2）。`peers.json` 只存**公**钥。
- **[已定]** **同侪在被认识之前不被信任。** §3 不接受来自接收方未被配置为认识的节点的消息：没有「首次使用即信任」，也没有按地址的信誉。未知的 `from` 是 `refused`。
- **[已定]** **节点替同侪做的事在链上。** 一条签名消息要求、节点照做的行为，是与其他行为一样的审计行（[security-model.md](security-model.zh-CN.md) §7）—— 这一层认证请求，绝不变成第二本账。

**冻结**：签名不是授权、私钥的收束、不做首次信任、以及「链仍是记录」。**未冻结**：部署自己的边界
（哪些节点能到哪些节点 —— [decisions §7](decisions.zh-CN.md) 把拓扑留给部署者）。

## 10. 四条红线

[roadmap §1](roadmap-v1.0.zh-CN.md) 写下四条约束，并说它们是每个里程碑的工作都得熬过的测试。此处只
引用，不复述。

- **非通用沙箱。** §8 已为这一层写下：身份与签名不点名任何架构，消息体是不透明的。
- **无内置 supervisor。** 签名决定的是**谁**，从不是**什么**：§3 止步于 capability 层，这里没有任何规则让一个节点凭它的密钥替另一个节点行动。
- **无官方运营服务。** 密钥对是部署者机器上的一个文件，签名由接收节点验证；本文不点名任何**提供**服务的一方（[§6](#6-跨区域服务器--deferred-m4d) 是履行该义务的地方，待它被写下时）。
- **审计不变量不动。** §9 让链仍是记录，而 §2 与 §3 没有定义任何审计事件、哈希输入或链操作 —— §7 的 digest 是对**已经存在**的链的**传输**。

**冻结**：本文的任何修正都不得让四条之一失败。**未冻结**：那四条是**测试**，不是改动其含义的许可。

## 11. 两条被携带而永远没人读的通道 —— 已知缺口（v1.0 M6-2a）

两条与审计侧自己的缺口同型——分叉的关键事件推送到了服务器的内存、而没有任何读者（[cross-chain-verification.zh-CN.md §7](cross-chain-verification.zh-CN.md)）：有东西被生产、被这一层携带，然后没有任何人索取。记在这里，免得下一批把二者误当成一条能走的路。

### 11.1 注册携带声明了，而这一行现在有了读者

**[已定]** §6.6 的注册带着节点对自己的声明 —— `capabilities` 与 `rooms` —— 而自 **v1.0 M6-2b-1** 起，前者不再是空的：节点从自己的**配置**推导它（跑内网服务器角色时声明 `server`；认识至少一个同侪时声明 `dispatch`；见 [decisions §151](decisions.zh-CN.md)），且**不涉及任何新设置字段**。服务器依旧把它们留在该节点的行上（`OnlineEntry`，「它上次说自己能做什么」）。**[已定] 这一行现在有了读者（v1.0 M6-2b-2）。** `GET /v0/online` 用本节点 server role 自己的运行时表作答 —— `RelayServer::online`，每个注册到它的节点一条 `OnlineEntry` —— 于是注册作出的声明现在**可读**，而不只是被存下。它**不是**两样东西：不是 §4.1/§11.2 下发的那份注册表，也不是本节点自己的 `peers.json`。没有 server role 的节点回 `null`（连接层的规矩：缺失即 `null`，绝不是 `404`），在服务但无人注册的节点回 `[]`。

**[已定] 读它不等于对它行动。** 内核真正据以行动的两个 `capabilities` 词 —— `server`（§6.7 的同侪判断）与 `dispatch`（M6-1b 的默认拒绝）—— 仍然读节点**自己的** `peers.json`，从不读行；一个任务该去哪个节点仍是调用方的（[cross-device-dispatch.zh-CN.md §6](cross-device-dispatch.zh-CN.md)）。行里其余字段按它们的名字理解：`addresses`（尚未声明 peer 端口时为空）、`last_heartbeat_ms`（传输事实），以及 **`state` 与 `judged_at_ms` —— 它们是这台服务器对某个同侪的*意见***（一个观察者的沉默，与见证者的一致，§6.7），而不是关于世界的事实。行里没有任何密钥。

### 11.2 注册表可以主动索取，而生产代码没人索取

**[已定，仍是缺口 —— 且 `/v0/online` 不是它的读者]** §4.1 的下发两半都在盘上：`RelayServer` 用一个 generation 与它的表回答注册表请求，`RelayClient::request_registry` 负责问。**没有任何生产代码调它** —— `host-core` 没有，`server` 没有，CLI 也没有；唯一的调用者是净码 crate 自己的测试。于是节点只持有它在**启动时与每次重连时**被下发的那张 `NodeTable`（§4.1 描述的推送），自己从不主动要一张新的。§11.1 的 `/v0/online` **不**收口这一条：它读的是服务器的*注册行*，与 §4.1 下发的那份*发布的表*是两个不同的存储。一条命令或一个 M 将来是否需要轮询后者，开放。

同一枚硬币的**另一面**是 [§4.1](#41-网络内服务器下发的表)：被下发给节点的表带着每个条目的 `capabilities`，所以节点*本可以*不去问同侪就读到它声明的声明 —— 但今天没有读，而 §11.1 说明了它读到的那份声明为什么只是配置里的那份。

**冻结**：这里不改 §4.1 的推送、§6.6 的行、以及内核**确实**读的那两个词。**未冻结**：注册表缺口（§11.2）是否收口、在哪一批收口。
