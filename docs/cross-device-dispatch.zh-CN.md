# 跨设备调度

> **状态** v1.0 规范（M6-1）｜ **日期** 2026-09-30 ｜ **面向读者** 内核开发者，以及部署不止一个节点的人。

[roadmap §5](roadmap-v1.0.zh-CN.md) 列出了内核为第三层提供的**五项**，本文是其中的第三项：*「一个调度接口：按名字把一个任务交给一个节点」*。它说明「按名字」是什么意思、谁可以把什么交给谁、以及回来的是什么。其余四项 —— 节点注册表、能力描述、跨节点事件关联与待批槽 —— 是别的批次的事。

## 1. 一条路由，一个参数

`POST /v0/tasks` 本已接受 `target`、`input`、`sandbox`、`instance` 与 `id`，并把任务路由到**本节点**的执行者队列（[control-plane-api.md](control-plane-api.zh-CN.md) §5.2）。它多出一个可选成员：

```json
{ "target": "helper", "input": "…", "node": "dev-b" }
```

- **`node` 指名任务该在哪个节点上跑。** 缺席、或写本节点自己的名字，就是本地队列 —— 与这个端点从前一字不差。
- **`target` 相对于那个节点。** `node: "dev-b", target: "helper"` 意为*`dev-b` 上那个叫 `helper` 的执行者* —— 那个标签是**那个**节点 `settings.executors` 里的名字，不是本节点的一份拷贝。
- **无新路由，无新 capability。** §5 把这个接口叫作「按名字把一个任务交给一个节点」，所以名字作为参数旅行，路由表不动。调用方自己的权限也不变：`/v0/tasks` 仍是 `agent.run`，与从前一样。

## 2. 什么东西旅行，怎么走

**同侪之间的一帧普通 §3 帧**（[connection.md](connection.zh-CN.md) §3）—— 与 §6.7 的探测、§33 的报告、以及一个关闭的段所用的机制同一个。§14.6 的规则就是「没有新东西」的原因：*「M-to-M 通信：复用跨设备协议 —— 没有 M 自己的协议。」*

```json
{ "task": 1, "task_id": "task-dev-a-1-7", "target": "helper", "input": "…", "sandbox": null, "instance": null }
{ "task_reply": 1, "task_id": "task-dev-a-1-7", "agent_id": "dev-b", "outcome": { … } | "error": "…" }
```

- **一个任务一帧、一个答复一帧。** 没有什么可批的：任务*就是*消息，而答复*就是*答案（v0.9 E0 的「回答就是结局；没有任务表可轮询」）。
- **`task_id` 形如 `task-<device>-<pid>-<seq>`**（[agent/src/dispatch.rs](../agent/src/dispatch.rs)）：它点出它出生的那台机器，于是两个节点的 id 在一个节点的记录里相遇时不会撞号。调用方送出的 id 就是回来的 id。
- **答复要么是结果、要么是错误，绝不同时。** `agent_id` 指名跑了它的那个执行者 —— **对端自己**的身份，调用方不可能事先知道。
- **身份是前言的 `from`。** 同侪像任何一帧一样由 §3 认证，所以发送方是节点、不是人：一次跨设备派发是关于两个节点的事实。

## 3. 授权：默认拒绝

接收方只问**它自己的** `peers.json` 一个问题，关于发送方的那一条：

> 它的 `capabilities` 列表里有没有 **`dispatch`** 这个词？

没有 —— 包括这个节点根本不认识发送方 —— 任务就**被拒**。这个词是一条普通的声明字符串，与 §6.7 的 `server` 声明同形：

```json
{ "node_id": "dev-a", "address": "…", "public_key": { … }, "capabilities": ["dispatch"] }
```

- **它不是控制面的 capability 名。** 声明它对那个节点的 HTTP 面什么也不授予；能力词汇表（33 个名字）未变，而调用方的 `agent.run` 仍然是「可以这样要求」的依据。
- **两条轴，有意分开。** **HTTP** 那条轴说一份*凭据*可以要求一个节点做什么；这条轴说一个*同侪节点*可以交给它什么。一个任务只有在也通过了前者的前提下，才会跨过后者。
- **拒绝是可读的。** 未被授权的同侪会被明确告知，调用方看到的是 `the peer did not authorise dispatch`，而不是一次超时。

## 4. 双方各做什么

**发送方。** 节点用它本已有的客户端发一帧（与心跳和 digest 同一个），然后等回复：轮询节点读方填入的共享回复槽，总时长 `REMOTE_DISPATCH_TIMEOUT`（30 秒）、每 `REPLY_POLL`（100 毫秒）一次。回复落地时，那个结果就是任务的结果。

**接收方。** 节点的**探测线程** —— 一个节点唯一的读方 —— 认出这一帧、检查声明、**在它自己的队列上**跑这个任务、记下 `host.dispatch.received`，并作答。跑不动、或 `target` 不在它队列里，都会**作答**而不是丢弃：发送方总会拿到一个答复或一个理由。

**四类拒绝，凭消息可辨**，且都不需要自己的错误变体：

| 发生了什么 | 谁的话 | 消息 |
|---|---|---|
| 帧出不去 | 发送方 | `the peer is unreachable: …` |
| 同侪没有授权派发 | 同侪 | `the peer did not authorise dispatch` |
| 同侪的队列失败 | 同侪 | `the executor failed: …` |
| 30 秒内没有回音 | 发送方 | `the peer did not answer in 30 s` |

## 5. 边界：节点必须在某个 workgroup 里

**跨设备派发以「节点在某个 workgroup 里」为前提。** 需要两样东西，而它们来自同一处：

1. **一个够得着的同侪。** 没有它就没有可派发*到*的地方。
2. **一个能听见答复的读方。** 回复到达节点的会话，而节点的会话由它的探测线程读。没有 workgroup 的节点不会启动探测者，于是派发会被送出而永无回音 —— 句柄会报告超时，而不是假装成功。

一个要求在它没有路由的 `node` 上跑的调用方，会拿到「不可达」的拒绝。除此之外没有任何退化。

## 6. 这不是什么

**[roadmap §5](roadmap-v1.0.zh-CN.md) 的红线：内核只发机制，策略属调用方。** 本文描述的正是那个机制，而其余一切的缺席是有意的：

- **不调度。** 没有任何节点*选择*一个任务去哪里。调用方指名那个节点。
- **不拆解、不建依赖图、不定重试策略。** 一帧只出一次；有答复或没答复，由调用方判断。
- **不排队，也没有任务表。** 一次派发是同步的，与它旁边那个本地派发一样。
- **不做跨节点事件关联。** 一个任务的事件跨设备保持同一身份，是 §5 的*第四*项、属后续批次；今天 id 会旅行，而一个节点拿它做什么是它自己的事。
- **没有项目侧服务。** 两个节点都是部署者的；项目只发软件与一个参考 M，自己不跑任何一个（[decisions §33](decisions.zh-CN.md)、§14.3）。

**冻结**：`node` 参数；两个帧 body；`task_id` 的形状；`dispatch` 声明与它的默认拒绝；一来一回各一帧、不批；答复的二选一；四类可读的拒绝；workgroup 这个边界。**未冻结**：一次拒绝是否该有自己的 HTTP 状态（今天四者都是 `500` + 可辨消息）；一个节点如何在手工编辑的文件之外知道*哪些*同侪可以派发；以及 M-to-M 除「它就是跨设备协议」之外的一切。

## 7. 名字指向的那个节点能跑什么

**[settled] 派发指名一个节点；那个节点能跑什么，要问那个节点自己（v1.0 M6-2a）。** §1 按名字把一个任务交给一个节点，紧跟着的问题就是「那个节点能跑这个吗？」。在**本节点**这一侧，答案已经存在，而现在一条命令就能把它收齐：`riscdom node capabilities` 读一个人需要的那五样 —— 节点自己的 `node_id`、它能路由到的执行者、它认识的沙箱定义、以及 QEMU 与 RISC-V 工具链在本地是否就绪 —— 并合并成一个回答。

**[settled] 合并是 CLI 做的，不是一条路由。** 没有聚合端点，本批也不加：`GET /v0/executors`、`/v0/sandboxes`、`/v0/qemu`、`/v0/toolchain` 已经在各自作答，UI 的 node 页读的正是其中三个。CLI 是**纯 HTTP 客户端** —— 它从不直接调 `AppState` —— 所以在本地把它们拼起来，`node_id` 则从 `GET /v0/identity` 里取。**零新路由、零新 capability、零 SDK 改动。** 某一节失败时在原地报告，而不会把整个回答拖垮；某一节回答 `found: false` —— 没有 QEMU、没有工具链 —— 是一个**回答**，不是失败。

**[settled] 它说的是节点*是什么*，从不是任务*该*去哪里。** 一个任务该发往哪个节点，仍然是调用方的（§6 第一条，红线 1）：命令把事实交给调用方，选择是他们的。这里不做任何调度。

**对端那一侧，今天只有一个声明。** 同侪 `peers.json` 条目里带着一个 `capabilities` 列表，而内核只从中读两个词（`server`、`dispatch`）—— 所以它说的是一个节点被*配置声明*成什么，而不是它现在能跑什么。自 **v1.0 M6-2b-1** 起，这份声明不只可读，还**被展示出来了**：`GET /v0/peers` 用本节点自己的条目作答（`capabilities` 都在），而 `riscdom node capabilities` 把它们作为最后一节 **PEER DECLARATIONS** 打印 —— 标题就写明它们是什么：每个同侪对自己说的，一个**声明而非事实** —— 于是调用方不必问任何人就能看到谁声明了什么。它就是本地文件的内容（所以可能含本节点自己那一条）。跨线去问一个同侪它能跑什么，是 **M6-2b**，仍是以后的事。同一问题牵涉的两条「被携带而无人读」的通道，记在 [connection.zh-CN.md §11](connection.zh-CN.md)。

**冻结**：命令的形状（`{node_id, executors, sandboxes, qemu, toolchain, peers}`）、它是 CLI 自己的拼装、以及它只做报告。**未冻结**：同侪的能力面是否有一天要跨线去问（M6-2b），以及 `/v0/peers` 是否有一天会带更多东西。
