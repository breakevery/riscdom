# 性能预算

**状态** v1.0 规范（M7h）｜ **日期** 2026-09-29 ｜ **面向读者** 贡献者，以及必须决定「一项改动被允许花掉什么」
的人。

**本文是什么。** [decisions §18](decisions.zh-CN.md) 定了四个数字，并称它们为**预算**：

> **VM 启动 ≤ 2s；派发往返 ≤ 100ms（同机）/ ≤ 500ms（跨网）；单节点十个 agent ≤ 2GB；日志增长可预测。**

本文把每个数字*是什么意思*写下来 —— 从哪里量到**哪里**、在什么条件下 —— 好让「这项改动破了预算」是一句可被
核对的话，而不是一种感觉。它是一份**规格**；测量的工装在后续批次。

**预算不是测量。** §18 自己的话：它们是产品不再像本地工具的那个数量级，而**破了其中一个的改动，是要作出
解释的回归** —— 不是一条失败的测试。这个不对称是刻意的，它塑造了下面的一切：预算写成整数、用点名的工具
在点名的条件下测量，而**本文里的数字是天花板，不是任何机器都能达到的承诺**。

## 1. VM 启动（≤ 2s）

**从：** 节点决定启动一个 guest 的那一刻 —— 对沙箱 `start` 的调用，此时端口租约已持有、QEMU 命令行已
拼好（`sandbox/src/vm.rs::start`）。
**到：** guest 可用的那一刻 —— `start` 返回 `Ok`，即以下三次握手按序完成之后：

1. **串口连接。** `wait=on` 时 QEMU 阻塞在串口套接字上，所以串口握手完成也是 guest 启动所倚的那道闸。
2. **QMP 连接并协商。** QMP 客户端消费问候（greeting）、协商能力。
3. **被恢复的 guest 在运行。** *仅快照恢复*（`-incoming`）：start 等到重启后的 guest 报告 running
   （`wait_for_running`，以迁移超时为界）。

**测量的是：在已经跑过一次的机器上，对一个配置好的 guest 做冷启动** —— QEMU 在路径里、内核与磁盘镜像在页
缓存里是热的。从未启动过的冷缓存启动，或其实是在恢复一个大快照的启动，是另一回事，**不是** 2s 这个数字
所界定的（见 §6）。

## 2. 派发往返（≤ 100ms 同机 / ≤ 500ms 跨网）

**从：** 控制平面开始处理一个携带任务的请求的那一刻（`POST /v0/tasks`，`server/src/routes.rs` →
`AppState::dispatch_task`）。
**到：** 该请求有答案的那一刻 —— 执行器产出了 `TaskOutcome`、控制平面拿到了它。

**预算落在控制平面与传输上，不落在工作上。** 今天的派发是**同进程、同步**的（`LocalDispatcher` 持有本节点
自己的句柄），执行器在这同一次调用里跑完整个 agent 回合 —— 包含模型调用。模型推理是无界的，也不是这些
数字中任何一个所指的事。于是被测量的量是**派发这一跳**：接受一个任务、把它交给执行器、并收到执行器的
outcome 信封，**所对着的执行器其工作可忽略地短** —— 一个不经过模型往返就作答的本地执行器。被界定的正是
RiscDom 增添的开销，形状是一个 HTTP 请求加一次进程内调用。

- **同机（≤ 100ms）。** 派发方与执行器在同一个节点：只有控制平面那一跳，没有网络。
- **跨网（≤ 500ms）。** 派发方与另一个节点上的**远程**执行器：同样是那一跳，加一次网络往返。**远程执行器
  尚不存在** —— 派发接口为它留了位置（`agent/src/dispatch.rs`：「那个向量正是第二个本地 agent —— 或一个
  远程 agent —— 落脚的地方」）—— 所以这一半现在定规格、等那批落地时再测量。两个数字之差 **400ms**，就是
  设计接受的两个节点之间的网络余量。

## 3. 内存（单节点十个 agent ≤ 2GB）

**数的是什么：** **单节点上十个并发运行的 agent** —— 十个在飞的 agent 回合，各带自己的 guest。测量对象是
**为这些 agent 服务的进程的常驻内存**：节点自己的进程，加上它启动的十个 QEMU guest 进程，以 RSS 相加。
Guest 内存是可见的那部分 —— 一个 agent 的 guest 按默认 `VM_MEMORY_MB = 128` MB 配置
（`agent/src/tools.rs`）→ **十个 guest ≈ 1.25GB** —— 天花板剩下的部分，是 QEMU 每进程的开销、guest 触碰的
页缓存，以及节点自身的工作集。

- **不数什么：** 节点空闲（零 agent）时的基线不是本题（它很小、且不属于任何预算）；**单个** agent 的占用
  也不是本题 —— 预算说的是十个同时跑时那条曲线的形状，因为那正是「一个靠实例数扩展的节点」必须回答的事。
- **RSS，不是虚拟大小。** 虚拟大小算进了进程从未缺页载入的映射；RSS 数字才是机器真得有的内存。预算是一条
  RSS 预算。

## 4. 日志增长（可预测）

**可预测的意思是：增长是「发生了什么」的一个既定函数，没有任何东西只随时间增长。** 审计存储是一个
**append-only 的 SQLite 数据库**（`audit/src/store.rs`）：每个事件一行，而 `BEFORE UPDATE` / `BEFORE DELETE`
触发器是硬保证 —— 日志**无法通过 SQL 被改写、裁剪或缩小 —— 没有轮转、没有保留窗口、没有 `DELETE`**。
存储单调增长，永不把内存或磁盘还回去。

于是这个预算是一个形状，而且可以核对：

- **一个事件一行。** 行数与事件成正比，永不与运行时长或客户端数成正比。一个起了但空闲的节点，增长为零。
- **每行字节有界。** 一行的大小是该事件的规范 JSON 加它那对哈希；它不取决于进程跑了多久。
  字节 ≈ 事件数 × 平均行大小。
- **没有隐藏的放大。** [observability §1](observability.zh-CN.md) 的结构化日志行在 stderr 上是同一个故事：
  每个事件一行，没有任何东西被缓冲进无界内存。一个「可预测」的写入器同样意味着**没有无界标签或键**
  （observability §2 的规矩）—— 一张以「随工作量增长的东西」为键的表，正是日志与指标端点同时不再可预测的
  方式。

**不承诺什么：** *速率*。可预测关乎曲线的形状，不是「每秒事件数」的上限 —— 速率由运维者通过控制「节点被
要求做什么」来控制。

## 5. 预算怎么被核对

每个预算都点名了它的工具与条件，所以一次核对是可复现的：

| 预算 | 用什么量 | 条件 |
|---|---|---|
| VM 启动 | 在沙箱 `start` 前后取时间戳，或事件流上的 `vm.started` 时刻 | 配置好的 guest、热缓存（§1） |
| 派发往返 | 在控制平面那一跳前后取时间戳（§2） | 工作可忽略地短的本地执行器；远程情形待远程执行器落地后 |
| 内存 | 节点自身进程 + 它的 QEMU 子进程，RSS 相加 | 十个 agent 同时运行 |
| 日志增长 | 审计存储的行数与文件大小（[observability §2](observability.zh-CN.md)） | 在已知数量的事件之前与之后 |

- **可观测性已经提供什么。** [observability.md](observability.zh-CN.md) §2 之所以把 `/metrics` 定规格，
  正是要给预算核对一个来源：日志一侧有 `riscdom_audit_events` 与节点身份，状态标尺有连接数与 agent 数。
  **指标并不就是整套工装** —— §17 的第一批族里没有内存指标、也没有计时指标，所以内存与往返目前是直接
  计时。预算与可观测性在审计计数与状态标尺处相会，并非处处相会。
- **工装是后续批次。** 本文只固定定义；把它们测量出来、记录下来、并把一次运行与预算对比的工具，会像其它
  每个 M7 条目一样，在规格之后自行落地。

## 6. 不覆盖什么

- **没有尾部分位、没有峰值。** 这里每个数字界定的都是一次典型、可复现的行为（§5 的条件），不是最坏情形。
  一个 p99、一次负载下的峰值、一次冷缓存的首启 —— 都不是 §18 所预算的，也都不在此核对。预算是用户能感到
  的那个数量级，不是服务级目标。
- **没有绝对的机器承诺。** 「≤ 2s」是产品所面向的那一类机器的天花板、在一台热宿主上于 §5 条件下满足 ——
  不是对每一台能跑节点的宿主的陈述。
- **代码里没有任何东西在强制它。** 没有测试会因为漏了预算而失败；§18 的要点正是*评审者*会问、改动会自己
  解释。把预算变成一道闸，需要它自己的决策。
- **测量工装、远程执行器，以及任何内存指标**都是后续批次；本文是它们将要依据的那份契约。
