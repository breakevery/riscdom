# 跨链验证

> **状态** v1.0 规范（M6-5-1、M6-5-2a、M6-5-2b）｜ **日期** 2026-09-30 ｜ **面向读者** 内核开发者，以及部署不止一个节点的人。

[roadmap §7](roadmap-v1.0.zh-CN.md) 有意留了**三个问题**没答。[audit-v2 §5](audit-v2.zh-CN.md) 把它们记下来、却没有替它们收口。本文是替它们收口的地方 —— 而且是**分片**收口，因为它们需要的机制正是 M5 刚完成的那一个，每一片是一个批次。

## 1. 三个问题，以及它们背后站着什么

1. **汇总链是否需要它自己的 `prev_hash`。**
2. **跨链引用怎么验证** —— 按摘要、按区间，还是两者都要。
3. **当两个段都声称同一个动作时，冲突怎么判定。**

三个问题背后是同一个事实：**两台设备各持一条链，各有自己的创世。** §4 的 `head_prev_chain` 是唯一把它们连起来的东西 —— 一个在*发送方*链上的哈希 —— 而接收方**看不到发送方的链**。摘要（M4e-1）是对**链头**的承诺；引用点名的却是一个**内部点**。头承诺验不了内部点。

**M5 已经铺好的**（以及它有意没做的）：

| 已在 | 还缺 |
|---|---|
| 段行上的 `head_prev_chain`（`segments.head_prev_chain`，M5-1b） | 一个**验证者** —— 无人读它 |
| 锚点随结束帧到达中心（M5-3c-2） | 锚点的**长度** |
| 送达、重建与 `merge_segment`（M5-3c-2） | 任何「该段**确实承接自**锚点」的检查 |
| `ChainDigest { chain, length }`（M4e-1），服务器按节点持有 | 一个**过去某点**的摘要 |

## 2. 选择：按摘要，锚点长出第二半

**[已定]** **对 (2) 的回答：按摘要。** 一个可验证的锚点是一个 `(chain, length)` 对 —— 段开启那一刻发送方链的**头哈希**，以及**那条链当时有多长**。这个对，正是 M4e-1 所说的「对一点的承诺」；缺的只是锚点过去只带了它的前一半。

- **不是按区间。** 一个区间证明（「从创世到锚点的一切」）意味着在 §127 定下的那一个公式旁边，再添第二套摘要结构 —— Merkle 树或滚动哈希。owner 在第一批里否掉了它。
- **不是汇总链。** 把各摘要串成一条链，能让中心证明*它*被告知了什么、且顺序如何；它对某节点的内部点仍然什么也说不了，而且会让中心成为历史的持有者 —— 而 §6.2 明确避开这一点（「持有的是摘要，不是消息」）。

**M6-5-1 落地的是证据，不是检查。** 本批加入：

- **`segments.head_prev_length`** —— 紧挨 `head_prev_chain` 的一个 `INTEGER` 列；在此列存在之前写下的行为 `NULL`。它与头在**同一刻**读出（在段自己的开启事件被追加**之前**），所以两者点名的是**同一个**点。列坐在链旁边，故 `AUDIT_SCHEMA_VERSION` **保持 1**，不改写任何东西。
- **`segment_done` 帧上的 `anchor_digest` / `anchor_length`。** `anchor_digest` 与 `head_prev_chain` 是**一个值、两个名字** —— M5-3c-2 的字段保住它的名字，好让每一个既有读方继续工作；锚点词汇则拿到自己那个指向同一字符串的名字。两个名字都由同一行字段写出，因此不会分叉；读方优先读 `anchor_digest`、回落到 `head_prev_chain`，所以早于本批的发送方仍然读得进来。
- **`adopt_segment` 记下两半。** 中心写下 owner 报告的东西 —— 名字、引用、以及引用的长度。**它一样都不验。**

## 3. 接收方验什么 —— 以及验不了什么（M6-5-2a）

**[已定]** **中心验的是「交付」，验不过就拒、并记下。** 自 v1.0 M6-5-2a 起，`receive_segment` 在重建段与合并之间验两件事：

| 验什么 | 怎么验 | 回答什么 |
|---|---|---|
| **信封** | 事件对收尾的那个结束帧 | 是不是每个位置 `0..total` 都恰好到一次？这个流是不是发给本节点的？ |
| **重建** | 对中心刚写出的存储调 `verify_chain` | 这个存储是不是完整的？ |

- **`host.audit.chain_verified`** —— 交付站得住。detail 带 `segment_id`、`from`、`anchor_digest`、`anchor_length`、`events` 与 `checked`（`"delivery"`，或对没有长度的旧锚点记 `"skipped"`）。随后 `merge_segment` **照旧**运行。
- **`host.audit.chain_rejected`** —— 交付站不住。detail 带同样的字段外加 `reason`。**不调 `merge_segment`**：该段没有任何东西进入主链，行既不是 `folded` 也不是 `forked` —— fork 是「两边都是真的、还没人说谁对」，而这是「交付自身站不住」。段自己的文件**留下**：被拒的交付也是证据。
- **一个没带任何事件的流会被作答。** `total: 0` 且什么都没到 = 自洽，于是一个**空段会被验过并并入** —— M5-3c-2 把这种情况扔在地上，所以合法的空段从未被并入，而发送方可能以为它交付了一个中心从未听说的段。`total: n` 而什么都没到 = 缺口，被拒。
- **锚点的 `anchor_length` 为 `None` 的段记为 `skipped`** —— 它在长度列存在之前开启，无物可比。它会照常并入，而行上写明「没验什么」，而不是假装验过。

**它有意不验什么 —— 而这是诚实的那一半。** 中心**无法**声称那些事件曾经在发送方的链上，也无法声称该段真的承接自 `anchor_digest`：流带的是事件用于转录的五个字段、**不是它们的哈希**（M5-3c-2 有意如此 —— id 与哈希属于发送方的链）。头承诺验不了内部点（§1），且没有任何摘要历史可供比对过去某点。所以一次通过的检查记为**已检查**，绝不是**已证明**。

## 4. 流自己的链 —— 以及那根缺失的环节（M6-5-2b）

**[已定]** **每个事件现在带着它被写下时的两个哈希，中心会重算它们。** 自 v1.0 M6-5-2b 起，`segment_event` body 带 `hash` 与 `prev_hash`（源行自己的值，被搬过来、发送方**不**重导），于是接收方可以多问两件事：

- **每个事件是否重算得出**它声称的哈希 —— 用 `audit::compute_hash`（**调用、从不修改**），且 detail 的渲染方式与发送方 `append` 完全一致？
- **每个事件是否承接**前一个（第 *n* 条的 `prev_hash` 就是第 *n-1* 条的 `hash`）？

末条不需要额外的东西：重算它*就是*「它自己的哈希自洽」这一查。裁决仍用同样的两个词，各多一个取值：

| 发生了什么 | `checked` | `linkage` |
|---|---|---|
| 流重算且链接成功 | `delivery+chained` | `ok` |
| 没有（合并被拒） | `delivery` | `broken` |
| 发送方没带哈希（**跨版本窗**；仍合并） | `delivery` | `skipped` |
| 锚点没有长度（仍合并） | `skipped` | `skipped` |

**[已定] 锚点本身仍未验，而且以现有交付物无法验 —— 这是「尚欠的活」，不是疏忽。** 锚点（`head_prev_chain`）是 `segment_opened` 标记**之前**那个链位置，而一个段被交付的事件是在该标记**之后**的那一段。所以第一条被交付事件的 `prev_hash` 是**标记**的哈希，离锚点差一环；而中心永远握不到那个标记：它是该段*生命*的记录，不是它的事件之一。早先的计划假定 `events[0].prev_hash == anchor_digest`；它**按构造就是假的** —— 两者恰好相差那一行 `segment_opened`。要让它成真，需要再多一件证据（标记自己的哈希，或把锚点重新定义成该哈希），**记为 M6-5 尚欠的工作**，不是本批交付的东西。

**所以，这份链接检查证明的是「这个流是一条链」，而不是「它是发送方链上的一段」。** 它能抓出被改过的 detail、被换序或丢掉的事件，以及用别的流拼起来的流 —— 而它不声称锚点。

## 5. 另外两个问题

**对 (1) 的回答：锚点不需要汇总链。** §2 的选择在没有它的情况下回答了 (2)。一条自备 `prev_hash` 的汇总链回答的是另一个问题 —— *中心*被告知了什么、顺序如何 —— 那是 **M6-5-4**，不在第一批。

**对 (3) 的回答：内核给可观测性与工具，不给规则。** M5-2 已经做了诚实的那一半：尽可能窄的测试（`actor`、`action` 与清除后 detail 的精确相等）、**fork** 而不是合并、两边都留下（[audit-v2 §11](audit-v2.zh-CN.md)）。剩下的是**拿 fork 怎么办**，而 §33 的多数规则搬不过来：它裁定的是「一个节点知道什么」（liveness，已由 M5-3a 的证人规则实现），不是「两个动作谁对」。一条**规则**是策略 —— 属调用方、不属内核（roadmap §1）。所以 M6-5-3 是**可观测性 + 一件手动工具**：fork 看得见，且可导出给人判断。不做自动裁定，**M6**。

## 6. 还没有的东西

- **锚点那一环**（见 §4）：把第一条事件接回 `anchor_digest` 需要 `segment_opened` 标记的哈希，而它不被交付。记为 **M6-5 尚欠的工作**。
- **不新增帧。** M6-5-2a 与 M6-5-2b 只是给 M5-3c-2 已经在发的帧加成员；没有任何新连接。
- **不做汇总链、不做它自己的 `prev_hash`、不做区间证明**（M6-5-4）。
- **不定冲突规则**（M6-5-3），也不改 M5-2 的精确测试。
- **不改 `ChainDigest`。** 它仍然是对链头的承诺。
- **`compute_hash`、`verify_chain`、append-only 触发器、路由表与 33 名的能力词汇表都未动。** 链旁边多一列、既有帧 body 多两个成员，都不是格式变更：版本原地不动。

**冻结**：锚点是一个 `(chain, length)` 对；`segments.head_prev_length` 存在，且对旧行为 `NULL`；`anchor_digest` ≡ `head_prev_chain`（一个值、两个名字，旧的那个永不删除）；交付的段**对着它自己的结束帧**被验、其事件自己的哈希被**重算并链接**；锚点没有长度、或发送方没带哈希的段记为 **skipped**；验不过的交付**记下且不并入**、其文件留下；冲突就 fork、绝不自动裁定。**未冻结**：`segment_opened` 标记的哈希是否有一天上线，好让**锚点那一环**能被验；中心将来是否缓存过去的摘要（今天只留最新）；是否有一天要区间证明；以及 M6-5-3 那件工具的形状。
