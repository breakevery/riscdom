# RiscDom v1.0 纲领

**版本** 1.0 草案 ｜ **日期** 2026-09-27 ｜ **基线** v0.9.9（`3365970`）｜ **性质** 内核 API 冻结，
三层功能兑现。

**受众**：内核开发者 —— 其中 §6（冻结级）与 §8（沙箱插件接口）同时是**发行集成者**的规范。

**怎么读一条决策。** 下面的每条决策都带三个标签之一。**[已定]** —— 讨论已收敛，形状不会再动。
**[默认]** —— 暂时这样定，且**有意**可改；十四条全部收在 §14。**[待定]** —— 有意留到需要它的那个
里程碑再定。已经写进 [decisions.zh-CN.md](decisions.zh-CN.md) 的决策，本文**按编号引用、不再重决**：
本文加的是讨论在其之上收敛到的形状。

**本文不是什么。** 它是一份纲领 —— 不是日期，不是规范，也不承诺每一行都会被实现。当某一行说某个
机制已存在，那它就在内核里、或在某条已写下的决策里。之所以现在就把它落盘：一场花了好几个对话才收敛的
讨论，不该再被重新讨论一次 —— 只活在对话里的纲领，就是会丢的纲领。

## 1. 定位与边界

**一句话。** v1.0 是内核毕业的地方：**三层功能跑起来**，而**内核 API 停止移动**。

**那个让形状不跑偏的类比。** v1.0 的几件东西就是操作系统的几件东西；用这个名字称呼它们，
「什么属于内核」才变得可回答：

| 操作系统 | RiscDom |
|---|---|
| 进程 | 沙箱**实例** —— 由 `sandbox` 启动、停止、快照 |
| 系统调用日志 | **审计链** —— 只追加，一个动作一条事件 |
| 调度器 | **M**，§9 描述的那个 AI 调度员 |
| 分布式 IPC | **跨设备** —— `@`、房间、转发（§4） |

**与 multi-agent 的关系：一条能力线，不是一个版本。** **[已定]** v0.8 与 v0.9 交付的是多 Agent 的
**接口** —— 名册、派发端点、远端句柄、沙箱请求队列 —— v0.9.9 的发行正文就是这么写的（「接口，
不是策略」）。v1.0 交付的是**能力**：好几台设备上的好几个 AI，真的在分工。这样读的话，
「multi-agent」不是 v1.0 新加的东西；它是好几个版本一起推进的一条线，而 v1.0 是它变得可用的那个点。

**四条红线。** 这些是约束、不是目标；下面每一个里程碑都得让它们活着过去。

- **[已定]** **不内建监工。** 内核只给机制、从不定策略（决策 §1）。一个自带 AI 监工的内核，等于把本该
  属于调用者的选择钉死 —— 而 M（§9）正好证明不需要这么做：M 是控制平面的一个*调用者*。
- **[已定]** **不官方运营服务。** 本仓不为任何人跑服务；跑节点、跑内网服务器、跑跨区域服务器的是
  部署者（决策 §1）。
- **[已定]** **不追通用沙箱。** RiscDom 是「以 RISC-V 为核心的可插拔安全沙箱运行时」：RISC-V 是主色调、
  是基底、是默认实现，但不是唯一实现（决策 §2）。
- **[已定]** **不改审计不变量。** 链的保证就是产品本身；audit v2（§7）把*语义*扩展到
  「主链 + 临时段」，并在段首**加元数据、不改哈希公式**（决策 §33）。任何会改公式的事都不是 v1.0 的
  条目，而是另一个项目。

## 2. 三层递进

| 层 | 它是什么 | 它需要什么 |
|---|---|---|
| **L1 —— 单设备** | 一台机器上多个沙箱、多把 API key、多个 AI | 实例 API（§3）、M（§9） |
| **L2 —— 连接** | 一个局域网上的 workgroup，加一台面向公网的跨区域服务器 | 节点身份、签名与房间（§4） |
| **L3 —— 跨设备派发** | 好几台设备上的好几个 AI 互相派发 | L1 **与** L2，加 audit v2（§5） |

- **[已定]** L1 与 L2 碰的是内核的不同部分，**可以并行**推进。
- **[已定]** L3 依赖前两层；它的审计那一半依赖 audit v2：一次跨设备的派发，必须能在一串跨设备的链里
  被验证。

## 3. 第一层：一台设备上的多个沙箱

- **[已定]** **定义与实例。** 沙箱*定义*（跑什么：镜像、资源、语言）与沙箱*实例*（一个正在跑的东西）
  是两个名字、两种寿命。A-2 与 C-2 是**同一个定义**实例化两次 —— 这对名字存在的意义正在于此。决策
  §31 已经把 `default_sandbox`（配置）与 `current_sandbox`（运行时状态）分开；v1.0 补上「多实例」的那
  一半。
- **[已定]** **裸机不复用。** 一个实例拿自己的一台 VM：一个串口、一台 VM、一个实例。发行正文里记的
  「每个 agent 同时只有一个 VM」正是被它取代的东西，而取代它的是显式的实例表，不是共享。
- **[已定]** **M 是 AI 调度员，且始终在内核之外。** M 有三层 —— 节点、局域网、跨区域（§9）—— 它通过
  **控制平面**驱动内核，也就是人用的同一个接口（决策 §6）。M 从不进入内核：没有编译进去的监工，也没有
  特权后门。
- **[已定]** **执行者申请，M 决定。** 想改沙箱的执行者走**待批槽** —— 决策 §36 已经定下的那个请求面
  （`POST /v0/sandboxes/requests` 只需要 `agent.run`；决定则需要 `sandbox.read` 加上该请求的动作所
  蕴含的那个 capability）。
- **[已定]** **内核给 M 的五个 API**：建实例（`POST /v0/sandboxes/instances`）、删实例
  （`DELETE /v0/sandboxes/instances/{id}`）、列实例（`GET /v0/sandboxes/instances`）、问节点能做什么
  （`GET /v0/capabilities`），以及 `Task.instance` 字段 —— 于是被派发的任务会写明它跑在哪个实例上。
- **[已定]** **多 LLM 配置。** 今天一套提供方配置就是一个值；一台节点上的好几个 AI 需要好几套。这个设置
  变成一张**映射表**（按角色或按名字），而这是一次 `settings.json` 的 schema 变更 —— **v1 → v2** —— 因此
  它随 §6 的迁移机制一起走。
- **[已定]** **新增 capability。** `sandbox.instantiate`（建实例）、`sandbox.mux`（对不止一个动手）、
  `executor.register`（作为执行者加入某个节点的名册）加入词汇表 —— 其中 `sandbox.read` 已是第 29 个、
  `sandbox.assemble` 是第 31 个（决策 §31、§36）。
- **[已定]** **M 的审计事件**：`m.sandbox.spawn`、`m.sandbox.reap`、`m.request.approve`。M 做过什么
  在链里、署名是 M，就挨着执行者申请过什么 —— 这正是决策 §33 对「AI 发起的权威」要求的事后审计。
- **[已定]** **API key 断了是配置变更，不是换实体。** M 的 key 失效时，要改的是 key、base URL 或
  model；M 的循环重启（§9），继续的是*同一个* M。身份不是凭据。

## 4. 第二层：连接

**模型：局域网上的 workgroup，加一台面向公网的跨区域服务器。** **[已定]** 两种形状，不是三种。更早的
讨论带着三种拓扑；本节记录的就是这次收敛，而它是**朝**决策 §7 收敛，不是背离。

**一个网络之内 —— workgroup。**

- **[已定]** 一个 workgroup = 一个局域网上的节点 **+ 一台内网服务器**（共识 **B**：内网服务器存在；
  这不是一张只有对等节点的扁平网）。
- **[默认]** **发现。** 内网服务器**静态下发节点表**；UDP 广播是补充，用于在两次下发之间出现的节点
  （决策 §7 已经点名 UDP 广播加房间隔离作为发现机制）。见 §14.14。
- **[已定]** 节点身份是 **Ed25519** —— 公钥与私钥，存 `<data-dir>/node.key` 或钥匙串（决策 §13：
  标准格式、默认 mode 600、钥匙串可选）。
- **[已定]** **签名。** `@` 既是寻址、也是签名（决策 §7）：一条 `@` 寻址的消息，由它所点名的密钥签名。
- **[默认]** **房间。** 一个房间 = 成员名单 + 它的规矩（速率、谁可以 `@` 谁、是否要求签名），落点是
  `rooms.json`。见 §14.5。
- **[已定]** **凭据批量导入**是 `peers.json`：每条 `{node_id, addresses[], public_key, capabilities,
  rooms[]}`，正是决策 §13 已经定下的形状。

**跨网络 —— 跨区域服务器。**

- **[已定]** 它是**专用**服务器：一台新服务器，不是一台兼职做桥的内网服务器。
- **[已定]** 它的四个角色：**信令**（谁在哪）、**转发**（替两个节点搬运它们自己搬不动的消息）、
  **管理**（注册表与房间定义）、**审计汇聚**（收集链的摘要 —— 见下一条）。
- **[已定]** **不自建打洞。** RiscDom 不自己实现 NAT 穿透。两个节点先试直连；失败就走转发 —— 而
  **转发是主路径**、不是例外。这就是决策 §7 那句「公网被当成一个大局域网」的意思：一座双方都主动
  拨出去的、无状态的桥，它消掉 NAT 与动态寻址，却不因此对任何人的数据拥有权威。
- **[已定]** **直连成功就退出数据路径。** 一旦两个节点直连上了，转发不再替它们搬任何数据；留下的
  是管理层 —— 注册表与房间定义。
- **[已定]** **审计按节奏走。** 摘要在 **30 秒**的定时器上成批送；**关键事件**（一次驱逐、一次 fork、
  一次临时中心接管）在发生的当下就推。
- **[已定]** **部署**：先一台起步，多台在 v1.x。多服务器冗余是商业化层的事，不属于本模型（决策 §33）。

**这几层不许违反的东西** —— 四条，都已写下：

- **[已定]** **日志全复制。** 每个节点持有全史并交叉验证它 —— 群聊模型（决策 §7）。上面的汇聚角色收的是
  *摘要*；它不会变成历史唯一存放的地方。
- **[已定]** **中心是一个特殊节点**：同一个内核，靠部署区分 —— 细胞分化模型（决策 §33）。
- **[已定]** **三层抑制**：等待期（30 秒 – 2 分钟静默重试），然后全局确认（多数节点都报「够不到中心」
  才可能触发），然后退避加顺位（决策 §33）。
- **[已定]** **临时中心。** 一台桥机器可以临时顶上；它写的事件带 `provisional: true`；真正的中心回来时，
  无冲突的一次并入，有冲突的一次两边都留 `fork` —— 绝不静默合并（决策 §33）。

**一句话概括这次收敛。** **[已定]** 「中心化还是去中心化」不是两种网络之间的选择：它是**同一个模型的两种
状态** —— 直连成功，或流量经中心 —— 而当前是哪一种，对用户不可见。

## 5. 第三层：跨设备调度

**三层 M 协作。** **[已定]** 顶上是跨区域 M，下面是局域网 M，再下面是节点 M，叶子是执行者。每一层看
它下面那一层，用的是它看一个人时用的同一个接口（决策 §6）。

**内核提供什么** —— 这份清单就是全部：

- **[已定]** **节点注册表**：有哪些节点，以及怎么够到它们；
- **[已定]** **能力描述**：一个节点能跑什么（决策 §2：内容不受架构约束，所以这是关于节点的问题，
  不是关于客机的问题）；
- **[已定]** **派发接口**：按名字把任务交给一个节点；
- **[已定]** **跨节点事件关联**：一个任务跨设备之后，它的事件仍然保有一个身份；
- **[已定]** **待批槽**：决策 §36 的请求面，也是「动手前先问」能跨设备成立的原因。

**内核不提供什么** —— 有意为之，这就是红线 1：

- **[已定]** 不做工作流引擎、不做依赖图、不做重试策略、不做调度算法。谁拆解一个复合任务、各部件怎么分配，
  是**策略**，而策略属于调用者（§9）。一个自带调度器的内核，等于让每一次部署都听命于同一种调度。

- **[默认]** **M 之间复用跨设备协议。** 两个 M 就是控制平面的两个客户端；不需要它们自己的协议。见 §14.6。
- **[已定]** **跨链审计验证依赖 audit v2**（§7）：没有一种可验证的方式把两台设备的链关联起来，
  「这个任务发生过」就是一句主张，不是一个事实。

## 7. audit v2

- **[待定]** **本节触红线 5** —— *拿不准就先问*（`PROJECT_CONSTITUTION.zh-CN.md` §8）—— 而它
  **不由本文授权**。决策 §33 就是这么说的：「v1.0 的跨设备设计必须单独获批」。下面这份计划，就是将来
  去申请那次授权时要覆盖的东西。
- **[已定]** **每设备一链，加临时段。** 扩展的是链的*语义*、不是它的公式：段首带一个**跨段引用** ——
  加的是**元数据**，哈希公式不变。
- **[已定]** `provisional` → 并入（无冲突的一次合并、标记清除）或 `fork`（两边都保留标记，且绝不静默
  合并）。
- **[待定]** 仍然未定，而且是有意留着的：汇总链是否需要自己的 `prev_hash`；跨链引用怎么验证（按摘要、
  按区间，还是两者都要）；以及当两个段都声称同一个动作时，**冲突**怎么判定。

## 8. 沙箱插件接口

- **[已定]** **进程外、stdio、JSON lines** —— 与 `worker` 同构（决策 §3）。不做进程内插件、不做动态库、
  不做 ABI。
- **[已定]** **机制层必含，语义层可选。** 启动 / 停止 / 执行 / 输出是必含的；快照 / 指纹是可选的 ——
  而插件**声明**自己有哪些能力（决策 §3）。
- **[已定]** **按设计，架构无关。** 插件内容不受架构约束，内核代码也不得假设客机是 RISC-V（决策 §2）。
- **[默认]** **能力声明格式**是一份草案（§14.11）：它是这个接口里唯一应当**最后**才冻结的部分，
  因为它是插件将来必须实现的那部分。
- **[已定]** **信任模型 = 能力受限。** 插件的权力就是它声明的那些能力，按与其它一切能力相同的方式
  检查（决策 §3 复用 capability 模型）。
- **[已定]** **预置环境**是四个机制，全都提供，用哪个交给策略：持久目录（一个实例目录加一个共享目录）、
  清单来源（插件声明、内核扫描、开发者手写文件，合并）、安装路径（一个手动的 shell 加一个 setup 脚本）、
  AI 感知（系统提示注入加一个工具查询）（决策 §4）。
- **[已定]** **插件仓库在 v1.x 建仓** —— 一个官方索引加多个社区仓库，工具配置多个来源（决策 §5）。
- **[已定]** **RISC-V 定位**：沙箱可以经插件扩展到别的架构，而 RISC-V 仍是基底与默认实现（决策 §2）。

## 9. M 的形态

- **[已定]** **M 是 AI 调度员，不是静态管理器。** 它决定*什么跑在哪*，然后就此打住：M 不坐在数据路径上、
  不代理任务的 I/O、也不在内核里。
- **[已定]** **三层** —— 节点、局域网、跨区域（§5）。每一层都是同一类东西；不同的是它能看见什么。
- **[已定]** **M 的权限就是控制平面的权限。** M 拿自己的凭据直接调 API —— 与人用的是同一个面 —— 不为
  使用它而向谁申请许可。M *能*做什么，由它的 capability 界定，而不是由内核里的某个守门人界定。
- **[已定]** **M 的循环与 M 的配置是两件事。** 循环是一个程序；配置是一个文件。改了配置，循环就
  **重启** —— 它不会去改一个正在跑的循环的信念。
- **[已定]** **M 的状态外置。** 真相住在审计链、实例表与待批槽里；M 的内存上下文只是它们的一份缓存。
  这是**前提、不是优化**：一个必须靠 M 的记忆完好才能知道「什么在跑」的设计，活不过上面那次重启。
- **[已定]** **M 失联时变得保守** —— 不派任何新任务、不派生、不回收，并且告诉用户。（在看不见的时候回收，
  就是一个监工摧毁自己看不见的工作的方式。）
- **[已定]** **回来的路是一次配置变更，不是换实体。** 用户修好 key（或 base URL、或 model）；M 的循环
  重启，**从磁盘**重建上下文；继续的是同一个 M。没有「新 M」需要向审计链解释 —— 那次变更本身就是链里的
  一条事件。

## 10. 设置统一

- **[已定]** **所有设置走 HTTP**，不走 shell 命令。shell 命令是一种传输，而一种只在桌面端存在的传输，
  就是第二种配置节点的方式。
- **[已定]** **三条路径，同一种行为。** 本机桌面、远程桌面、浏览器客户端够到的是同一批端点；不同的只有
  「是哪台节点」。
- **[已定]** **本机桌面常开一个内嵌 server**，绑 `127.0.0.1`。`lan_enabled` 不再意味着「server 该不该
  跑」，而开始意味着「局域网能不能够到它」—— 这正是它那条警示一直在说的意思。
- **[已定]** **两类设置，分开放。** *节点级*设置跟节点走（被配置的是那个节点）；*客户端级*设置跟客户端
  走（我在看哪台节点、它的 token 是什么）。
- **[已定]** **`host-tauri` 变薄。** 剩下的只有桌面上才能做的事：窗口、菜单、文件对话框、钥匙串壳、
  客户端级设置。
- **[已定]** **设置页 = 调试面板。** 每个值都显示它的**值**、它的**来源**（文件、默认值，还是被覆盖）
  与它的**状态**；底下的 JSON 可以原地查看与编辑；并且在**每一个**平台上都可读可写 —— 本机桌面、远程
  窗口、浏览器，一视同仁。
- **[已定]** **现有的每个 tab 都被改造**，并且**不加「高级」独立 tab**：每个 tab 都变成调试面板，因为
  「高级」tab 正是一个普通 tab 里缺失的信息躲藏的地方。

## 11. 生态起步

- **[默认]** **一套 SDK** —— 先做 Rust 与 TypeScript，因为这是本仓已经在说的两种语言（内核与前端）。
  见 §14.12。
- **[已定]** **管理程序迁往自己的仓库** —— `riscdom-adminapp` —— 在 v1.0。v0.9.9 的发行正文已经写明：
  它在 v0.9 随本仓分发，到 v1.0 独立成自己的仓库。
- **[已定]** 与它一起的：作为文档发布的**配置 schema**；**可观测性**（一个节点报告关于自己的什么，
  报到哪）；**`riscdom-backup`** 包（决策 §19：审计存储、快照与凭据作为一件可搬走的单位）；
  **性能预算**（决策 §18：是预算，不是测量值）；以及第二个仓库需要的 **CONTRIBUTING** 增补。

## 12. v0.9.x 结转

这些是 v1.0 继承的开口项。列在这里，是为了让任何讨论都不必重新发现它们。

- **[已定]** **D4：桌面端控制操作。** 浏览器的控制调用今天是有意拒绝的（「控制随 D4 到来」）；D4 就是
  把它们落到 HTTP 上的那一批。
- **[已定]** **D5：桌面端统一。** 桌面端自己的路径与浏览器的路径收敛到同一个 HTTP 面上（§10）。
- **[待定]** **`task_id` 缺口。** `POST /v0/agent/run` 不收 `task_id`，于是当多个客户端跟同一个节点时，
  一个事件帧无法归属到产生它的那个任务。v0.9.9 的正文把它记作「在 v1.0 之前解决」。
- **[待定]** **`--follow` / `--wait` 的毛边**：进程退出时流可能还开着。
- **[待定]** **Python 作为客机语言**（已有 C、Zig 与 Rust）。
- **[待定]** **会话库的 WAL 模式** —— v0.9 有意不设（决策 §54）。
- **[待定]** **Linux 与 macOS 的 server zip** —— v0.9.9 只发了 Windows 那份。
- **[待定]** **QEMU 与门禁的并行 flake** —— QMP `10054` 那一族，以及端口竞争的挂死；每次都如实报告，
  从不粉饰。
- **[待定]** **GUI 开关的点击目标。** 一个开关就是一个宽约 14 px 的裸复选框；v1.0 全仓换成一个像样的
  `Toggle`，命中区是整行。
- **[待定]** **「首次重启停本机看板」。** 来自 v0.9.9 走查的一条观察：第一次重启后应用停在**本机**看板，
  且远端地址没了。清掉残留的开发进程后它不再复现，也没有任何代码路径能解释它；
  `manual-acceptance.zh-CN.md` 的层次 9 是给它结案的地方。
- **[已定]** **NetworkTab 的死循环已修** —— 提交 `dd599c0`，本批一并推送：三个 effect 依赖的是整个
  store 对象、而不是 store 里那些稳定的 `useCallback` 函数，于是表单在每次渲染时被重建，两个开关与两个
  输入框都在毫秒内被还原，页面在空闲时占掉约三分之一核。

## 14. 待决清单

十四条，每一条都是**一个可改的默认值**。它们都不阻塞上面的里程碑；每一条都记下讨论收敛到的取值，
这样改它就是一次决策，而不是一次漂移。

1. **沙箱复用规则。** **[默认]** 复用听**能力声明**的：插件说哪些可以复用、哪些不可以。
2. **实例生命周期。** **[默认]** 任务级，超出任务的那部分可配保留。
3. **M 的参考实现。** **[默认]** 官方出一份，放在 `examples/` 下，与已经住在那里那份参考监工并列。
4. **实例上限的配置落点。** **[默认]** 扩展 `settings.executors`，而不是新开一节。
5. **房间定义落在哪。** **[默认]** `rooms.json`。
6. **M 之间怎么通信。** **[默认]** 复用跨设备协议 —— 不为 M 另造协议。
7. **M 的 `agent_id` 形状。** **[默认]** 与执行者同构，于是一份名册同时描述两者。
8. **API 策略落盘时点。** **[默认]** M1，立刻。
9. **先迁移机制还是先 schema。** **[默认]** 先做机制 —— 一份没有迁移路径的 schema 变更，是一份没人能
   应用的 schema 变更。
10. **插件接口冻结时点。** **[默认]** M3。
11. **能力声明格式。** **[默认]** §8 的那份草案。
12. **SDK 优先级。** **[默认]** 先做 Rust 与 TypeScript。
13. **内网服务器形态。** **[默认]** **有**内网服务器（共识 B）；§4 的 workgroup 依赖它。
14. **workgroup 发现。** **[默认]** 优先由内网服务器静态下发节点表，UDP 广播作补充。

## 15. 风险

- **audit v2 触红线 5。** 这里唯一一件不只是「难」、而是**未获授权**的事：扩展链的语义必须单独获批
  （决策 §33）；若那次授权被拒，v1.0 的跨设备那一半就失去了它的验证故事。
- **时机。** 多个 AI 协作是前沿，而不是刚需。v1.0 的第三层可能既正确、又太早 —— 而为一种还没到来的用法
  建设，正是一个内核长出策略的方式。
- **没有参照物。** 「一个 AI 派发一群 AI」没有既定形状，所以 M 的设计没得可抄，也没什么能一眼看出错。
  缓解办法就是 §9 的保守：拿不准的时候，什么都不派。
- **分布式复杂度。** 房间、签名、转发、临时中心、跨链验证，是五套在这里从没一起跑过的系统。每一套都小；
  它们的乘积不小。
- **时间。** 该串行的地方层与层就是串行的（L3 在 L1、L2 与 audit v2 之后），而里程碑有八个。
- **资源。** 每一层都在乘「同时能跑的东西」的数量：每节点的实例数、每 workgroup 的节点数、每区域的
  workgroup 数。决策 §18 的那些预算，是本纲领唯一的天花板。
