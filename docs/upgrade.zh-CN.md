# 升级流程

**状态** v1.0 规范（里程碑 [M1](roadmap-v1.0.zh-CN.md)）｜ **日期** 2026-09-28 ｜ **基线**
v0.9.9（`3365970`）｜ **读者** 发行集成者 —— 发布或操作一次升级的人。

这就是 [decisions §14](decisions.zh-CN.md) 点名、[api-compatibility.md §7](api-compatibility.zh-CN.md)
所指的成文流程。规则在那边、以及 [decisions §11](decisions.zh-CN.md) 里定下；本文件是**操作顺序**，
让一次升级是一张核对表，而不是一次阅读理解。

## 1. 一次升级改了什么

**[已定]** 一次升级只改两样东西，且仅此两样：**安装**（原地覆盖）与**持久化数据**（新构建第一次打开
它时迁移）。它从不要求操作者重装、搬走数据目录，或手工跑一次迁移。

- **就地。** 安装包覆盖安装；不重装，数据目录不搬家（[decisions §14](decisions.zh-CN.md)）。
- **迁移是自动的。** 每个格式在打开时迁移一次（[decisions §11](decisions.zh-CN.md)、
  [api-compatibility.md §6](api-compatibility.zh-CN.md)）。没有需要记住的独立迁移步骤 —— 这正是重点：
  一次需要人记住的升级，就是一次会被跳过的升级。

## 2. 哪些东西带版本标记，标记住在哪

**这张表就是全部名单。** 不在这张表里的持久化格式，没有本流程能据以行动的标记 —— 而新加一个格式，
就在创建它的同一批里给它加一行（[api-compatibility.md §6](api-compatibility.zh-CN.md)）。

| 格式 | 位置 | 今天的标记 | 早于该标记的文件 |
|---|---|---|---|
| `settings.json` | `<data-dir>/settings.json` | `version` = `SETTINGS_VERSION`（自 v1.0 M2b-1 起为 **2**） | 读作 `1`，**打开时**迁移为 `2` |
| run 指纹 | 每条 run 记录之内 | `riscdom.run.fingerprint.v1` | v2 指纹是一个新的标记**值**，绝不是改写 v1 记录 |
| 审计库 | `<data-dir>/audit.db`（SQLite） | `PRAGMA user_version` = **1**（v1.0 M2b-3a） | 读作 `0`，**打开时**迁移，然后盖号 |
| 会话库 | `<data-dir>/sessions.db`（SQLite） | `PRAGMA user_version` = **1**（v1.0 M2b-2） | 读作 `0`，**打开时**迁移，然后盖号 |
| 凭据文件 | `<data-dir>/token` | 无（一行只做形状检查的 hex） | 手工放置的 token **永不被改写** |
| 节点身份 | `<data-dir>/node.key`，或 OS keyring | `schema_version` = **1**（v1.0 M4a） | v1.0 M4a 新增；**更新**的文件被拒 |
| 同侪表 | `<data-dir>/peers.json` | `schema_version` = **1**（v1.0 M4a） | v1.0 M4a 新增；**更新**的文件被拒，更旧的**打开时**迁移 |
| 房间表 | `<data-dir>/rooms.json` | `schema_version` = **1**（v1.0 M4c） | v1.0 M4c 新增；**更新**的文件被拒，更旧的**打开时**迁移 |

这张表的两个性质决定了下面的流程：

- **`.bak` 有格式有、有格式没有。** `settings.json` 与 `sessions.db` 会把迁移前的字节另存一份
  （`settings.json.bak`、`sessions.db.bak`）。审计库刻意**不**这么做：它是 WAL 且可能被多个进程打开，
  只拷 `audit.db` 会漏掉还在 `-wal` 里的帧。这就是 §3 第 3 步拷**整个目录**的原因。
- **标记不是对其他节点的承诺。** 不同版本的两个节点只共用协议允许共用的部分；较旧的那个拒绝较新的
  文件，而不是去猜。

## 3. 流程

**[已定]** 六步，按此顺序。第 1–3 步是操作者的；4–6 步是新构建第一次打开每个文件时要做的事。

1. **读这一步的发行说明。** 跨大版本必须逐步（§5），而该步的迁移工具随那一步的发行说明提供。
2. **停掉节点。** 迁移发生在打开时，所以它不能与正在运行的进程抢。
3. **把数据目录整体另存一份。** 自动的 `.bak` 覆盖 `settings.json` 与 `sessions.db`；审计库刻意不做
   字节拷贝（§2），所以保护它的是目录拷贝。迁移**不可逆** —— 这份拷贝就是回头路。
4. **就地装上新构建。** 安装包覆盖安装；数据目录不搬家。
5. **启动一次，让它迁移。** 每个文件第一次被打开时迁移，然后盖上当前标记。不需要动的文件不会被
   回写任何东西。
6. **核对。** `GET /v0/audit/status` 会答链是否仍然验证通过、以及它有多少行；`GET /v0/status` 会答
   节点自己起来了。一次返回「链验证不通过」的升级就是失败的升级，而第 3 步的拷贝就是回退点。

## 4. 文件被拒绝时

**[已定]** 两种拒绝，都响亮，都把文件原样留下。

- **旧构建遇上更新的文件**：拒绝并报 `data_too_new` —— 它不读、也不写。什么也不应用，也绝不静默降级
  （[decisions §11](decisions.zh-CN.md)）。
- **迁移不了的文件**：让构建继续运行、文件原样不动；迁移前的字节仍在 `.bak` 里（或在 §3 第 3 步的
  拷贝里）。

没有「迁移了一半」需要收拾：一个文件要么处在构建要写的那个标记上，要么停在它原来的标记上，备份就在
旁边。

## 5. 跨大版本

**[已定]** 大版本**不可**跳过。`1.x → 3.x` 必须走 `2.x`。

- 每一步带上它需要的迁移，该步的迁移工具随那一步的发行说明提供
  （[api-compatibility.md §7](api-compatibility.zh-CN.md)）。
- 「逐步」这条针对的是**数据**：每个大版本的迁移都假定上一个大版本的结果已经在了。
- 从 `1.x` 直接升 `3.x` 会被**拒绝**，而不是被尝试
  （[api-compatibility.md §8](api-compatibility.zh-CN.md)）。

`0.x → 1.0` 不承诺无痛 —— `v0.x` 什么都不承诺 —— 但 1.0 的迁移是写出来的，且先留一份 `.bak`
（[api-compatibility.md §8](api-compatibility.zh-CN.md)）。

## 6. 集成者不许做的事

- **发布与本文不一致的安装包。** 一套自带升级规矩的包就是一个 bug：macOS / Linux 的包与 Windows
  安装包遵循本文，而不是各自的规矩（[api-compatibility.md §8](api-compatibility.zh-CN.md)）。
- **跳大版本**，或让用户以为可以跳。
- **把「手工跑迁移」当成常规路径。** 一次操作者必须记住的迁移，就是一次不会发生的迁移
  （[decisions §11](decisions.zh-CN.md)）。

## 7. 本文不覆盖什么

- **各个 schema 本身。** 每个格式装什么、每个版本标记是什么意思，在
  [api-compatibility.md §5 与 §6](api-compatibility.zh-CN.md) 以及 [decisions §11](decisions.zh-CN.md)。
- **回滚。** 迁移不可逆；要回头就是把 §3 的拷贝恢复回去。
- **关于另一个节点的任何事。** 标记说的是**这份**安装写了什么；它对同侪什么都不承诺。
