# 技术决策账本

> **适用于 v0.x 整条线；每条自带日期与状态。** 这些决策是在对话里定下的，现在落盘于此，好让新协作者（人或 AI）不必重新发现一遍，也让 v1.0 有东西可以「重新讨论」，而不是得从头重建。

**append-only。** 新决策加在末尾。已有条目的正文永不修改；只有状态可变（机制已定者后来获得实现版本，或决策被推翻）。被推翻的决策以**追加**一条新条目的方式记录，并在其中点名旧条目——不改写历史。

**状态词表。** 已定 / 待定 / 已推翻。日期为本地时间（Asia/Shanghai）。

**读者。** 内核开发者与发行版集成者：每条都写明它造成的约束、以及留给后续的缝。

## 1. 内核定位

**日期**：2026-09-20 ｜ **状态**：已定

**决策**：内核只提供机制，不提供策略。

**理由**：通用沙箱、内建 AI 监工、官方运营服务，三者都是策略。把它们任何一个烙进内核，就等于替调用方把选择定死了。

**影响**：机制在内核，策略在调用方。不做通用沙箱方向的功课、不内建监工、不官方运营服务。

## 2. RISC-V 定位

**日期**：2026-09-22 ｜ **状态**：已定

**决策**：RiscDom 是「以 RISC-V 为核心的可插拔安全沙箱运行时」。RISC-V 是主基调、底层、默认实现，但不是唯一。

**理由**：RISC-V 的核心地位来自「项目之根」，不来自排他。

**影响**：沙箱可作为插件扩展至其它架构；沙箱内容不受架构限制。内核代码不得假设 guest 一定是 RISC-V。

## 3. 沙箱插件

**日期**：2026-09-22 ｜ **状态**：已定（机制），v1.x 实现

**决策**：沙箱是插件，可插拔，且可多插件并行。

**理由**：架构与执行模型的差异几乎都集中在沙箱这一层；只做一个内建实现，等于把所有这些差异都塞回内核。

**影响**：进程外（stdio JSON lines，与 `worker` 同构）。机制层（启动 / 停止 / 执行 / 输出）必含；语义层（快照 / 指纹）可选，由插件声明自己具备哪些能力。开发者可在限度内写插件——插件能力受限，且复用 capability 模型。插件接口优先冻结，早于内核 API。v0.9 留缝，v1.x 实现。

## 4. 沙箱预置环境

**日期**：2026-09-22 ｜ **状态**：已定（机制），v1.x 实现

**决策**：沙箱可预置环境，用来解决「AI 每次都重造轮子」。四机制全提供，用哪个由策略定。

**理由**：有没有预置，就是「AI 头几分钟都在重装编译器」与「AI 直接开工」之间的差别。

**影响**：四机制为——① 持久目录：实例目录 + 共享目录，挂载什么由插件决定；② 清单来源：插件声明 + 内核扫描 + 开发者手写，三者合并；③ 装入路径：手动 shell + setup 脚本；④ AI 感知：system prompt 注入 + 工具查询。预置内容带哈希，启动时校验。v0.9 留缝。

## 5. 插件仓库

**日期**：2026-09-22 ｜ **状态**：已定，v1.x 建仓

**决策**：官方仓与社区仓共存，工具可配多源。主仓保留官方全量 index，指向外部。

**理由**：单一集中仓库会让项目成为每个插件的守门人；多源既让官方 index 保持权威，又不让「能不能发布」取决于一台服务器。

**影响**：插件包格式复用凭据规范——Ed25519 签名 + 元数据 + 内容。v0.9 只留缝。

## 6. 控制平面

**日期**：2026-09-22 ｜ **状态**：已定，v0.9 已落

**决策**：人管 AI 与 AI 管 AI 走同一套接口。

**理由**：建两条控制通道而不是一条，正是这套设计存在的意义所在要避免的错误；对内核而言，监工 AI 的指令与人的指令都是来自控制平面的、已被授权的指令。

**影响**：HTTP（命令 / 查询）+ SSE（事件推送——零新依赖、单向、不用 WS）。设备无关语义：同一协议既承载本地 IPC，也承载联网连接。认证为 `Authorization: Bearer` 加 `Authn` 钩子；开源版只提供明文 HTTP 与钩子，TLS 归部署方——这条边界写在文档里，而不是靠默认。capability 判定发生在请求路径中、对着路由表作出，而路由表第三列本身就是 `Capability` 类型，因此「跳过检查的路由」写不出来。

## 7. 跨设备

**日期**：2026-09-22 ｜ **状态**：已定，v1.0 实现

**决策**：公网当作一张大内网（overlay）。三层拓扑：LAN 节点 > 核心桥机 < WAN 节点。

**理由**：NAT 与动态地址是障碍；一台两侧都主动外连的无状态桥机把它们消掉，同时不赋予桥机对任何一方数据的支配权。

**影响**：核心桥机无状态、可替换。日志全复制——群聊模型：每台设备持有全部日志并交叉验证。发现用 UDP 广播 + 房间隔离；任务派发用点对点 TCP + Ed25519 签名。`@` = 寻址 + 签名。速率、房间、成本计量、`@` 权限：机制在内核，策略在调用方。

## 8. CLI

**日期**：2026-09-22 ｜ **状态**：已定，v0.9 早期

**决策**：做 CLI——单一 `riscdom` 命令 + 子命令，混合架构：本地内嵌，或 `--remote host:port` 连 daemon。

**理由**：在 shell 里驱动这套工具的 AI 是一等用户，而 shell 是每个环境都有的那一个接口。

**影响**：AI 友好是硬要求：`--json` 输出、退出码语义明确、幂等、流式 stdin/stdout。CLI 是控制平面客户端：不直接碰内核状态。

## 9. 管理程序

**日期**：2026-09-22 ｜ **状态**：已定，v0.9 实现

**决策**：形态混合——Web 端（手机浏览器优先）+ 桌面沿用 Tauri。

**理由**：管 AI 的人常常不在跑 AI 的那台机器旁，而只有 Tauri 的桌面构建在手机浏览器里够不着。

**影响**：v0.9 不独立建仓（先放主仓）；v1.0 独立。管理程序是控制平面客户端。面向固定地址（局域网，或固定公网 IP）；动态 IP 场景不在本项目范围内。

## 10. API 稳定性策略

**日期**：2026-09-22 ｜ **状态**：已定，v1.0 冻结

**决策**：冻两层——`host` 公共 API 与控制平面 HTTP 协议。

**理由**：这两面正是集成者所要依赖的；冻别的，要么窄到没意义，要么宽到守不住。

**影响**：允许加可选字段、加新 endpoint；不允许改已有字段语义、删字段、改 URL 语义。弃用：旧 endpoint 至少留一个大版本。semver：0.x 不承诺稳定；1.0 之后承诺严格。

## 11. 数据迁移与 schema 演进

**日期**：2026-09-22 ｜ **状态**：已定

**决策**：每个持久化格式首字段带 `schema_version`。

**理由**：数据里没有版本，就只能靠「知道是哪个构建写的」才知道该怎么读。

**影响**：打开即迁移，从不要求用户跑工具。新版本必须能读旧数据；旧版本读新数据拒绝并报错——绝不静默降级。迁移前自动备份 `.bak`。迁移不可逆。

## 12. 错误模型

**日期**：2026-09-22 ｜ **状态**：已定，v1.0 前扩展

**决策**：一个分类枚举：`Network { timeout | unreachable }`、`Refused { reason }`、`Crashed { exit_status }`、`Partial { completed, failed }`、`Invalid { reason }`。

**理由**：这些类别正对应调用方能作出不同反应的那些情形——重试、拒绝、报崩溃、续做半成品、驳回非法输入。

**影响**：每变体带 `Retryable` 标记 + `Cause` 链，且序列化友好（跨进程、跨设备）。

## 13. 凭据 / 密钥管理

**日期**：2026-09-22 ｜ **状态**：已定

**决策**：算法 Ed25519；用标准格式（PEM 或 JWK），不自造。

**理由**：标准算法加标准编码，是唯一能让别的实现验证本实现签名的组合。

**影响**：私钥默认存文件（权限 600），系统 keyring 可选。轮换：多密钥并行——灰度期内新旧同时有效。撤销：撤销列表随房间广播，失陷节点全网踢。批量导入规范：`{node_id, addresses[], public_key, capabilities, rooms[]}`，JSON。

## 14. 升级与迁移路径

**日期**：2026-09-22 ｜ **状态**：已定

**决策**：就地升级——安装包覆盖安装，不重装。数据迁移自动。

**理由**：要求用户重装或手工跑迁移的升级，就是一种会被跳过的升级。

**影响**：跨大版本必须逐级，不能跳级，并为该级提供迁移工具。文档 `docs/upgrade.md`。

## 15. 安全披露政策

**日期**：2026-09-22 ｜ **状态**：已定

**决策**：`SECURITY.md` + GitHub 私密漏洞报告。

**理由**：写明唯一渠道，是让报告私下抵达、而不是变成公开 issue 的前提。

**影响**：时限：48 小时确认、7 天评估、90 天披露（与报告者协调）。CVE 由维护者申请。不设漏洞奖金——项目非盈利，文档明写。

## 16. 配置 schema

**日期**：2026-09-22 ｜ **状态**：已定，v0.9 期间

**决策**：用 JSON Schema 定义，落 `docs/config-schema.md`。

**理由**：一份机器可读的 schema，是让校验器、编辑器与自动生成的参考文档同源的前提。

**影响**：覆盖节点配置、房间、速率上限、权限规则。

## 17. 可观测性契约

**日期**：2026-09-22 ｜ **状态**：已定，v0.9 期间

**决策**：结构化日志（JSON lines）+ 指标接口（`/metrics`，Prometheus 格式）+ 追踪 ID（`agent_id` 与 `task_id` 串起来）。

**理由**：审计链本就每个事件带一个身份；拿它当追踪 ID，意味着一个工作单元只有一个标识，而不是多出一套要对齐的命名空间。

**影响**：日志与指标按契约、而非按惯例保持机器可读。

## 18. 性能预算

**日期**：2026-09-22 ｜ **状态**：已定

**决策**：VM 启动 ≤ 2s；派发往返 ≤ 100ms（同机）、≤ 500ms（跨网）；单节点 10 个 agent 内存 ≤ 2GB；日志增长可预测。

**理由**：这些正是「产品不再像本地工具」的那个数量级。

**影响**：它们是预算而非实测值：任何改动若破了其中一项，就是要作出解释的回归。

## 19. 备份 / 可移植性

**日期**：2026-09-22 ｜ **状态**：已定

**决策**：`riscdom-backup` CLI——把审计库 + 快照 + 凭据导出为一个可迁移包。

**理由**：能走，才是敢留的前提。

**影响**：该包就是可移植性的单位；恢复一个节点的历史与身份不需要包外的任何东西。

## 20. 贡献者工作流

**理由**：写下来的贡献流程，是「可以直接合入的补丁」与「得先谈一轮的补丁」之间的差别。

## 24. 遥测与法律立场

**日期**：2026-09-22 ｜ **状态**：已定

**决策**：遥测：不收集。

**理由**：沙箱运行时看得见源码与命令行；遥测通道会是项目自身承诺最容易被无意打破的那一处。

**影响**：法律：Apache 2.0 + 免责声明 + 使用条款边界。发布节奏：minor 3–6 个月，patch 按需。

## 25. SSE 与 WebSocket

**日期**：2026-09-22 ｜ **状态**：已定

**决策**：控制平面的事件推送用 SSE。

**理由**：SSE 零新依赖、单向（事件推送本就是单向），且每个浏览器都有原生客户端（`EventSource`）。

**影响**：WebSocket 留到 v1.0，且仅在跨设备工作确实需要双向流时才启用。

## 26. 事件 envelope

**日期**：2026-09-22 ｜ **状态**：已定，v0.9 已落

**决策**：所有事件、在所有传输上，统一一个 envelope：`{version, kind, event, agent_id, task_id, ts, payload}`，`kind` 取 `event` / `hello` / `gap`。

**理由**：多个传输承载的是同一批事件；统一 envelope，才让照着其中一个写出的客户端也适用于其余几个。

**影响**：版本规则——加 payload 字段、加事件名、加 `kind` 取值都不升 `version`；改字段含义或类型、或删字段才升。顶层字段冻结。事件身份取自**事件源**，不取自承载它的 sink。

## 27. 宿主拆分：host-core + host-tauri

**日期**：2026-09-23 ｜ **状态**：已定，v0.9 已落（A1，四波）

**决策**：宿主分成两个 crate——`host-core`（内核门面：审计接线、`AppState`、快照、会话、两条下载路径、预检、事件 envelope）与 `host-tauri`（53 个 Tauri 命令与 `TauriEventSink` 传输），由 `host-tauri` 再导出 `host-core`。

**理由**：`tauri` 此前被无条件链接，于是 `worker` 与 `server`——两个从不接触 webview 的无头进程——把一整套 GUI 工具链拖进了每次构建。拆 crate 才能把「链接 Tauri」从宿主的固有属性变成进程自己的选择。

**影响**：边界就是「是否需要 webview」这一问，且依赖只朝一个方向：`host-tauri → host-core → {agent, sandbox, audit}`。`worker` 与 `server` 依赖 `host-core` 且不含任何 Tauri crate（`cargo tree -p worker` / `-p server` 可验）；桌面壳只依赖 `host-tauri`，因为后者再导出了可移植面（`pub use host_core::*`）。39 个集成测试住在 `host-core/tests`；镜像常量守卫与 clippy 步骤覆盖两个 crate。工作分四波完成——core + 门面、测试 + 守卫、worker/server、更名 + 外壳——每波自身可绿，没有「暂时红」的中间态。crate 名本身即文档：`host-core` 说「无 webview」，`host-tauri` 说「只有 webview」。

## 28. CLI：落点、模式与退出码

**日期**：2026-09-23 ｜ **状态**：已定；骨架与只读子命令已随 v0.9 落地

**决策**：CLI 是新 crate `cli`，二进制 `riscdom`。它是**控制平面的客户端**：每条命令都经 HTTP，本地模式在 CLI 进程内、`127.0.0.1:0` 上把控制平面起起来。退出码：`0` 成功、`1` 本地失败、`2` 用法或 `400`、`3` 被拒或 `5xx`、`4` `401`/`403`。

**理由**：放进 `server` 会让同一个 crate 既是被服务的进程又是它的客户端；放进 `host-tauri` 会把 Tauri 链进一个无头工具。既然本地调用与远程调用必须表现一致，本地模式绕过 HTTP 直接摸 `AppState` 就毫无收益——代价却很大：那样只有远程路径会被真正走到。

**影响**：CLI 依赖 `server`（内嵌模式）、`host-core`、`reqwest`、`serde_json`——全部已在锁文件内；没有新增参数解析 crate，CLI 像 `riscdom-server`、`worker` 与两个 `audit` 二进制一样手写解析。`--json` 原样透传控制平面的 JSON；token 从不被打印或记录。门禁的 clippy 步骤以 `--no-deps` 覆盖 `-p cli`，于是新 crate 被 lint，同时不会把 `server` 自身（既有）的问题拖进门禁。控制类子命令与 `--follow` 属下一批。

## 29. 控制平面的参数错误装箱

**日期**：2026-09-23 ｜ **状态**：已定；随 v0.9 CLI 批次 3/N 落地

**决策**：`Params` 的五个读取器（`required`、`usize_required`、`usize_or`、`bool_required`、`bool_or`）与 `read_json_body` 返回 `Result<_, Box<Response<RespBody>>>`，而不是 `Result<_, Response<RespBody>>`。

**理由**：`400` 的应答方式是直接把一个现成的 response 交给调用方——正是这个形状让处理器保持可读；但 hyper 的 `Response` 有 128+ 字节，于是每个携带它的 `Result` 在体积上主要由错误构成（`clippy::result_large_err`）。装箱把大值放到真正产生它的那条路径背后的指针里，代价只是构造错误时的一次分配——成功路径上零成本。

**影响**：调用方写 `return *response`，因此同一条路径上传的仍是同一个值：行为不变，只换了地址。这些方法挂在一个 `pub(crate)` 类型上，所以 crate 之外看不到该签名。`server` 现在也在门禁的 clippy 步骤里——正是它最初让这六处浮出水面。

## 30. 两套装配共用一个形状

**日期**：2026-09-23 ｜ **状态**：已定；随 v0.9 沙箱批次 F1 落地

**决策**：「装配一个资源」只有一个形状，工具链与 QEMU 都用它：*spec*（`version`、`url`、`sha256`、`archive_kind`、`install_subdir`）→ 分块*下载*（带取消标志）→ *sha256 校验* → *Zip-Slip 守卫的解压* → *采用*（校验结果并写进 `settings.json`）→ *审计事件*（`host.<resource>.download.start|done|failed|cancelled`）→ *SSE 事件族*（`<resource>:download`，内部标签枚举、标签为 `state`）→ `AppState` 里每资源一个*槽*（`begin` / `status` / `cancel` / `finish`）。

**理由**：两种资源是同一个问题的两个实例——一个被 pin、受完整性校验的二进制，需要被抓取、验证、安装并设为当前——而客户端应当对两者读同一套词汇。共用形状也是让「沙箱 = 内核 + 工具链 + QEMU」（F2）变成「给资源起名」而不是「为每种资源新造一套机制」的前提。

**影响**：QEMU 下载的 payload 标签从 `kind` 改为 `state`，CLI 的 `--wait` 终止判定变成两族共用的一个函数，因此已按一族写好的客户端已经能读另一族。**形状是共用的，但并未抽象**：没有通用的 `Resource` trait 或 spec 类型，F1 刻意不加——两个模块仍是各自独立的文件与类型，这份重复是「在 F2 说出抽象是什么之前不猜」的、已被记录在案的代价。工具链的语义未变。`spec_for_current_platform` 仍是 QEMU 的平台分支，且今天在每个平台都拒绝（`docs/qemu-distribution.md` §5）：共用形状意味着将来 pin 一个发布版只是改一张表的数据变更。

## 31. 沙箱注册表：存储的定义、扫描出的列表、一个合并视图

**日期**：2026-09-23 ｜ **状态**：已定；随 v0.9 沙箱批次 F2a-1 落地

**决策**：一个沙箱有一个*定义*，而定义是**存储的数据，不是运行时**：`{ name, display_name?, memory_mb?, qemu_exe?, toolchain_path?, kernel?, notes? }`，手写在 `settings.json` 里。宿主*服务*的是它加上只有宿主当场能回答的三项——`source`（`manual` / `discovered`）、`runnable`、`shadowed`——且 **`runnable` 与 `shadowed` 从不存储**。注册表每次读取时按固定顺序由三个来源拼成——手写定义、扫描所得、一个名为 `default` 的内置兜底——同名冲突时手写者胜，而**被遮的那项留在列表里并标出**。

**理由**：客户端问沙箱的三个问题——这里装了什么、写下的是什么、现在能跑什么——有三个不同的生命周期。已安装资源会在没人改文件的情况下变化；`runnable` 会在 QEMU 被卸载时变化，把它存下来会让定义在机器一变就成了谎话；而合并如果藏起输家，被遮的扫描项就会隐形成形，而那正是人需要看见的情况——他手写的定义并不是正在被用的那个。不把扫描写回也是同一个理由：那会把「机器的缓存」变成「本该由人拥有的设置」，并让同一进程里的两个宿主互相覆盖对方的视图。

**影响**：`LocalSettings` 新增 `sandboxes` 与 `default_sandbox`，两者都是附加的（`#[serde(default)]`），因此不做迁移、`SETTINGS_VERSION` 仍为 1。扫描限于宿主自己的数据目录（`<data-dir>/toolchain/*`、`<data-dir>/qemu/*`）加上本机 QEMU，复用下载器的 `find_compiler` / `find_qemu`（现为 `pub(crate)`），不另长第二份「已安装」。`sandbox.read` 是第 29 个 capability；端点、Tauri 命令与 CLI 属 F2a-2，切换属 F2b，审批属 F2c，`Task.sandbox` 属 F2d。**定义刻意不是运行时配置**：它只给资源起名，一次运行拿它们做什么仍由 F2b 决定。

## 32. QEMU 装配规格故意为空（供应链安全）

**日期**：2026-09-23 ｜ **状态**：已定；随 v0.9 沙箱批次 F1 落地时记录

**决策**：`spec_for_current_platform()` 在**每一个**平台都拒绝：RiscDom 不 pin 任何 QEMU 发布版，不提供 URL，也不提供摘要，更不会去抓取模拟器。`POST /v0/qemu/download` 答 `503 unavailable`、`cause: "qemu"` 并附安装指引，且不占下载槽。工具链的装配不受影响：它的发布版是 pin 过的、带摘要、会被抓取。

**理由**：上游 QEMU 不发布 Windows 二进制，因此 RiscDom 能选的任何 URL 要么是第三方的重新打包，要么是一个我们无法验证的发布版。为一个我们自己没抓过的二进制编一个摘要是把完整性漏洞装裱起来——而这正是 pin 工具链要避开的那种失效模式。引导用户去装他们自己装的模拟器，把信任边界留在真正能被检查的地方。

**影响**：拒绝之后的 QEMU 下载路径是完整的（槽、状态、取消、采用、审计事件、`qemu:download` 事件族、Tauri 命令、端点与 CLI），因此**将来 pin 一个发布版只是数据变更**：答案变成 `202`，其余不动。有一处不对称保留未修（已报告）：规格为空正是 `qemu.read` / `qemu.configure` 端点能不发网络请求就报告「不可用」的原因，也正是它们能用回环夹具离线测试的原因。

## 33. 中心化连接与临时中心

**日期**：2026-09-23 ｜ **状态**：已定；v1.0（跨设备）实现

**决策**：中心是一个**角色**不同的 RiscDom 节点——同一内核，按部署分化。规则：合法性按预定优先级；优先级由中心在注册时分发、每个节点各持副本；节点间认知不一致时取多数决；触发条件是**所有**节点都联系不上中心（全局确认，不是某一点）；事件归并时把临时中心的链接入主链；权限上由 AI 自动发起、事后审计；终止即回归中心；桥机在内网内独立，临时可代中心；内核接口是「节点接口 + 可选的中心能力」，由部署者决定。

**抑制机制（三层全要）**：一等，等待期（30s–2min 静默重试）；二等，全局确认（多数节点都报「连不上」才会触发）；三等，退避 + 顺位（第一顺位随机退避，一收到接管广播就退让）。

**审计并入（方案 A）**：临时中心期间写下的事件带 `provisional: true`；真中心回来后，无冲突则并入并清掉标记，有冲突则**双方都**保留、标为 `fork`——绝不静默合并。链语义扩展为「主链 + 临时段」，其中段首的跨段引用是**加元数据、不改哈希公式**。

**影响**：一套代码，部署即分化（细胞分化模型）；商业版的多中心冗余不在此模型之内。

**待授权项**：v1.0 做跨设备设计时必须单独审批——把审计链语义扩展为「主链 + 临时段」会触及红线 5（`当有疑问，先问`，PROJECT_CONSTITUTION.md §8）的边界。

## 34. 节点在跑什么是运行时状态，它从什么开始是配置

**日期**：2026-09-23 ｜ **状态**：已定；随 v0.9 沙箱批次 F2b-1 落地

**决策**：两个名字，两种寿命。`default_sandbox` 住在 `settings.json` 里，是节点重启后的**起点**；`current_sandbox` 只活在内存里，是节点**现在跑着的**——由一次成功的切换写入，在它之前为 `None`。`AppState::sandbox_default_name()` 回答前者，`AppState::current_sandbox()` 回答后者，而切换只写后者。

**理由**：它们在不同时刻回答不同问题。为一次实验切到草稿沙箱的人，并没有要求把这件事变成这台机器的配置；而磁盘上被改过的配置，与「槽里那台 VM 来自这个定义」也不是同一个断言——槽可能是空的，VM 可能已停，机器可能已重启。把两者合成一个，会让每次切换都变成一次设置写入（也让每次设置编辑都变成关于「正在跑什么」的断言），而这正是 F2a 的注册表要避开的混淆。

**影响**：切换只改运行时字段；它让 `settings.json` 逐字节不变，F2b-1 的测试就是这么断言的。因此注册表里的 `current` 与 `default` 确实是两个不同的值，问「一次运行会用哪个」的客户端必须说清它指的是哪一个。把这一切暴露出去的端点、Tauri 命令、CLI 与 `sandbox:switch` 事件属 F2b-2；`Task.sandbox`（F2d）是第三个问题——单次*运行*要什么——它坐在这两者之上。
