# 技术决策账本

> **适用于 v0.x 整条线；每条自带日期与状态。** 这些决策是在对话里定下的，现在落盘于此，好让新协作者（人或 AI）不必重新发现一遍，也让 v1.0 有东西可以「重新讨论」，而不是得从头重建。

**append-only。** 新决策加在末尾。已有条目的正文永不修改；只有状态可变（机制已定者后来获得实现版本，或决策被推翻）。被推翻的决策以**追加**一条新条目的方式记录，并在其中点名旧条目——不改写历史。

**状态词表。** 已定 / 待定 / 已推翻。日期为本地时间（Asia/Shanghai）。

**读者。** 内核开发者与发行版集成者：每条都写明它造成的约束、以及留给后续的缝。

## 1. 内核定位

**日期**：2026-09-20 ｜ **状态**：已定

**决策**：内核只提供机制，不提供策略。

**理由**：通用沙箱、内建 AI 监工、官方运营服务，三者都是策略。把它们任何一个烙进内核，就等于替调用方把选择定死了。

**影响**：机制在内核，策略在调用方。不做通用沙箱方向的功课、不内建监工、不官方运营服务。

## 2. RISC-V 定位

**日期**：2026-09-22 ｜ **状态**：已定

**决策**：RiscDom 是「以 RISC-V 为核心的可插拔安全沙箱运行时」。RISC-V 是主基调、底层、默认实现，但不是唯一。

**理由**：RISC-V 的核心地位来自「项目之根」，不来自排他。

**影响**：沙箱可作为插件扩展至其它架构；沙箱内容不受架构限制。内核代码不得假设 guest 一定是 RISC-V。

## 3. 沙箱插件

**日期**：2026-09-22 ｜ **状态**：已定（机制），v1.x 实现

**决策**：沙箱是插件，可插拔，且可多插件并行。

**理由**：架构与执行模型的差异几乎都集中在沙箱这一层；只做一个内建实现，等于把所有这些差异都塞回内核。

**影响**：进程外（stdio JSON lines，与 `worker` 同构）。机制层（启动 / 停止 / 执行 / 输出）必含；语义层（快照 / 指纹）可选，由插件声明自己具备哪些能力。开发者可在限度内写插件——插件能力受限，且复用 capability 模型。插件接口优先冻结，早于内核 API。v0.9 留缝，v1.x 实现。

## 4. 沙箱预置环境

**日期**：2026-09-22 ｜ **状态**：已定（机制），v1.x 实现

**决策**：沙箱可预置环境，用来解决「AI 每次都重造轮子」。四机制全提供，用哪个由策略定。

**理由**：有没有预置，就是「AI 头几分钟都在重装编译器」与「AI 直接开工」之间的差别。

**影响**：四机制为——① 持久目录：实例目录 + 共享目录，挂载什么由插件决定；② 清单来源：插件声明 + 内核扫描 + 开发者手写，三者合并；③ 装入路径：手动 shell + setup 脚本；④ AI 感知：system prompt 注入 + 工具查询。预置内容带哈希，启动时校验。v0.9 留缝。

## 5. 插件仓库

**日期**：2026-09-22 ｜ **状态**：已定，v1.x 建仓

**决策**：官方仓与社区仓共存，工具可配多源。主仓保留官方全量 index，指向外部。

**理由**：单一集中仓库会让项目成为每个插件的守门人；多源既让官方 index 保持权威，又不让「能不能发布」取决于一台服务器。

**影响**：插件包格式复用凭据规范——Ed25519 签名 + 元数据 + 内容。v0.9 只留缝。

## 6. 控制平面

**日期**：2026-09-22 ｜ **状态**：已定，v0.9 已落

**决策**：人管 AI 与 AI 管 AI 走同一套接口。

**理由**：建两条控制通道而不是一条，正是这套设计存在的意义所在要避免的错误；对内核而言，监工 AI 的指令与人的指令都是来自控制平面的、已被授权的指令。

**影响**：HTTP（命令 / 查询）+ SSE（事件推送——零新依赖、单向、不用 WS）。设备无关语义：同一协议既承载本地 IPC，也承载联网连接。认证为 `Authorization: Bearer` 加 `Authn` 钩子；开源版只提供明文 HTTP 与钩子，TLS 归部署方——这条边界写在文档里，而不是靠默认。capability 判定发生在请求路径中、对着路由表作出，而路由表第三列本身就是 `Capability` 类型，因此「跳过检查的路由」写不出来。

## 7. 跨设备

**日期**：2026-09-22 ｜ **状态**：已定，v1.0 实现

**决策**：公网当作一张大内网（overlay）。三层拓扑：LAN 节点 > 核心桥机 < WAN 节点。

**理由**：NAT 与动态地址是障碍；一台两侧都主动外连的无状态桥机把它们消掉，同时不赋予桥机对任何一方数据的支配权。

**影响**：核心桥机无状态、可替换。日志全复制——群聊模型：每台设备持有全部日志并交叉验证。发现用 UDP 广播 + 房间隔离；任务派发用点对点 TCP + Ed25519 签名。`@` = 寻址 + 签名。速率、房间、成本计量、`@` 权限：机制在内核，策略在调用方。

## 8. CLI

**日期**：2026-09-22 ｜ **状态**：已定，v0.9 早期

**决策**：做 CLI——单一 `riscdom` 命令 + 子命令，混合架构：本地内嵌，或 `--remote host:port` 连 daemon。

**理由**：在 shell 里驱动这套工具的 AI 是一等用户，而 shell 是每个环境都有的那一个接口。

**影响**：AI 友好是硬要求：`--json` 输出、退出码语义明确、幂等、流式 stdin/stdout。CLI 是控制平面客户端：不直接碰内核状态。

## 9. 管理程序

**日期**：2026-09-22 ｜ **状态**：已定，v0.9 实现

**决策**：形态混合——Web 端（手机浏览器优先）+ 桌面沿用 Tauri。

**理由**：管 AI 的人常常不在跑 AI 的那台机器旁，而只有 Tauri 的桌面构建在手机浏览器里够不着。

**影响**：v0.9 不独立建仓（先放主仓）；v1.0 独立。管理程序是控制平面客户端。面向固定地址（局域网，或固定公网 IP）；动态 IP 场景不在本项目范围内。

## 10. API 稳定性策略

**日期**：2026-09-22 ｜ **状态**：已定，v1.0 冻结

**决策**：冻两层——`host` 公共 API 与控制平面 HTTP 协议。

**理由**：这两面正是集成者所要依赖的；冻别的，要么窄到没意义，要么宽到守不住。

**影响**：允许加可选字段、加新 endpoint；不允许改已有字段语义、删字段、改 URL 语义。弃用：旧 endpoint 至少留一个大版本。semver：0.x 不承诺稳定；1.0 之后承诺严格。

## 11. 数据迁移与 schema 演进

**日期**：2026-09-22 ｜ **状态**：已定

**决策**：每个持久化格式首字段带 `schema_version`。

**理由**：数据里没有版本，就只能靠「知道是哪个构建写的」才知道该怎么读。

**影响**：打开即迁移，从不要求用户跑工具。新版本必须能读旧数据；旧版本读新数据拒绝并报错——绝不静默降级。迁移前自动备份 `.bak`。迁移不可逆。

## 12. 错误模型

**日期**：2026-09-22 ｜ **状态**：已定，v1.0 前扩展

**决策**：一个分类枚举：`Network { timeout | unreachable }`、`Refused { reason }`、`Crashed { exit_status }`、`Partial { completed, failed }`、`Invalid { reason }`。

**理由**：这些类别正对应调用方能作出不同反应的那些情形——重试、拒绝、报崩溃、续做半成品、驳回非法输入。

**影响**：每变体带 `Retryable` 标记 + `Cause` 链，且序列化友好（跨进程、跨设备）。

## 13. 凭据 / 密钥管理

**日期**：2026-09-22 ｜ **状态**：已定

**决策**：算法 Ed25519；用标准格式（PEM 或 JWK），不自造。

**理由**：标准算法加标准编码，是唯一能让别的实现验证本实现签名的组合。

**影响**：私钥默认存文件（权限 600），系统 keyring 可选。轮换：多密钥并行——灰度期内新旧同时有效。撤销：撤销列表随房间广播，失陷节点全网踢。批量导入规范：`{node_id, addresses[], public_key, capabilities, rooms[]}`，JSON。

## 14. 升级与迁移路径

**日期**：2026-09-22 ｜ **状态**：已定

**决策**：就地升级——安装包覆盖安装，不重装。数据迁移自动。

**理由**：要求用户重装或手工跑迁移的升级，就是一种会被跳过的升级。

**影响**：跨大版本必须逐级，不能跳级，并为该级提供迁移工具。文档 `docs/upgrade.md`。

## 15. 安全披露政策

**日期**：2026-09-22 ｜ **状态**：已定

**决策**：`SECURITY.md` + GitHub 私密漏洞报告。

**理由**：写明唯一渠道，是让报告私下抵达、而不是变成公开 issue 的前提。

**影响**：时限：48 小时确认、7 天评估、90 天披露（与报告者协调）。CVE 由维护者申请。不设漏洞奖金——项目非盈利，文档明写。

## 16. 配置 schema

**日期**：2026-09-22 ｜ **状态**：已定，v0.9 期间

**决策**：用 JSON Schema 定义，落 `docs/config-schema.md`。

**理由**：一份机器可读的 schema，是让校验器、编辑器与自动生成的参考文档同源的前提。

**影响**：覆盖节点配置、房间、速率上限、权限规则。

## 17. 可观测性契约

**日期**：2026-09-22 ｜ **状态**：已定，v0.9 期间

**决策**：结构化日志（JSON lines）+ 指标接口（`/metrics`，Prometheus 格式）+ 追踪 ID（`agent_id` 与 `task_id` 串起来）。

**理由**：审计链本就每个事件带一个身份；拿它当追踪 ID，意味着一个工作单元只有一个标识，而不是多出一套要对齐的命名空间。

**影响**：日志与指标按契约、而非按惯例保持机器可读。

## 18. 性能预算

**日期**：2026-09-22 ｜ **状态**：已定

**决策**：VM 启动 ≤ 2s；派发往返 ≤ 100ms（同机）、≤ 500ms（跨网）；单节点 10 个 agent 内存 ≤ 2GB；日志增长可预测。

**理由**：这些正是「产品不再像本地工具」的那个数量级。

**影响**：它们是预算而非实测值：任何改动若破了其中一项，就是要作出解释的回归。

## 19. 备份 / 可移植性

**日期**：2026-09-22 ｜ **状态**：已定

**决策**：`riscdom-backup` CLI——把审计库 + 快照 + 凭据导出为一个可迁移包。

**理由**：能走，才是敢留的前提。

**影响**：该包就是可移植性的单位；恢复一个节点的历史与身份不需要包外的任何东西。

## 24. 遥测与法律立场

**日期**：2026-09-22 ｜ **状态**：已定

**决策**：遥测：不收集。

**理由**：沙箱运行时看得见源码与命令行；遥测通道会是项目自身承诺最容易被无意打破的那一处。

## 25. SSE 与 WebSocket

**日期**：2026-09-22 ｜ **状态**：已定

**决策**：控制平面的事件推送用 SSE。

**理由**：SSE 零新依赖、单向（事件推送本就是单向），且每个浏览器都有原生客户端（`EventSource`）。

**影响**：WebSocket 留到 v1.0，且仅在跨设备工作确实需要双向流时才启用。

## 26. 事件 envelope

**日期**：2026-09-22 ｜ **状态**：已定，v0.9 已落

**决策**：所有事件、在所有传输上，统一一个 envelope：`{version, kind, event, agent_id, task_id, ts, payload}`，`kind` 取 `event` / `hello` / `gap`。

**理由**：多个传输承载的是同一批事件；统一 envelope，才让照着其中一个写出的客户端也适用于其余几个。

**影响**：版本规则——加 payload 字段、加事件名、加 `kind` 取值都不升 `version`；改字段含义或类型、或删字段才升。顶层字段冻结。事件身份取自**事件源**，不取自承载它的 sink。

## 27. 宿主拆分：host-core + host-tauri

**日期**：2026-09-23 ｜ **状态**：已定，v0.9 已落（A1，四波）

**决策**：宿主分成两个 crate——`host-core`（内核门面：审计接线、`AppState`、快照、会话、两条下载路径、预检、事件 envelope）与 `host-tauri`（53 个 Tauri 命令与 `TauriEventSink` 传输），由 `host-tauri` 再导出 `host-core`。

**理由**：`tauri` 此前被无条件链接，于是 `worker` 与 `server`——两个从不接触 webview 的无头进程——把一整套 GUI 工具链拖进了每次构建。拆 crate 才能把「链接 Tauri」从宿主的固有属性变成进程自己的选择。

**影响**：边界就是「是否需要 webview」这一问，且依赖只朝一个方向：`host-tauri → host-core → {agent, sandbox, audit}`。`worker` 与 `server` 依赖 `host-core` 且不含任何 Tauri crate（`cargo tree -p worker` / `-p server` 可验）；桌面壳只依赖 `host-tauri`，因为后者再导出了可移植面（`pub use host_core::*`）。39 个集成测试住在 `host-core/tests`；镜像常量守卫与 clippy 步骤覆盖两个 crate。工作分四波完成——core + 门面、测试 + 守卫、worker/server、更名 + 外壳——每波自身可绿，没有「暂时红」的中间态。crate 名本身即文档：`host-core` 说「无 webview」，`host-tauri` 说「只有 webview」。

## 28. CLI：落点、模式与退出码

**日期**：2026-09-23 ｜ **状态**：已定；骨架与只读子命令已随 v0.9 落地

**决策**：CLI 是新 crate `cli`，二进制 `riscdom`。它是**控制平面的客户端**：每条命令都经 HTTP，本地模式在 CLI 进程内、`127.0.0.1:0` 上把控制平面起起来。退出码：`0` 成功、`1` 本地失败、`2` 用法或 `400`、`3` 被拒或 `5xx`、`4` `401`/`403`。

**理由**：放进 `server` 会让同一个 crate 既是被服务的进程又是它的客户端；放进 `host-tauri` 会把 Tauri 链进一个无头工具。既然本地调用与远程调用必须表现一致，本地模式绕过 HTTP 直接摸 `AppState` 就毫无收益——代价却很大：那样只有远程路径会被真正走到。

**影响**：CLI 依赖 `server`（内嵌模式）、`host-core`、`reqwest`、`serde_json`——全部已在锁文件内；没有新增参数解析 crate，CLI 像 `riscdom-server`、`worker` 与两个 `audit` 二进制一样手写解析。`--json` 原样透传控制平面的 JSON；token 从不被打印或记录。门禁的 clippy 步骤以 `--no-deps` 覆盖 `-p cli`，于是新 crate 被 lint，同时不会把 `server` 自身（既有）的问题拖进门禁。控制类子命令与 `--follow` 属下一批。

## 29. 控制平面的参数错误装箱

**日期**：2026-09-23 ｜ **状态**：已定；随 v0.9 CLI 批次 3/N 落地

**决策**：`Params` 的五个读取器（`required`、`usize_required`、`usize_or`、`bool_required`、`bool_or`）与 `read_json_body` 返回 `Result<_, Box<Response<RespBody>>>`，而不是 `Result<_, Response<RespBody>>`。

**理由**：`400` 的应答方式是直接把一个现成的 response 交给调用方——正是这个形状让处理器保持可读；但 hyper 的 `Response` 有 128+ 字节，于是每个携带它的 `Result` 在体积上主要由错误构成（`clippy::result_large_err`）。装箱把大值放到真正产生它的那条路径背后的指针里，代价只是构造错误时的一次分配——成功路径上零成本。

**影响**：调用方写 `return *response`，因此同一条路径上传的仍是同一个值：行为不变，只换了地址。这些方法挂在一个 `pub(crate)` 类型上，所以 crate 之外看不到该签名。`server` 现在也在门禁的 clippy 步骤里——正是它最初让这六处浮出水面。

## 30. 两套装配共用一个形状

**日期**：2026-09-23 ｜ **状态**：已定；随 v0.9 沙箱批次 F1 落地

**决策**：「装配一个资源」只有一个形状，工具链与 QEMU 都用它：*spec*（`version`、`url`、`sha256`、`archive_kind`、`install_subdir`）→ 分块*下载*（带取消标志）→ *sha256 校验* → *Zip-Slip 守卫的解压* → *采用*（校验结果并写进 `settings.json`）→ *审计事件*（`host.<resource>.download.start|done|failed|cancelled`）→ *SSE 事件族*（`<resource>:download`，内部标签枚举、标签为 `state`）→ `AppState` 里每资源一个*槽*（`begin` / `status` / `cancel` / `finish`）。

**理由**：两种资源是同一个问题的两个实例——一个被 pin、受完整性校验的二进制，需要被抓取、验证、安装并设为当前——而客户端应当对两者读同一套词汇。共用形状也是让「沙箱 = 内核 + 工具链 + QEMU」（F2）变成「给资源起名」而不是「为每种资源新造一套机制」的前提。

**影响**：QEMU 下载的 payload 标签从 `kind` 改为 `state`，CLI 的 `--wait` 终止判定变成两族共用的一个函数，因此已按一族写好的客户端已经能读另一族。**形状是共用的，但并未抽象**：没有通用的 `Resource` trait 或 spec 类型，F1 刻意不加——两个模块仍是各自独立的文件与类型，这份重复是「在 F2 说出抽象是什么之前不猜」的、已被记录在案的代价。工具链的语义未变。`spec_for_current_platform` 仍是 QEMU 的平台分支，且今天在每个平台都拒绝（`docs/qemu-distribution.md` §5）：共用形状意味着将来 pin 一个发布版只是改一张表的数据变更。

## 31. 沙箱注册表：存储的定义、扫描出的列表、一个合并视图

**日期**：2026-09-23 ｜ **状态**：已定；随 v0.9 沙箱批次 F2a-1 落地

**决策**：一个沙箱有一个*定义*，而定义是**存储的数据，不是运行时**：`{ name, display_name?, memory_mb?, qemu_exe?, toolchain_path?, kernel?, notes? }`，手写在 `settings.json` 里。宿主*服务*的是它加上只有宿主当场能回答的三项——`source`（`manual` / `discovered`）、`runnable`、`shadowed`——且 **`runnable` 与 `shadowed` 从不存储**。注册表每次读取时按固定顺序由三个来源拼成——手写定义、扫描所得、一个名为 `default` 的内置兜底——同名冲突时手写者胜，而**被遮的那项留在列表里并标出**。

**理由**：客户端问沙箱的三个问题——这里装了什么、写下的是什么、现在能跑什么——有三个不同的生命周期。已安装资源会在没人改文件的情况下变化；`runnable` 会在 QEMU 被卸载时变化，把它存下来会让定义在机器一变就成了谎话；而合并如果藏起输家，被遮的扫描项就会隐形成形，而那正是人需要看见的情况——他手写的定义并不是正在被用的那个。不把扫描写回也是同一个理由：那会把「机器的缓存」变成「本该由人拥有的设置」，并让同一进程里的两个宿主互相覆盖对方的视图。

**影响**：`LocalSettings` 新增 `sandboxes` 与 `default_sandbox`，两者都是附加的（`#[serde(default)]`），因此不做迁移、`SETTINGS_VERSION` 仍为 1。扫描限于宿主自己的数据目录（`<data-dir>/toolchain/*`、`<data-dir>/qemu/*`）加上本机 QEMU，复用下载器的 `find_compiler` / `find_qemu`（现为 `pub(crate)`），不另长第二份「已安装」。`sandbox.read` 是第 29 个 capability；端点、Tauri 命令与 CLI 属 F2a-2，切换属 F2b，审批属 F2c，`Task.sandbox` 属 F2d。**定义刻意不是运行时配置**：它只给资源起名，一次运行拿它们做什么仍由 F2b 决定。

## 32. QEMU 装配规格故意为空（供应链安全）

**日期**：2026-09-23 ｜ **状态**：已定；随 v0.9 沙箱批次 F1 落地时记录

**决策**：`spec_for_current_platform()` 在**每一个**平台都拒绝：RiscDom 不 pin 任何 QEMU 发布版，不提供 URL，也不提供摘要，更不会去抓取模拟器。`POST /v0/qemu/download` 答 `503 unavailable`、`cause: "qemu"` 并附安装指引，且不占下载槽。工具链的装配不受影响：它的发布版是 pin 过的、带摘要、会被抓取。

**理由**：上游 QEMU 不发布 Windows 二进制，因此 RiscDom 能选的任何 URL 要么是第三方的重新打包，要么是一个我们无法验证的发布版。为一个我们自己没抓过的二进制编一个摘要是把完整性漏洞装裱起来——而这正是 pin 工具链要避开的那种失效模式。引导用户去装他们自己装的模拟器，把信任边界留在真正能被检查的地方。

**影响**：拒绝之后的 QEMU 下载路径是完整的（槽、状态、取消、采用、审计事件、`qemu:download` 事件族、Tauri 命令、端点与 CLI），因此**将来 pin 一个发布版只是数据变更**：答案变成 `202`，其余不动。有一处不对称保留未修（已报告）：规格为空正是 `qemu.read` / `qemu.configure` 端点能不发网络请求就报告「不可用」的原因，也正是它们能用回环夹具离线测试的原因。

## 33. 中心化连接与临时中心

**日期**：2026-09-23 ｜ **状态**：已定；v1.0（跨设备）实现

**决策**：中心是一个**角色**不同的 RiscDom 节点——同一内核，按部署分化。规则：合法性按预定优先级；优先级由中心在注册时分发、每个节点各持副本；节点间认知不一致时取多数决；触发条件是**所有**节点都联系不上中心（全局确认，不是某一点）；事件归并时把临时中心的链接入主链；权限上由 AI 自动发起、事后审计；终止即回归中心；桥机在内网内独立，临时可代中心；内核接口是「节点接口 + 可选的中心能力」，由部署者决定。

**抑制机制（三层全要）**：一等，等待期（30s–2min 静默重试）；二等，全局确认（多数节点都报「连不上」才会触发）；三等，退避 + 顺位（第一顺位随机退避，一收到接管广播就退让）。

**审计并入（方案 A）**：临时中心期间写下的事件带 `provisional: true`；真中心回来后，无冲突则并入并清掉标记，有冲突则**双方都**保留、标为 `fork`——绝不静默合并。链语义扩展为「主链 + 临时段」，其中段首的跨段引用是**加元数据、不改哈希公式**。

**影响**：一套代码，部署即分化（细胞分化模型）；商业版的多中心冗余不在此模型之内。

**待授权项**：v1.0 做跨设备设计时必须单独审批——把审计链语义扩展为「主链 + 临时段」会触及红线 5（`当有疑问，先问`，PROJECT_CONSTITUTION.md §8）的边界。

## 34. 节点在跑什么是运行时状态，它从什么开始是配置

**日期**：2026-09-23 ｜ **状态**：已定；随 v0.9 沙箱批次 F2b-1 落地

**决策**：两个名字，两种寿命。`default_sandbox` 住在 `settings.json` 里，是节点重启后的**起点**；`current_sandbox` 只活在内存里，是节点**现在跑着的**——由一次成功的切换写入，在它之前为 `None`。`AppState::sandbox_default_name()` 回答前者，`AppState::current_sandbox()` 回答后者，而切换只写后者。

**理由**：它们在不同时刻回答不同问题。为一次实验切到草稿沙箱的人，并没有要求把这件事变成这台机器的配置；而磁盘上被改过的配置，与「槽里那台 VM 来自这个定义」也不是同一个断言——槽可能是空的，VM 可能已停，机器可能已重启。把两者合成一个，会让每次切换都变成一次设置写入（也让每次设置编辑都变成关于「正在跑什么」的断言），而这正是 F2a 的注册表要避开的混淆。

**影响**：切换只改运行时字段；它让 `settings.json` 逐字节不变，F2b-1 的测试就是这么断言的。因此注册表里的 `current` 与 `default` 确实是两个不同的值，问「一次运行会用哪个」的客户端必须说清它指的是哪一个。把这一切暴露出去的端点、Tauri 命令、CLI 与 `sandbox:switch` 事件属 F2b-2；`Task.sandbox`（F2d）是第三个问题——单次*运行*要什么——它坐在这两者之上。

## 35. 端口租约承诺的是「同时存活的租约互不同号」，不是「号码永不重用」

**日期**：2026-09-23 ｜ **状态**：已定；随 v0.9 relay-fix 批次 1/N–2/N 落地

**决策**：`relay::lease_local_ports` 只保证两件事，不多一件。号码在其租约存活期间被保留（且 `hand_off` 之前有绑定的监听器在 OS 层占位），因此**两个同时存在的租约绝不携带同一个号码**；而租约释放会把它的号码还给池子，OS 可以再把它发出去——发给本进程，也发给别的进程。「进程存活期间某号码绝不二次发出」被考虑并**否决**：它需要对已释放号码做无界增长的隔离，而且会改变一个没有任何调用方需要的契约，因为调用方本来就用重试绕开那个无法关上的窗口（peer 只能在我们放手后才 bind）。

**理由**：真正要紧的窗口是*我们释放*与*peer 绑定*之间那一段，而进程内的注册表关不上它——用今天的参数，QEMU 拿不到预先绑好的 socket。所以注册表的职责比看上去窄：不让本程序的两处同时拿到同一个端口，并把端口在 OS 层占到最后时刻。把这个说准了，测试才写得出来：失败两次的那条断言（`concurrent_leases_never_repeat_a_port`）记录的是本次运行中曾取到的每个端口，于是一个已结束线程释放、又被 OS 重新发出的号码，被读成了「两个持有者同时持有」——而库从未做过这个承诺。

**影响**：测试把每个线程的租约停放到全部取完再比对（即代码真正保持的不变量），另一条测试钉住另一半（被销毁的租约让端口对任何人可 bind）。释放路径只删**自己的**号码一次（`HashSet::remove`），因此一次释放永远不会把另一持有者的保留一起删掉；注册表是 `LazyLock<Mutex<HashSet<u16>>>`，因为 `HashSet::new` 无法初始化 `static`。没有公开签名变化，也没有调用点变化：`leased_ports()` 仍返回 `Vec<u16>`（它的顺序从来不是契约），`agent` / `host-core` / `sandbox::vm` 未动。`sandbox/README.md` 向调用方写下契约，`port_race.rs`（默认忽略）继续把跨进程窗口当作压力测试走。

## 36. 沙箱申请是一条请求；决断属于另一个 actor，且不执行任何东西

**日期**：2026-09-23 ｜ **状态**：已定；随 v0.9 沙箱 F2c 批次落地

**决策**：申请改动沙箱与真的改动，是**两个表面**。`POST /v0/sandboxes/switch` 仍然改动节点、仍需要 `sandbox.switch`；`POST /v0/sandboxes/requests` 则只落一条申请，只需 `agent.run`——能跑 agent 的 actor 就是可以表达它所想的 actor。决断一条申请（`approve` / `reject`）先需 `sandbox.read`，因为决策者先要看得见队列，然后再需该请求自己的 `action` 所隐含的 capability：`switch` 要 `sandbox.switch`，`define` / `assemble` 要 **`sandbox.assemble`**（第 31 个 capability）。把节点搬走、与给它一个要跑的新定义，是两种权力，词汇表现在也这么说。

**理由**：替代方案——路由表每条路由只名一个 capability——表达不了「随便这条请求要哪一个」：那张表是处理器运行前就检查的静态列，而 action 要等请求被解析出来才知晓。所以两条决策以 `sandbox.read` 为门，由处理器再拿精确的那个对 actor 检查，这也是 `dispatch` 现在接收 actor 的原因。由此产生的后果被记下来而不是藏起来：文档里那句「词汇表里每一个 capability 都至少有一条路由」改成「都在某处被强制」——因为 `sandbox.assemble` 在装配端点落地前没有自己的路由，它是在那个处理器内部被强制的，而那里正好知道自己在决断什么。

**影响**：`AppState` 长出一条申请队列（`SandboxRequests`：`Mutex` 包着的 `Vec<SandboxRequest>`，被克隆进 loop 的工具网关，另加 `current_sandbox` 上的 `Arc`，使两个视图不会分叉），id 是自成命名空间的 `req-<pid>-<seq>`，记录形状为 `{id, requester_agent_id, action, sandbox, definition, reason, requested_at_ms, status, decided_by, decided_at_ms}`。**批准不执行任何东西**（切换仍是另一次带授权的调用），决策不可逆（`409`），id 未知是 `404`，并且**没有 TTL**：`expired` 为预留、无任何路径产生它——一排申请不是高危资源，清扫器会是为无人受益而新加的机制。loop 经 `agent::SandboxRequester` 抵达队列；该 trait 属于 `agent` crate，因为它无法命名 `AppState`，由宿主用克隆的子句柄实现（loop 住在 `AppState` 里面，所以 `Arc<AppState>` 会构成循环）。`sandbox:request` 是第 14 个事件：每次变化一帧，`{id, status, requester, action}`。

## 37. 项目以一个文件的形式离开与回来；AI 的写入就在链上

**日期**：2026-09-23 ｜ **状态**：已定；v0.9 落了端点，git 集成（B）属 v1.0

**决策**：「把项目带上」是**两个 HTTP 端点**，不是挂载、也不是仓库。`POST /v0/workspace/export` 把 workspace 以 `tar.gz` 作答；`POST /v0/workspace/import` 把归档当请求体收（zip、tar.gz 或 tar）。**git 集成是 B，而 B 属 v1.0**：以归档离开的项目每个宿主今天就能做，而一个仓库会带来第二个真相来源与第二套凭证故事。**bind mount 是 C，C 不做**：把宿主目录共进沙箱，恰好是沙箱存在要划的那条边界。v0.9 一个节点一个 workspace（多项目随 B 到 v1.0）。

**理由**：归档是 shell 本来就会说的格式（`tar czf`、`unzip`），所以一个项目可以离开这个工具、再进来，而不必由这个工具决定项目怎么存。替代方案——服务端写归档、答一个路径，像审计导出那样——在这里形状是错的：那些导出把文件写**进** workspace，因为那是运行的产物；而项目导出是被拿走的 workspace 本身，另一台机器上的客户端读不了一个路径。

**影响**：`host-core/src/workspace_io.rs` 拥有两个方向与全部守卫：没有 entry 可以逃出目标，符号链接/硬链接一律不跟随，`.riscdom/`——宿主自己的状态（审计库、快照、预检缓存）——既不打包也不解包。**只做包含性检查、不走扩展名白名单**，理由与现有 exports 相同：`WorkspacePolicy::check_write` 只允许四个源文件扩展名，而项目不只有源文件。import 带**自己的 64 MiB 上限**（`413`），而不是抬高每个 JSON body 共用的 64 KiB `MAX_BODY_BYTES`；请求体按字节读，是该表面上的第一个非 JSON 请求；已有同名文件是 `409`，除非 `?force=true`——因为替换 workspace 里的东西是一个决定，不是默认。capability 按方向分开：导入需 **`workspace.write`**（第 32 个），导出需 `workspace.read`——读一个项目和替换它不是同一种权限。两个打包器（`zip`、`flate2` + `tar`）本来就在 `Cargo.lock` 里，现在对**每个**平台都声明：项目归档是用户工具链产出什么就是什么，所以 Windows 宿主必须能读 `.tar.gz`，unix 宿主必须能读 `.zip`。最后，AI 自己的写入也可见：`write_source` 往审计链记 **`agent.file.write`** `{path, bytes}`。它是审计事件、不是 SSE 事件——事件计数仍为 14——因为它属于来龙去脉可证的地方；它存在，是为了让「模型写过哪些文件」是一行记录，而不是去重剖 `agent.tool.call` 的 arguments——那些被截到 4 KiB。

## 38. 任务声明它的沙箱；只有切换才改变节点

**日期**：2026-09-23 ｜ **状态**：已定；随 v0.9 沙箱 F2d 批次落地

**决策**：一次运行可以**声明**它用哪个沙箱——`Task.sandbox`、`POST /v0/agent/run` 的 `sandbox`
字段、Tauri 命令的新参数——而这个声明抵达这次运行启的 VM（工具链、QEMU 可执行文件、客户机内存）。
它**从不搬动节点**：`current_sandbox` 不变，搬动它仍旧是 `POST /v0/sandboxes/switch`，需要
`sandbox.switch`。两条拒绝守着它：没有的名字是 `404`（`cause: "name"`），不是**正在跑的** VM
所来自的名字是 `409`（`cause: "sandbox"`）。一次运行的解析顺序：声明，否则 `current_sandbox`，
否则配置默认，否则内置兕底（宿主发现）。

**理由**：VM 不能在运行时里被替换：一个 `vm_slot` 持有它，它的 QMP 与串口已交给它，agent 的工具
就操作它。所以任务级的选用是*启动参数*的选用，而其它读法都比例绝更差——静默地在错的客户机上运行，
或把「跑一个任务」变成一次需要调用方未必持有的 capability 的节点改动（而那正是 F2b/F2c 分离开的东西）。
同一理由固定了内核问题（F2d 裁决二）：`start_vm` 的 `elf_path` 是**运行**时启的，`def.kernel` 是
**切换**时启的；把两者混在一起会让一个定义静默地覆盖模型的选择。

**影响**：`Task` 多出 `sandbox: Option<String>`（带 `#[serde(default)]`，旧 supervisor 的任务行仍可解析）
与 `Task::with_sandbox`；worker 本就读整条 `Task`，所以跨进程协议改动就是那一个字段。`run_agent`
保留签名并委派给新的 `run_agent_for(emitter, input, sandbox)`，所以直接调用点一个都没动；三个能声明的
表面（HTTP、Tauri、worker）各自传递它。宿主需要一个它原本没有的事实：`current_sandbox` 只由成功的切换
写入，所以由 `start_vm` **工具**启起的 VM **没有记录下来的来源**——而冲突检查读的正是它。现在
`AppState::active_sandbox` 记录它：在运行的 VM 落入槽时（宿对对工具启 VM 的唯一视角）、由
`switch_sandbox`、以及快照恢复时（作为节点自己的沙箱，对一台从本节点恢复的客户机而言这是实话）写入；
由 `stop_current_vm` 清除。一次运行的拒绝阶梯按此顺序移进一个函数——声明、冲突、就绪（新的类型化
`HostError::NotConfigured`，路由因此不再重复检查就绪）——意味着坏的*参数*先于环境被回答：
`POST /v0/agent/run` 带一个未定义沙箱时，即使没有配置模型也是调用方的 `404`。定义的 `memory_mb` 经
新增的 `agent.set_memory_mb` 抵达 VM（`VM_MEMORY_MB` 曾是硬编码的 128；`VMConfig` 形状未变）。
解析读的是注册表的合并视图，所以一个任务命中手写定义时，拿到的与切换会拿到的一模一样。

## 39. 任务端点：同步、配置驱动的队伍、声明 `agent.run`

**日期**：2026-09-23 ｜ **状态**：已定；随 v0.9 接口交付 E0 批次落地

**决策**：`Dispatcher` 在进程内从 v0.8 起就可达，而**哪里都不可达**——本批让它可以从 HTTP 抵达，并定了三件事。**（一）执行者登记与那个端点同一批做**：只把本节点挂进 `LocalDispatcher` 的 `/v0/tasks` 会是 `/v0/agent/run` 的别名，所以队伍来自 `settings.json` 的 `executors`（label + program + args），**没有 `env`**，也**没有运行时注册端点**。**（二）同步**：`POST /v0/tasks` 以执行者的 `TaskOutcome` 作答，没有任务表，没有 `GET /v0/tasks/{id}`。**（三）不加 capability**：两条路由都声明 `agent.run`。

**理由**：（一）端点的价值完全在于「按 target 路由到**另一个**执行者」；只有本节点时，它与「在这里跑」的区别小到无法向人解释（仅多：按 target 路由、返 `TaskOutcome` 而非 `AgentOutcomeView`、多一道 `NoSuchAgent`）。队伍必须来自某处，而**配置**正是「一台节点被交给你时它是什么」的所在：不是一条会改节点行为的运行时写路径（那是另一批的权限问题），而是一个人可以打开来读和改的文件。不暴露 `env` 符合本仓库的红线：一个设置文件会变成放密钥的地方——而 handle 的 `env` builder 仍留给有资格决定执行者环境的代码。（二）`/v0/agent/run` 已是同步的，而一项会跨进程启动编译与引导的工作本来就不短：把异步硬加进来需要全仓都不存在的任务表（侦察安全阀 3），换来的是一个没人要求的轮询形状。一个跑失败的任务**仍是**一个 `Ok(TaskOutcome)`——它的 `outcome` 说 `failed`——所以「失败」不需要 500。（三）`agent` 的 capability 词汇表是 32 项，而 `server/src/auth.rs` **硬断言** `Capability::ALL.len() == 32`；更根本的是，派发一个任务就是在导致一台 agent 跑，而这正是 `agent.run` 早已意味的事（F2c 用了同一套推理：能跑 agent 的 actor 就是能说它想要什么的 actor）。把一个目标从「无人拥有」中区分出来是**参数**问题，而不是权限问题。

**影响**：`LocalSettings` 多出 `executors: Vec<ExecutorSpecSettings>`（`#[serde(default)]`，`SETTINGS_VERSION` 不动——与 `sandboxes` 同款加法），而 `load` 会丢掉 label 或 program 为空的条目（为了一个不可达的目标列出队伍是在承诺做不到的事）。`ExecutorSpecSettings` 是 **host-core 本地**类型：`worker::ExecutorSpec` 不能复用，因为依赖方向是 `worker → host-core`，反过来就是环。`AppState` 多出 `executors: Mutex<Vec<Arc<dyn AgentHandle>>>`，由 `register_executors` 在三个构造函数的 `load_settings` 之后填充——**这是纯数据，不起任何进程**（`StdioExecutorHandle::new` 只记录要跑什么；子进程出现在 `run` 里），所以安全阀「构造时起子进程」未命中，登记也就无所谓即起还是懒起。节点**未被登记**：它自己的 handle 仍由 `local_dispatcher` 构建，那是「本节点作为执行者」的预留缝隙。（本批未用的）`HostAgentHandle` 会持 `Arc<AppState>`，而若把它挂进 `AppState` 就会造出一个自引用环——把本节点排除在外既是对的，也避开了这个。`AppState::dispatch_task` 在调用方没给时补一个 `TaskId`，并借 `dispatch_task_value` 走同一个 `LocalDispatcher`；两个新的 `HostError` 变体（`NoSuchExecutor`、`TaskFailed`）让路由层把「调用方的参数」与「宿主坏了」分开，`task_error` 再把它们映射为 `404 cause "target"` / `500 cause "task"`。两边各有一条 Tauri 命令（已注册、未接线）与一个 CLI 子命令。

## 40. 工具 schema 是文档，每一半的真相各有一个归属

**日期**：2026-09-23 ｜ **状态**：已定；随 v0.9 接口交付 E2 批次落地

**决策**：这条接口的词汇以两份文档发布，而真相的每一半恰好有一个核对者。`docs/tool-schema-executor.md` 携带 `tools_json()` 构建的八个工具，就是执行者模型每轮拿到的那个数组；`docs/tool-schema-control-plane.md` 把每个端点写成一条 OpenAI 风格函数定义（75 条工具：32 查询、36 控制、3 本机、4 带路径参数），名字用一套写明的推导规则从路径得出。核对按各自能看到的东西分工：`agent/tests/tool_schema_doc.rs` 把执行者文档与 `tools_json()` 对校；`server/src/routes.rs` 的测试把控制平面的带标记路由表与 `ROUTES` + `LOCAL_ROUTES` + `resolve` 对校；`scripts/check-tool-schema.mjs`（gate 的一步）owns 两者都看不见的东西——译文携带逐字相同的带标记块、表里每个名字是文档自身的推导结果、且每个名字既有表行又有定义。`agent/README.md` 的表变成指向 schema 文档的索引。

**理由**：工具 schema 是与模型之间的契约，而不是关于模型的叙述：执行者的模型靠那些描述决定做什么，监工的模型靠那些定义决定要什么。两者都是手写的——执行者那份是因为 `tool_specs()` 在调用时用 `serde_json::json!` 字面量构建 `parameters`，控制平面那份是因为根本不存在机器可读的参数来源——所以两者都可能漂。按**可见性**而不是按文档来拆守卫，才是诚实的做法：只有 Rust 读得到 `tools_json()` 与 `ROUTES`，只有 Node 脚本能不编译就比较一份文档与它的译文。两半都不重述对方的活了，所以一次失败只指向一个原因。替代方案（一份生成文件）被否决：控制平面的描述与参数是**写出来**的，生成周围文本就意味着发明一个服务端并不存在的参数来源。

**影响**：四份新文档（两对）、两个新核对、gate 一步，以及更小的 `agent/README.md`。刻意**不**机器核对、并在两份文档里写明的部分：控制平面文档的 `description` 与 `arguments` 两列、以及 `parameters` 对象。规范表仍是 API 文档的 §5。命名推导由脚本强制（表里某行的名字不是推导结果就失败），而六个 `_post` 后缀与四条动词命名路由是仅有的例外——它们列在文档里、硬编码在脚本里，于是第五个例外必须被决定而不是被偶然发现。

## 41. 参考监工是 Python、仅标准库、走 HTTP

**日期**：2026-09-23 ｜ **状态**：已定；随 v0.9 接口交付 E3 批次落地

**决策**：这条接口的外部那一半得到一份可跑的参考实现：`examples/python/dispatch.py`——一个在内核之外、自己不持有模型、通过 HTTP 上的控制平面驱动一个节点的进程：`GET /v0/executors`、每条任务一次 `POST /v0/tasks`（同步、一条一条）以及 `--follow` 下的 `GET /v0/events`。它**只用标准库**（`urllib.request`、`json`、`argparse`、手写的 SSE 拆帧）；token 来自 `--token-file` 或 `$RISCDOM_TOKEN`，绝不来自参数；退出码沿用 CLI 的约定（`0`/`1`/`2`/`3`）；而 `--self-test` 用一个 stdlib `http.server` 假控制平面跑真实的派发路径，于是它能离线自证。gate 在 `PATH` 上有 Python 解释器时跑这个自证，没有就打印 skip。

**理由**：侦察发现四个 Rust example、Python 侧无任何可复用——于是「写一个监工」从白纸开始。参考实现是拿来**读**的，不只是跑的：它得展示**形状**——三个端点、一条任务进一个结果出、一次派发的四种归宿——而不是把它埋在客户端库下面。`requests` 与 `httpx` 因此被否决（它们会教一个监工并不需要的依赖，还会把「线上格式就是接口」这件事藏起来），靠 stdio 直接跟 `worker` 说话也被否决（那是 `worker/examples/dispatch.rs` 的活，而它根本不需要节点）。自证是让这份示例诚实的那部分：无法验证的示例会烂，而这一份是 gate 的一步，没办法悄悄烂掉。选 Python 而不是第五个 Rust example，是因为读者是写监工的人——多半不是 Rust 开发者——也因为 stdlib Python 是最短的真实示意。

**影响**：`examples/python/`（脚本 + 双语 README，于是一般的文档门禁同样适用它）、`scripts/gate.sh` 的一步新步骤（带打印的 skip）、客户端指南的一节（§8）以及本条。已在 README 里写明而非藏起来的已知限制：任务一条一条发（真正的监工会让它们重叠，而一个队列会把契约藏起来）；`--follow` 无法把一帧归因到某条任务，因为信封的 `task_id` 对宿主事件是 `null`——归因在审计链里；节点必须已经配好 `executors`，因为队伍是配置（E0）。`worker/examples/dispatch.rs` 未动：它是同一幅画的另一半，README 把差别列成表。

## 42. 远程执行者是一个示例，且它的传输是手写的

**日期**：2026-09-23 ｜ **状态**：已定；随 v0.9 接口交付 E4 批次落地

**决策**：`agent::AgentHandle` 自 v0.8 留开的那条缝（*「远程实现……正好实现这个 trait。**尚未写**」*）由一个**示例**填上：`worker/examples/remote_executor.rs`，而不是生产代码。`HttpExecutorHandle` 持一个本地 label、节点的 base URL、可选的 bearer token 与远端 target；它的 `run` 把一个任务形状的 body POST 到 `POST /v0/tasks`，并返回远端执行者产出的 `TaskOutcome`——身份是**节点的**，绝不是它自己的 label。注册就是那条缝承诺的那一行——`LocalDispatcher::new(vec![Arc::new(handle) as Arc<dyn AgentHandle>])`——而**本工作区没有任何 crate 被改动**。传输是用 `std::net::TcpStream` 手写的 HTTP；自证对着回环上的替身节点跑。

**理由**：（一）**那条缝本身就是交付物**。这个 trait 被设计成可以从外部实现，所以证明就是一份什么都不碰的实现——如果填它需要改 `agent` 或 `host-core`，那说明那条缝不对，而那才是真正的发现。（二）**是示例，不是随行句柄**。生产级的 `HttpExecutorHandle` 需要一套关 token、TLS、重试与身份的策略，而 v0.9 尚未定下这些；示例可以展示形状并在 README 里说明这件事。（三）**不新增依赖**。`worker` 只依赖 `host-core`、`agent` 与 `serde_json`；`reqwest` 0.12 在锁里是因为 `cli` 用它，但在这里加上它会让参考实现把它要展示的那根线藏起来。请求用手写，用的是本仓已有的手法（`server/tests/smoke.rs`、`host-core/tests/common/mod.rs`）。（四）**端点是 `POST /v0/tasks` 而不是 `/v0/agent/run`**。后者在节点自身上跑、答 `AgentOutcomeView`；只有前者路由给远端节点**拥有的**执行者并答 `TaskOutcome`——与 `StdioExecutorHandle` 从子进程拿到的契约相同，这正是它是真正执行者而非形状演示的原因。（五）**两个名字，与 stdio 句柄一样**。本地派发器按句柄的 `agent_id` 路由；远端节点按它认识的 label 路由，所以 body 把它作为 `target` 带上。发本地 label 就是在要一个远端节点未必拥有的执行者。

**影响**：一个新示例、一步新 gate 步骤（`cargo run -q -p worker --example remote_executor -- --self-test`，与 Python 那一步并列）、`worker/README.zh-CN.md` 的一节、客户端指南 §9（于是「还没有的东西」重编号为 §10）以及本条。映射是刻意的、并写在代码里：远端节点的 `404` 是 `DispatchError::NoSuchAgent`（缺的是**对面**的队伍——一个路由事实），其它都是 `Failed`，而一条指向别的任务的应答是协议破裂而不是结果，与 stdio 句柄的处理完全一致。已在 README 写明而非藏起来的已知缺口：它是回环 HTTP，不是跨设备方案——真正的跨机句柄需要双向认证以及对端一个 token 授权什么的叙事，那是 v1.0 的工作；而示例是对着替身节点证明的，因为真的那个住在 `server` crate 里，而 `worker` 刻意不依赖它（`POST /v0/tasks` 由服务端自己的测试拥有）。

## 43. §20 的 DCO 条款已撤销；CLA 已覆盖其目的

**日期**：2026-09-24 ｜ **状态**：已定

**决策**：§20 里的「DCO」部分撤销。贡献只由 CLA 覆盖——即 `.github/workflows/cla.yml` 记录的那份签署，与 `CONTRIBUTING.zh-CN.md` 的描述完全一致。不要求 `Signed-off-by` trailer，也不在 CI 里接任何 DCO 校验。

**理由**：两件工具并不干同一件事，而更强的那件已经在位。CLA 是**权利授予**（再许可、专利）——正是它让一个 open-core 项目能把派生作品以商业专有许可分发，所以在这里是必需的。DCO 是**来源声明**（`Signed-off-by`），是两者中更弱的那个。§20 自己的措辞就带着矛盾——「DCO（CLA 已有）」。接 DCO 也不是免费的：它是每个 PR 上又多一条规则，并会把一个 `Signed-off-by` 校验塞进 CI。

**影响**：`.github/` 不接 DCO 校验。同批新增的 issue 表单与 PR 模板要的是 CLA 与 gate，而不是 sign-off。若日后想在 CLA 之上再加 DCO，那是本账本里的**新条目**加一步新 CI——而不是重写 §20。

## 44. 需要 guest 或工具链的测试，在它的 `#[ignore]` 标记里明说

**日期**：2026-09-24 ｜ **状态**：已定

**决策**：环境前提在 CI runner 上不满足的测试，带 `#[ignore = "<它需要什么>; run with --include-ignored"]`，三选一：`requires a QEMU guest and a RISC-V GCC`（会编译 guest 并启动它）、`requires a discoverable QEMU`（只构建 VM 句柄或探测 discovery，不起 guest）或 `requires a discoverable RISC-V GCC`。gate 因此按**能力**分叉而不是按平台：没有工具时跑 `cargo test --workspace --no-fail-fast`（标记把这些测试挡在外面），有工具时跑 `cargo test --no-fail-fast -- --include-ignored`，再加每个需要 `DEEPSEEK_API_KEY` 或会真写 OS 钥匙串的测试一个 `--skip`。不需要这些的测试保持无标记，处处都跑。

**理由**：过去按平台分叉——非 Windows 跑 `cargo test -p audit -p sandbox --lib`，638 个里的 10 个——于是它以下的一切在非 Windows 上**静默**失去覆盖，而这件事直到某个 Linux 步骤终于编译 `host-core` 并变红才被发现（E4）。前提是**能力**，不是操作系统。标记的 reason 字段是需求唯一能待的地方，因为 Rust 没有测试标签——而 `--skip` 过滤的是**测试名**，集成测试里就是函数名：文件名永远匹配不上，而短子串会连带带走可移植测试（`--skip keyring` 会带走三个，其中两个是可移植的）。

**影响**：50 个测试带标记（37 + 8 + 5），`tests/` 的 ignore 从 8 变成 58，`scripts/gate.sh` 再无按平台分叉的测试分支。没有工具时 `cargo test --workspace` 跑 588 个（过去是 10）；有工具时 `--include-ignored` 跑 643 个。一个默默需要工具的测试现在会在 runner 上失败而不是被跳过——三种标记存在的意义就是让前提被**点名**，而不是靠猜。

## 45. 模拟缺前提，必须覆盖每一条 discovery 路径

**日期**：2026-09-24 ｜ **状态**：已定

**决策**：要判断某个测试是否需要环境前提（QEMU guest、RISC-V GCC、网络、OS 钥匙串），靠**模拟其缺失**时必须覆盖被测代码能走的**每一条** discovery 路径，而不只是显式那一条。就工具链而言共有四条：`CompilerConfig::discover()`（显式探测，失败即 `Err`）、`CompilerConfig::from_env()`（**失败时回退裸可执行名**，而裸名靠 `PATH` 解析）、环境变量（`RISCDOM_*` / `QEMU_SYSTEM_*`），以及 `PATH` 本身。因此仿真要**同时**把变量指向不存在的路径，**并**把已知的工具链 / QEMU 目录从 `PATH` 里滤掉（`.cowork-temp/run-noguest.ps1`）。

**理由**：§44 的第一次仿真只把 `RISCDOM_*` 指向不存在的文件——那能打断 `discover()`，却打断不了 `from_env()`，它的回退是裸名，而开发机的 `PATH` 上正好有工具链。于是有 4 个测试从未被标记，而那批加标记的提交恰恰在本地看着绿的 target 上 CI 变红。这个洞是**系统性**的，不是偶然：以后每新增一条 discovery 路径都会把它重新打开。

**影响**：将来新增工具链 / 沙箱 / 网络探测，必须逐条路径覆盖，`.cowork-temp/run-noguest.ps1` 随之扩。这也是本系列记下的第二类「本地 gate 绿、CI 红」根因：第一类是缺系统包（E4 的 `libdbus-1-dev`），这一类是环境**能力**。

## 46. 第二种语言按源扩展名选，不靠 toolchain map

**日期**：2026-09-24 ｜ **状态**：已定

**决策**：v0.9 F3a 给沙箱加上第二种语言 Zig，而语言由**源文件扩展名**决定——`.c` / `.h` / `.S` / `.s` 走 GCC，`.zig` 走 `zig build-exe -target riscv64-freestanding`。`compile_freestanding` 保持原签名，Zig 编译器作为第二个值藏在 `CompilerConfig` 里（`CompilerConfig.zig: ZigConfig`），所以 `toolchain_path` 与 `zig_path` 是**两个独立的单值**，不是 map。生成的 `link.ld` 原样复用（它不指定任何编译器），Zig 也不注入任何东西：源自己写 `_start`，因为 `-bios none` 的客机跳到载入地址而不是 ELF 入口点，启动代码必须排最前——这正是 `.text.start` 段的用途。

**理由**：架构 §9 早就为「将来有多种语言」预留了 `toolchain` 变 map，但本批**故意不**迈这一步：变 map 会把 fingerprint schema 从 v1 推到 v2，那是另一个关于历史与 diff 的决策。两个并列的单值今天零成本，将来也仍是加法——map 里的 `{c: …}` 项就是改名后的 `toolchain_path`。

**为什么用扩展名而不是参数**：模型先写文件、再把文件名给它，扩展名本来就在请求里；另加一个「语言」参数只会多一个必须与源保持同步的东西。这也让 C 路径一字未动——旧代码没有一条分支挪位。

**拆出去的（F3a-download）**：下载 Zig 归档**不**在本批。Zig 的 macOS/Linux 构建是 `.tar.xz`，而 `toolchain_download::ArchiveKind` 只认 `Zip` 与 `TarGz`，要解包就得新增一种归档类型加一个 xz 解码器；产物定位器也带 GCC 形状（`find_compiler` 匹配 `agent::GCC_NAMES`，而 Zig 装的是 `zig` / `zig.exe`）。任一条都超出现有下载器的「填一条规格」形制，所以它是独立批次——而且正是 Rust 也需要的那一批，因此排在 F3b 之前。

**影响**：`write_source` 放行 `.zig`（`Policy.allowed_extensions`），`settings.json` 新增 `zig_path`，工具 schema 文档与 `agent/README.md` 都点名两种语言。Rust（F3b）复用同一分派点；Python 不属 v0.9（它需要 Linux 沙箱，属 v1.x）。

## 47. MVP 期的 Zig 禁令解除

**日期**：2026-09-24 ｜ **状态**：已定

**决策**：`PROJECT_CONSTITUTION.md` 在**三处**禁 Zig——§3.6（在「不可协商」列表内）、§4.6（代理层）、§5（语言限制）——并在 §9 的 v0.1 清单里又记了一次。自 v0.9 F3a 起 **Zig 解禁**；C++、Rust、Python 仍在禁令内（Rust 待 F3b，Python 待 Linux 沙箱，v1.x）。**原句全部保留**，三处各带一条旁注，说明它所写的时效条件已过。§9 **不动**：那是历史清单，v0.1 当时确实只支持 C。

**理由**：Zig 自带交叉编译器（无 sysroot、无外部链接器），能为 `riscv64-freestanding` 产出载入地址 `0x80000000` 的裸机 ELF——与 C 路径同形，所以沙箱本身无需改（§46）。MVP 期禁 Zig 是为把 MVP 面收小，不是长期语言政策。起决定作用的是：那些条款禁 Zig 的条件是「**MVP 阶段**」，而 MVP 已于 v0.8.0 结束——条款自带的限定词不再成立。因此解禁 Zig **不是协商一条不可协商的原则**，而是诚实读条款自己的时效条件。「不可协商」列表没有被削弱，其标题也一字未动。

**影响**：§3.6、§4.6、§5 各带一条时效旁注（原句完整、`non-negotiable` 完整）；§9 未改。受支持的语言现为 C / Zig。宪法本身是一份停在 v0.5 roadmap 节之后的活文档——那是独立议题，在这里记录，本批**故意不修**。

## 48. xz 解码器用 `xz2`，且 `.tar.xz` 那条臂不带平台门

**日期**：2026-09-24 ｜ **状态**：已定

**决策**：`ArchiveKind` 新增 `TarXz`，由 `extract_tar_xz` 解包——它逐行照抄 `extract_tar_gz`，只把 `flate2::read::GzDecoder` 换成 `xz2::read::XzDecoder`，保留同一个 Zip-Slip 守卫（`safe_relative`）、同一个 `set_overwrite(true)`、同一套逐条目取消。解码器用 **`xz2`** 而非 `lzma-rs`，且分派臂**不带 `cfg` 门**。

**为何选 `xz2`**：它与 `flate2` 同作者、API 同形（`read::XzDecoder` 就位在 `read::GzDecoder` 旁），所以新函数是**照抄**而不是新设计；且它早已在 `Cargo.lock` 里——`zip` 拉了 `xz2` → `lzma-sys`——因此直接依赖边只让锁**多一行**、无版本变动。`lzma-sys` 在 MSVC 上直接编译其 vendored liblzma C（它故意禁用 `pkg-config`），而在 unix 主机没有 `liblzma` 时也回落到同一份 vendored 构建，所以两个平台都**不新增系统库前提**。备选 `lzma-rs`（纯 Rust，也经 `zip` 在锁内）需要我们自己写「先解压流、再交给 `tar`」的桥，而我们发布的每个平台本来就已编译那条 C 路径，因此没有收益。

**为何不加 `cfg` 门**：`.tar.gz` 在这里被限到非 Windows，是因为它只是我们自制下载里的 **unix 资产**。`.tar.xz` 不同：它是**宿主自己** Zig 发行包的形态（Windows 是 `.zip`，macOS/Linux 是 `.tar.xz`），也是 Rust 的 `rust-std-*.tar.xz` 在所有平台的形态。把它限到非 Windows 只会被下一批撤销，而「Windows 主机也能读 `.tar.xz`」正是那两个下载需要的能力。

**影响**：`extract_tar_xz` 在所有平台可用；`spec_for_current_platform()` **未改**（仍是那一条 xPack 规格），所以目前还没有任何东西会去下载 xz 归档——Zig 定位器与 Zig/Rust 规格属 apply 批。`ArchiveKind` 不参与 serde，无线类型变动。

## 49. 下载要说出自己的工具链；语言是个标签，规格仍是两个函数

**日期**：2026-09-24 ｜ **状态**：已定

**决策**：`DownloadSpec` 新增 `toolchain: Toolchain`（`C` / `Zig`，可 serde，缺省即 C）。它决定模块推不出的**两件事**：解包后的归档里由**哪个定位器**找产物（`product_locator`：C 走 `find_compiler`，Zig 走新的 `find_zig`），以及装完之后宿主做哪一次**采用**（C 走 `set_toolchain_path`，Zig 走 `set_zig_path`）。语言以**标签**抵达下载——CLI 的 `--toolchain zig`、`POST /v0/toolchain/download` 的 body `{"toolchain":"zig"}`、Tauri 命令的可选参数——而**只有一个**函数 `Toolchain::parse` 把标签变成枚举，任何一条边都不可能跟另一条打架。Zig 有自己的规格函数（`zig_spec_for_current_platform`），`spec_for_current_platform()` 一字未动。

**为何用一个字段而不是第二套规格家族**：两个规格函数共用一个枚举。规格携带的是**产物**（版本、URL、校验和、归档种类），两个发布在这上面毫无共同之处；但下载之后的一切——暂存目录、改名、幂等的「已安装」判定、采用——完全相同，而它需要知道自己面对的是哪个产物。`toolchain` 字段正是把这份知识放在两边都已读到的那一个位置。

**为何线上传的是标签而不是更富的类型**：HTTP body 的参数按设计就是扁平字符串（`Params::from_json` 保留标量、丢弃嵌套值），而 Tauri 命令收 `Option<String>`，前端因此发不出别的边会拒的形状。`None` 与空串都等于 C——正是本批之前每个调用者一直在发的——所以改动在每条边上都是加法，包括那个原本没有 body 的端点。

**为何 `install_subdir` 仍然是死的**：本批本想「接通或删掉」，结果发现接通不成立。`download_and_install` 最后一步是 `fs::rename(staging, install_dir)`，而 `install_dir = dest_root/<version>`；若按「解压到 `dest_root/<install_subdir>`」且 Zig 用空串，就会往已存在且非空的 `dest_root` 上改名，直接失败。模块真正需要的是**定位器**，那是逐语言的，不是一个目录提示。字段保持原样、继续是死字段：那是它自己的（小）决策，记在这里，免得下一批重新踩。

## 50. 读别的进程输出时，不得因第一行读不出来就停下

**日期**：2026-09-24 ｜ **状态**：已定

**决策**：抽出子进程 stderr 的那个循环，对读不出来的行**只计数、继续读**。`InvalidData`（字节不是 UTF-8）与其它 I/O 错误让 `bad_lines` 加一；`Interrupted` 重试而不计数；`Ok(0)`（EOF，子进程已退出）仍然结束线程。线程的存活状态与缓冲并列发布，超时的测试把三样都打印出来：已捕获行数、坏行数、读取器仍在读还是已停止。

**理由**：旧循环——`for line in reader.lines() { let Ok(line) = line else { break }; … }`——会把**一行**读不出来变成它之后**所有行**的永久、静默丢失。这是最差的失败形态：读取器看起来健康，缓冲区只是不再增长，而超时的测试分不清「那行根本没来」与「读取器早就停了」。`server/tests/logging.rs` 的 `the_connection_line_appears_at_info` 在 Linux CI 上正是这种形态（两次，各 5.09 s，捕获到的 stderr 里只有启动警告）。

**本决策不主张的事**：不主张这就是 CI 的根因。证据反而说这不可能是我们的改动造成的（它之前那个提交对 `server` 的唯一改动是下载臂的参数读取），而且同一测试在之前两次 Linux run 都是绿的；读取器当时到底有没有停，正是新的诊断要回答的。5 秒超时与 25 ms 轮询**故意不动**：加长超时只会把这类 bug 盖住，而本仓此前的两个 flake（relay 端口租约、`audit::concurrency`）都是靠消除竞态修好的。

**影响**：这条规则可推广到每一个「读别的进程输出」的 helper——一个遇到坏输入就死掉的读取器，它的沉默毫无信息量。生产代码零改动；三个既有测试保留各自超时，另加两个单测读 `Cursor`（不涉及子进程）把那两半钉住：正常流的每一行，以及非 UTF-8 行之后的所有行。

## 51. 给子进程的每一根管道都要读到 EOF，否则写入就可能把子进程杀死

**日期**：2026-09-24 ｜ **状态**：已定

**决策**：本仓交给子进程的管道（`Stdio::piped()`）要**读到 EOF**，而不是「读到调用方要的东西就停」。`server/tests/logging.rs` 的 `read_banner` 把读取器**交还**给调用方继续抽干，且子进程的 stdout 与 stderr 走同一个 `drain_reader`。

**理由**：那个测试原本读完 banner 行就把子进程的 stdout 丢掉，而 server 紧接着还要写三行（`server/src/main.rs:81-83`）；往一个读端已关闭的管道写就是 EPIPE——而 **Unix 上这会触发 SIGPIPE，其默认行为是终止进程**，而且无声：没有 panic 消息、来不及记任何日志、stderr 直接到 EOF。两次 CI 失败正是这个形态（stderr 读取器健康并报 `0 line(s) unreadable`、读取器已到 EOF、而 server 在写出 `connection from … ended` 之前就消失了）。Windows 没有 SIGPIPE（关闭的管道在那里只是错误），所以同一提交本地绿、Linux 红。这是本系列记录的**第三类**「本地绿、CI 红」根因：前两类是缺系统包（E4）与缺环境能力（B-3b）。

**影响**：`Stdio::piped()` 就意味着「把管道抽干净」——这里如此，本仓任何其它用管道驱动子进程的地方也如此；失败信息会带上子进程退出状态与 stdout 行数，所以再次发生时靠一行 CI 输出就能定性，而不必再花三个批次。生产代码零改动——server 自己的 `println!` 是对的，错的是读取端。

## 52. 与版本绑定的下载，在开始之前就拒绝，而不是之后

**日期**：2026-09-24 ｜ **状态**：已定

**决策**：只有当机器的 `rustc -vV` 报出与钉住资产**同一个 release** 时，才下载 Rust 的 sysroot（`rust-std`）；拒绝发生在 `AppState::begin_toolchain_download`——Tauri 命令、HTTP 路由与 CLI 都必经的那个方法——所以没有任何一条边能绕过，也不会先传出任何字节。判定本身是纯函数（`rust_release_matches`），因此在没有 `rustc` 的机器上也能测。给别的 release 的 sysroot 会被拒绝，并一条消息里同时说清两个版本。

**理由**：`rust-std` 里带着 `rustc` 会与自身比对的元数据，所以版本不符不是「稍微不对」，而是根本用不了。备选方案——下载时去取资产的兄弟文件 `.sha256`——在定版时就被考虑并否决了（§F3b 侦察裁决 3）：本仓在这里的承诺与 Cargo 的锁文件同类：**源码里的校验和就是这个构建要验证的那个**；运行时取来的校验和验证的是传输，不是意图。提前拒绝也让失败变得诚实：用户会知道自己的 `rustc` 是另一个 release，而不是在第一次编 `.rs` 时才发现——那时 12 MB 已经落盘。

**影响**：`RUST_VERSION`（1.98.1）就是那个 pin；工具链是其它 release 的用户在 pin 移动之前无法下载 sysroot——这是故意的，因为那个下载本就不可能有用。这条规则的推广面：将来任何与某个编译器 release 绑定的组件，都在 `begin_toolchain_download` 里以同一种方式设门，而不是在采用时。

## 53. MVP 期的 Rust 禁令解除

**日期**：2026-09-24 ｜ **状态**：已定

**决策**：宪法 §3.6、§4.6、§5 在 MVP 期禁 Rust。自 v0.9 F3b 起**解除 Rust 禁令**；C++、Python 的禁令不变（Python 待 Linux 沙箱，v1.x；C++ 仍不在范围）。**原句全部保留**，三处各带一条旁注，说明它所写的时效条件已过。

**理由**：Rust 的 `riscv64gc-unknown-none-elf` target 加 `no_std` 能编出载入地址 `0x80000000` 的裸机 ELF——与 C、Zig 路径同形，所以沙箱本身无需改。`rustc` 由系统提供（照 QEMU 的「用户自装」先例）；`rust-std` 自下载，且与 `rustc` 版本耦合，pin 在 1.98.1（§52）。禁令自带「MVP 阶段」限定词，而 MVP 已于 v0.8.0 结束——因此解禁 Rust **不是协商一条不可协商的原则**，而是诚实读条款自己的时效条件。

**影响**：§3.6、§4.6、§5 各带一条时效旁注（原句完整、`non-negotiable` 标题未动）；§9（v0.1 完成情况）未改，因为那是历史：v0.1 当时确实只支持 C。受支持的语言现为 C / Zig / Rust；Python 待 v1.x。

## 54. 会话库会等锁，但故意不做成审计库

**日期**：2026-09-24 ｜ **状态**：已定

**决策**：`SessionStore` 在它**第一次写之前**设好 `busy_timeout`（5 秒，`session::BUSY_TIMEOUT`），且 `append_message` 把消息插入与会话 `updated_at_ms` 更新当成**一个事务**。它**不拿 WAL、不拿 `synchronous = NORMAL`、不拿打开重试**——那三样是审计库自 v0.8/v0.9 起就带着的。

**理由**：两个库的并发模型**本就不同**。`audit.db` 是**有意跨进程共享**的（一个 workspace 一条链，多个写者追加），正因为如此，WAL、busy timeout 与打开重试在那里才是承重的——`PRAGMA journal_mode = WAL` 会绕过 busy handler，所以那次切换本身就需要重试。会话库是 **per-instance**：`with_data_dir` 让每个实例拥有自己的 `<data-dir>/sessions.db`。但「per-instance」是默认而**不是保证**——两个走默认路径的 CLI / 服务器进程会落到同一个 `<temp>/riscdom/sessions.db`，而显式共用 `--data-dir` 本就是刻意撞车——在这些情形下，SQLite 的 `busy_timeout` 默认 0 会把第二个写者变成即时的 `SQLITE_BUSY`。而这个失败落在 `SessionStore::open` 里，所以它失败的不是一条命令，而是**整个实例起不来**。busy timeout 解决的正是这件事；WAL 则只会为一种本库不存在的共享模型多加两个副文件（`-wal`、`-shm`）。若将来会话真的变为共享，**要重开的是这一条**——而不是默默把审计库的 WAL 抄过来。

**影响**：`session.rs` 多设一个 pragma、把一个方法包进事务；其余未改，审计库一字未动。`docs/multi-agent-foundation.md` 曾记的那条遗留（「会话 DB 没有 WAL 与 busy timeout」）由此被取代。两个库之间的不对称，从此是一条决策而不是一次疏忽。

## 55. Web UI 在路由表之外提供，且不需要 capability

**日期**：2026-09-24 ｜ **状态**：已定；随 v0.9 D2a 批落地

**决策**：当 `riscdom-server` 拿到 `--web-root <dir>` 时，它把该目录的 `index.html` 挂在 `/`、把它的文件挂在 `/assets/*`，位置在查路由表**之前**、且**不**做 `Authn` 检查。只有 `GET` 走这条路，命名空间只有这两种形状，**没有 SPA fallback**，也**没有为此向 `ROUTES` 加任何路由**。目录是请求时读盘；二进制内不内嵌任何东西。`/v0/*` 下的一切不变，仍要 capability 检查。

**理由**：三条理由，每一条在别的设计里都会变成缺陷。（a）路由表**就是** API：`Capability::ALL` 是一套词汇，每条路由都要声明一个，而且有两个测试拿它与两个语言的文档对锁。静态文件没有 capability 可声明，硬放进去就只能伪造一个 capability，或引入第二种「路由」概念。（b）资源不带秘密——文档、样式表与只调 API 的脚本。为它们要求 token 一无所获（未认证的请求仍然学不到宿主的任何信息），却会赔掉最关键的那件事：那个要求输入 token 的页面本身。（c）备选方案——再起一个静态服务器，或上 CORS——会把 UI 放到与 API 不同的源上，于是同源 `fetch` 变成要预检的跨源请求，token 也成了跨站凭证。

**影响**：`.js` / `.css` / 图片类型显式映射（`content_type_for`）；hash 资源标 `immutable`，而 `index.html` 标 `no-cache`——因为一个指向已被后续构建删掉的资源的 `index.html`，正是唯一会让应用崩掉的那个陈旧文件。穿越被拦两道：名字不得含 `..`/根/前缀组件（`workspace_io::safe_relative` 的规矩），**且**真正找到的文件必须解析在解析后的 root 之内，因为 root 里的符号链接可以指向外面；客户端给的名字从不做百分号解码，所以编码过的 `..` 是「不存在的文件」而不是穿越。不给 `--web-root` 时，`/` 回一个 404，消息里点名该旗标。D2b 负责做它所提供的那个页面。

## 56. 一份前端产物，两种传输，运行时选

**日期**：2026-09-24 ｜ **状态**：已定；随 v0.9 D2b-1 批落地

**决策**：UI 的 API 面对同一个接口有**两个实现**——`ui/src/api/tauri.ts`（桌面外壳的 `invoke` / `listen`）与 `ui/src/api/http.ts`（控制平面的端点）——由 `ui/src/api/index.ts` 依 Tauri 2 自己的全局量（`window.__TAURI_INTERNALS__`，即 `@tauri-apps/api/core.js` 自己调 `invoke` 时用的那个对象）**在运行时选一次**。构建不变：一次 `npm run build`、一份 `ui/dist`，桌面外壳以 `frontendDist` 加载它，服务端用 `--web-root` 提供它。共用的形状在 `api/types.ts`，两种传输都需要的那条规则在 `api/envelope.ts`——两者都不属于某一种传输。

**理由**：另一条路是在**构建期**定实现（Vite alias，或带自己 `outDir` 的第二个入口）——那会产出两份产物，并立刻引出本项目不想回答的问题：`--web-root` 指向哪一份，`tauri build` 刚打包的又是哪一份？陈旧或错位产物是一类没有可见症状、直到用户报障才暴露的缺陷。运行时判定的代价是一个 `if`，换来「就是同一个 UI」这一字面事实。选这个全局量、而非构建标志或环境变量，是刻意的：它是 Tauri 自己的标记，不可能在某个配置文件里被忘掉；而浏览器（包括探针里的 Node）根本没有它。

**影响**：浏览器包里带上 Tauri 分支，反之亦然——今天构建出的 `dist/` **+7,041 字节（+1.1%）**，这是「一份产物」的价钱，已接受。`api/index.ts` 把面逐名写出而不是 `export *`，并把所选实现标注为「另一份的形状减去 Web 专有的几个助手」，因此「只在某一份实现里存在的名字或签名」是**编译错误**；`ui/scripts/probe-ui-api.mjs` 在两份源码文本上断言同一批名字，并用替身 `fetch` 跑通 HTTP 实现。两条路径上的拒绝都是**字符串**，因为桌面的命令是 `Result<_, String>`，而商店渲染的是 `String(e)`。将来若真需要一份不同的打包（移动外壳、另一种协议），**重开这一条**，而不是给构建分叉。

## 57. Web 客户端自己的名字要声明，而它的门在应用层

**日期**：2026-09-24 ｜ **状态**：已定；随 v0.9 D2b-2 批落地

**决策**：管理程序第二步的两条相关规矩。（a）API 面分两部分：**共有**部分（两种传输都携带的名字）与**声明的 Web 独有**部分（`setApiBase` / `setToken` / `currentToken` / `clearToken` / `verifyToken` / `getHealth` / `getStatus`）。共有部分由两处把关：`api/index.ts` 的 `SharedApi`（取一份实现的形状，另一份必须可赋给它才能编译）与 `ui/scripts/probe-ui-api.mjs`（在两份源码文本上逐名比对）；Web 独有部分则在**这两处**都以显式名单出现，且探针断言「多出来的名字**正好**是那份名单」。（b）登录页是 **`App.tsx` 里的一道门**，不是路由，也不是 `AppShell` 内部的分支：没有 token 就只有 `<Login>`。

**理由**：（a）这些名字**本就不对称**，不应假装对称。桌面端**就是**它的宿主——同进程，因同进程而天然已认证——所以「这个 token 是否被接受」「它存在哪里」「`/v0/status` 说了什么」都不是它的问题。把它们做成共有的，就只能要么伪造出返回「看似合理」结果的桌面命令，要么做一份说谎的接口。声明为 Web 独有能保住共有名单的诚实性；而把名单放在两处（类型与探针），则让「只加在一份实现里」同时被编译器**和**gate 抓住。（b）`AppShell` 正是调 `useAppStore()` 的地方，而商店在挂载时会读十几样东西。把门放在**壳内**就必须先挂载商店，于是那十几个读全部以未认证状态跑一遍，在用户还没敲任何东西之前就把错误状态填满——一个恰好在被介绍给用户的那一刻看起来就是坏的外壳。把门放在外面还让 `AppShell` 在唯一要紧的那点上保持不变（仍不接受 props、仍自己拥有商店），因此桌面端路径一字未动：在桌面端，这道门因其问题不存在而自然满足。

**影响**：token 存于 `sessionStorage`，勾选「记住此设备」时改存 `localStorage`，**绝不进 URL**；被拒的候选不会被装入，因为检查先于装入。`verifyToken` 报四种结果而不是一种，于是「令牌不对」与「服务没应答」对需要修其中之一的人仍是可区分的。状态页是外壳的第三个视图，且只在它真能工作的地方提供（`isTauriRuntime()`）——因为 `/v0/status` 是桌面端从不调用的控制平面端点。将来若又有一个桌面端无法供的页面，它属于同一份声明名单、同一份探针断言，而不是共有名单。

## 58. 繁忙的可执行文件是一个瞬间，不是缺陷——而且只重试这一个错误

**日期**：2026-09-24 ｜ **状态**：已定；随 v0.9 ETXTBSY 修复落地

**决策**：`state.rs` 的四个「这个产物能不能跑」探针——`zig_runs`、`rustc_release`、`rust_runs`、`toolchain_runs`——都经同一个助手 `exec_with_busy_retry` 跑命令，它**只**重试 `std::io::ErrorKind::ExecutableFileBusy`，最多 `EXEC_MAX_ATTEMPTS`（5）次、每次相隔 `EXEC_RETRY_DELAY`（10 毫秒）。其它任何错误都在第一次就返回，而超出预算的 busy 拒绝也会被返回。匹配用 `kind()`，**绝不**用 `raw_os_error() == 26`。

**理由**：本账本记录的第四个「本地绿、CI 红」机制（之前依次是缺系统包、缺环境能力、子进程被 `SIGPIPE` 杀死），也是第一个**根因不在我们自己的句柄生命周期里**的。`ETXTBSY` 是内核在**某个**进程以写方式打开该文件时拒绝 `execve`——而在 Unix 上这包括「已 **fork** 但尚未 **exec**」的进程：`CLOEXEC` 只在 exec 那一刻关闭继承来的描述符，所以在多线程进程里，兄弟线程的一次 `spawn` 可能在本进程已关掉自己的写句柄之后再持有几百微秒。测试二进制正是这样的进程，所以 `a_mock_zig_download_installs_and_adopts_the_compiler` 会在同一份代码上这次红、上次绿：解压写出 fixture 二进制、采用它、然后 exec 它——如果恰好有个兄弟测试在那窗口里 fork，这次 exec 就被拒。用 `kind()` 而非裸 errno，是因为 26 在 Unix 上是 `ETXTBSY`、在 Windows 上是毫不相干的错误码（已实测：Windows 上 `from_raw_os_error(26)` 得 `Uncategorized`），而按裸数字匹配会成为第二个、且是错的真相来源。重试被限在五十毫秒，是因为它要等过的窗口只有几微秒宽；预算的意义是让**瞬时**失败活下来，而不是让**永久**失败看起来健康——这也是其它错误一律不重试的原因。

**影响**：修在**生产代码**而不是测试里：这同样是用户需要的健壮性——索引器或杀软短暂持有刚下载的二进制时会撞到同一件事；它同时保住了探针的承诺（失败仍旧点名工具与错误）。有两件事被考虑并否决：在解压器里加显式 `drop`/`sync_all`（那一刻我们已无句柄可关——写引用属于**另一个**进程，关不掉；而 `sync_all` 回答的是耐久性，是另一个问题），以及不加区分的兜底重试（架构不对或缺库也会白白重试五次）。`#[cfg(unix)]` 测试钉住了错误类型的映射，并在进程内真的复现了这种拒绝；Windows 上没有这个错误可复现。

## 59. PowerShell 不读写任何源文件

**日期**：2026-09-25 ｜ **状态**：已定

**决策**：任何源文件（`.rs` / `.ts` / `.tsx` / `.mjs` / `.js` / `.py` / `.sh` / `.ps1` / `.md` / `.css` / `.json`）都**不用 PowerShell 读写**——改用 `edit` 与 `write` 工具，UTF-8、无 BOM。PowerShell 只用于*命令调用*（`git`、`gh`、`cargo`、`npm`、`node`、`python`）。

**一条例外**：对**不可见字符**（BOM、私用区码点）的**字节级**替换可用 Python 的显式字节模式（`open(rb)` / `open(wb)`）——必须先 hex dump、后 hex dump，并以 `git diff` 复核证明只动了那些字节。`edit` 根本表达不了这类字符：`oldText` 开头的 BOM 在匹配之前就被规整掉了，这条例外就是这么来的。

**理由**：Windows PowerShell 5.1 会把无 BOM 的 UTF-8 文件按 ANSI 代码页（本机是 GBK）读入，再把文本按 UTF-8 写回，一次丢失三样东西：`E2 80 xx`（破折号、省略号）变成 `U+9225` 加一个丢掉的字节，`C2 A7`（`§`）变成 `U+6402`，而 `Set-Content -Encoding utf8` **凭空加了一个 BOM**。本仓库发生过**两次**——v0.7（`sandbox/`，4 处）与 v0.9 的 D2b-1 批（`ui/src/api/`，18 处加 3 个 BOM）——而且**两次都没有任何检查看到**，因为受损字符全都坐在注释里：编译器、打包器、探针、字符串注册表、双语链接扫描**全部通过**。那条「Rust 源文件不用 PowerShell 读写」的规矩本就为此而立，只是当初把语言写窄了一种。

**影响**：本条把原有的「Rust 源文件不用 PowerShell」**扩到所有源文件**，因此各批次提示词的「规矩」节从此用一般化措辞。`scripts/scan-encoding.py --check` 已接进 `scripts/gate.sh`，第三次不可能再落地（而已经发生的两次已清完：五个文件、24 处、零行为变更）。不可见字符的例外记在这里，而不是下次临时发明；它是有边界的：字节进、字节出、两侧 hex dump、`git diff` 作证。

## 60. gate 只对确定的类失败

**日期**：2026-09-25 ｜ **状态**：已定

**决策**：gate 里的静态检查只对**不可能误报**的类失败——就编码扫描而言，即 mojibake（类 E）与 BOM（类 F）。模糊类继续**报告**、永不阻塞：连续三个以上 `?`、只由 `?` 构成的字符串字面量、紧邻 CJK 的 ASCII `?`。

**理由**：`scripts/scan-encoding.py` 的类 C 无法判定——「只由 `?` 构成的字面量」与三元的记号、或合法的 `"?"` 无法区分——它在本仓实测 13 处，**全部误报**（v0.5 第 12 批）。脚本因此被*故意*留在 gate 之外，理由写在它自己的 docstring 里。那个推理成立；变化的是：现在可以只问它那几类确定的形态。会狼来了的守卫会侵蚀 gate——gate 是「绿」的唯一定义（handoff §4）——所以 `--check` 是刻意窄的，而它报出的东西值得立刻处理。

**影响**：`--check` 在 E 或 F 命中时退出 `1`，否则 `0`；其它模式仍恒退 `0` 且照常全部打印。加入当天它报的是 `A 0, B 4, C 16, D 0, E 0, F 0`——那 4 与 16 是模糊类，刻意可见、设计上无害。

## 61. Web 客户端用手写 `fetch` 读事件流

**日期**：2026-09-25 ｜ **状态**：已定；随 v0.9 D2b-3 批落地

**决策**：浏览器用 `fetch` + `ReadableStream` 读取 `GET /v0/events`，而不是 `EventSource`。帧由 `ui/src/lib/sse.ts` 解码——一个纯模块（无 `fetch`、无 DOM），探针直接 import 它——每帧里的 envelope 决定去向：`kind: "event"` 给该 `event` 名字的订阅者，`kind: "gap"` 给单独的 **`onGap`** 回调，`kind: "hello"` 哪儿也不去。传输层记住最后看到的 `id:`，并在下次拨号时作为 `Last-Event-ID` 发回；只要还有人订阅，就按倍延迟重连（1 秒 → 15 秒）。

**理由**：`EventSource` 设不了请求头，而本流用 `Authorization: Bearer` 认证——替代方案（cookie 会话、把 token 放进查询串）正是 `docs/control-plane-events.md` 已列为不推荐的两种，而本服务端两种都没实现。`hello` 不分发，是因为它描述的是**流**（缓冲与过滤器）而不是宿主；而客户端真正需要的那点信息——缓冲伸到哪里——每一帧的 `id` 都带着。`gap` 有自己的回调，而不是被伪装成一个宿主事件，因为它不是：它在说重放缓冲盖不住那个洞，唯一诚实的应对是重读「能重读的东西」。解析器放在 `lib/` 里，与那里其它规则同理：它才是值得测的部分，而纯模块能在 Node 里被探针直接跑，不需要服务器或浏览器。

**影响**：一条流服务所有订阅者——第一个订阅打开、最后一个关掉——所以不再关心的页面不会留下一个开着的请求。连接断开不作为错误暴露（页面继续显示上次读到的内容），重拨是退避而不是空转。gap **无法**恢复的东西写在处理它的地方：流式聊天文本与串口字节只曾以事件形式到达，没有任何端点会重放它们。`api/index.ts` 的 `Omit` 名单与 `probe-ui-api.mjs` 都点名 Web 客户端自己的导出（`onGap` 本期加入），因此两份名单不会漂移。

## 62. 只读看板仍然可以写显示偏好

**日期**：2026-09-25 ｜ **状态**：已定；随 v0.9 D2b-4a 批落地

**决策**：Web 客户端「只看不动」的规矩**只有两个**例外——主题与语言。它们与浏览器用的其它一切一样走 HTTP（`api/http.ts` 里的 `POST /v0/settings/theme` 与 `/v0/settings/language`），且外观页**刻意不**包 `DesktopOnly`，而客户端里其它每一个控制都包。

## 63. Web 看板把节点信息做成同一个页里的子 tab，而不是更多的 view

**日期**：2026-09-25 ｜ **状态**：已定；随 v0.9 D2b-4b 批落地

**决策**：浏览器不为每类信息长出一个 view。它的节点页变成一页三 tab——**Status / Executors / Sandboxes**——作为 `StatusPanel` 内部的本地 `useState`，而 `StatusPanel` 现在是 `panels/node/` 之上的容器。`AppShell` 的 view 联合仍是三态（`main` / `settings` / `status`）。

**理由**：三条，每条避开的是不同性质的代价。（a）手机上一个 tab 行是一次手势，而再套一层导航是两次；节点的状态、它的队伍与它的沙箱是**同一个**主题的三个面，让人“先离开这一页”才能看到第二个面，是为了文件布局而导航。（b）view 是**全局**状态，由外壳为所有面板持有；tab 是**局部**状态，对外不可见。把这三样放在 tab 之后，新增一类节点信息不会让外壳的状态增长。（c）那一行本身就是设置页的 `.settings-tabs` / `.tab-btn`，所以「加一个 tab」零新增样式；而「加一个 view」意味着顶栏一个按钮、外壳渲染里一个分支，还要决定 Escape 键该怎么办。

**影响**：将来新的节点维度信息（另一种资源、一个队列）扩的是 tab 行而不是 view 联合；`probe-ui-node-panel.mjs` 把这个承诺的两半都钉住：页面有三个 tab、且外壳的联合未变。新 tab 需要的四个读接口在适配层是**共有**名字（桌面端一直就有这些命令），所以没有为此新增任何 Web 独有名字，探针的名单断言也未动。

## 65. 迁移 relay 也像其它 bind 一样以租约持有它的端口

**日期**：2026-09-25 ｜ **状态**：已定；扩展 §35

**决策**：`MigrationRelay::bind_local_with_timeout` 现在会把它绑定的回环端口在进程级登记表里预留（`reserve`），并把随之产生的 `PortLease` 作为自己的 listener 持有，于是这个号一直保留到 relay 被 drop。在此之前，登记表只由 `lease_local_ports` / `lease_local_port` 供给。

**理由**：§35 的契约针对的是**活着的**租约——同时存在的两个租约绝不带同一个号——而 relay 曾是唯一不参与的 bind。OS 本来就不会把**已绑定**的端口再分出去，所以实际缺口很小：缺的是这条规则的弱半边，即本进程在放手的那一刻也不会把这个号交给第二个持有者。修法留在内部：租约持有 listener，`addr()` 未变，构造函数签名未变，因此公开 API 一字未动。

**影响**：relay 活着时它的端口出现在 `leased_ports()` 里，被 drop 时离开（新增一个单元测试钉住）；耗尽路径报 `SandboxError::PortLease`，与 `lease_local_ports` 同一形状。`send_file_to` 不受影响——它连接的是一个已在监听的同伴，从不 bind。

## 66. 桌面端先于任何 token 被回答

**日期**：2026-09-25 ｜ **状态**：已定；随 v0.9.1 修复落地

**决策**：前门**先**问「这是哪个运行时」，**再**问 token。桌面端直接短路到外壳；token 门是一个桌面端永不进入的独立组件。

**理由**：两个运行时对「有没有 token」的答案不同——Web 客户端有一个非给不可的 token，而桌面端既没有可持有的 token，也没有可用来校验的 `/v0/health`，因为它的宿主就在同一个进程里。v0.9.0 发出的那道门根本没问这个问题，于是每个桌面用户都被拦在一个怎么输都过不去的登录页前：桌面端完全不可用。**顺序本身就是修法**——放在 token 读取之后的短路仍然会读 token，而把两件事放在同一个组件里仍然会画出登录页。

**影响**：`SharedApi` 与它的 `Omit` 名单未动（修法在 `App` 内部），因此没有任何名字变成 Web 独有，适配层的形状也没有移动。`probe-ui-login.mjs` 把顺序钉住——桌面端在任何 token 之前就被放行、登录页只在 Web 侧——而这正是 Node 探针能看见的那一半：探针跑在没有 `window` 的环境里，所以每个探针走的都是 Web 分支，桌面分支靠真机验证。

## 67. 设置页可以显示 token，但绝不能凭空造一个

**日期**：2026-09-25 ｜ **状态**：已定；随 v0.9.9 网络批第 2 批落地

**决策**：桌面端的网络 tab 可以显示局域网 token，经由一个 shell 本地命令（`read_lan_token`）——它**只读 `<data-dir>/token`，从不创建**。打开一个设置页绝不能让一份凭据凭空出现；造 token 始终是那个真正启动的服务端的事。

**理由**：token 必须能到达人手上——同网段的手机需要有人把 token 给它——而在本批之前唯一的读取者是 `riscdom-server`，它在文件缺失时会**生成**它。一个复用 `load_or_create` 的命令，会仅仅因为有人看了一眼设置页就写出一份 token：那是凭据作为「导航的副作用」出现。读文件并在缺失时干净地拒绝（`no token yet: …`），把创建这件事留在它该在的地方。

**影响**：值只交给调用方，不去别处——不进日志、不落盘、不过网——页面也只在按钮被按下时显示它。文件名取自 `server` 自己的常量（`TOKEN_FILE`）；`probe-ui-network-tab.mjs` 断言两者一致，因此那边改名不会让这里静默读错文件。`settings.json` 自己的规矩也仍成立：属于**别人节点的 token** 本批不存（字段存在但保持 `None`）。

## 68. 桌面端服务的看板就是它跑着的那个节点，而前端随包分发

**日期**：2026-09-25 ｜ **状态**：已定；随 v0.9.9 网络批第 3 批落地

**决策**：桌面端的局域网看板，是**在应用自己的 `Arc<AppState>` 之上**启动的内嵌控制平面。shell 以 `Arc` 管理 state，而 `host-tauri` 的 68 个命令接受同一个句柄。构建好的前端作为 Tauri **resource** 随包分发（`{"../dist": "dist"}`），由同一个 helper 解析（先试 resource 目录、再试源码树）。任何网络设置的改动都会重绑——先停再起——而 `RunEvent::ExitRequested` 会 abort 掉 server。

**理由**：另一条路——给 server 一个**克隆体**——被拒，而拒的理由值得写下来：`AppState` 把 VM 槽、settings 缓存与 run 记账都留在**内存**里，所以克隆体不是同一个节点。一台机器上能开出第二个 QEMU 的看板，比没有看板更坏，而任何测试都拦不住它。68 个签名就是让这个错误变不可能付出的代价；它们是机械的（函数体未动，因为 `Arc<AppState>` 会自动 deref 到 `AppState`），且 `probe-ui-lan.mjs` 会数它们。resource 之所以存在，是因为 `frontendDist` 把前端**编进二进制**、磁盘上不留任何可服务的目录；回落之所以存在，是因为 `tauri dev` 根本没有 resource bundle。

**影响**：一个 `Arc`、一个节点，窗口与手机看到的是同一个。除非打开 `lan_allow_lan`，只绑回环——那正是那个开关带警示的原因。手机要输的 token，就是 server 在 `<data-dir>/token` 里生成的那一个——也正是上一批那条只读命令读的同一个文件——因此凭据没有任何一部分挪进 `settings.json`。

## 69. 构建产物住在稳定的父目录下

**日期**：2026-09-25 ｜ **状态**：已定；随 v0.9.9 3/N-fix2 批落地

**决策**：前端构建进 `ui/dist/app/`，父目录 `ui/dist/` 里放**一个被跟踪的文件**（`.gitkeep`），它唯一的工作是让该目录在全新 checkout 上存在——因为 `tauri-build` 用 `Path::exists()` 校验 `bundle.resources` 的路径。`emptyOutDir` 保留默认：它清的是 `app/`，永远不会碰父目录。

**理由**：3/N 把 `"resources": {"../dist": "dist"}` 写进配置，于是把一个**构建产物变成了编译期前置条件**：在全新 checkout（CI）上 `ui/dist` 不存在，`cargo clippy ui/src-tauri` 就以 `resource path '../dist' doesn't exist` 失败。这是本仓账本里**第五个**「本地绿、CI 红」机制——前四个是缺系统包、缺环境能力、SIGPIPE 与 `ETXTBSY`——而它与前四个有一处值得记下的不同：**它由我们自己的变更引入，而不是环境**。最直觉的修法——在 `ui/dist` 里放被跟踪的 `.gitkeep`——已被尝试并证伪：Vite 的 `emptyOutDir` 每次构建都会删掉它，工作树会永远脏着（3/N-fix 批就停在这道安全阀上）。关掉 `emptyOutDir` 也被否决——那样本地 `tauri build` 会把每一份陈旧的 hash 资产都打进安装包。稳定父目录 + 被清空的子目录，一次满足全部三条。

**影响**：`--web-root`、`frontendDist` 与 `resolve_web_root` 的两个分支都指 `ui/dist/app`，`docs/manual-acceptance.md` 的局域网配方随之跟上。B-2 批当时记载的性质——`ui/dist` **不是** `cargo check` / `clippy` 的前置条件——恢复成立，已在有与没有 `dist/app/index.html` 两种情形下实测。今后的规矩：构建工具要求「编译期必须存在」的路径，应当放在**稳定的父目录**上，生成的内容放在该工具可以清空的子目录里。

## 70. 内网节点的凭据住在 OS 钥匙串里，不在设置文件里

**日期**：2026-09-25 ｜ **状态**：已定；随 v0.9.9「出」批落地

**决策**：桌面端连内网服务器时，**地址**存 `settings.json`（`network.remote_url`，一个偏好），**令牌**存 OS 钥匙串，账户名 `remote-token:<host>`（`host_core::keyring::user_for_remote`）。第 2 批留下的占位字段 `NetworkSettings.remote_token` **删除**，而不是填上。

**理由**：`settings.json` 自己的第一句话就是「这里只放非机密偏好」——v0.4 把 API key 送进钥匙串以来一直如此。远端 token 是本应用接触过的最强的凭据：它是另一台机器的 owner token，而那个文件是纯 JSON，它所在的目录正是备份、支持包和截图会顺手收走的东西。钥匙串本来就是 provider key 的家，形状已经存在；账户名**按 host** 命名，于是连第二台节点不会静默覆盖第一台的 token。

**影响**：JS 读不到钥匙串，所以三个壳命令（`save_remote_token`、`read_remote_token`、`clear_remote_token`）是那座桥，而它们**在任何模式下都作用于本机**——远端窗口想出来时，要动手的是这台机器。`read_remote_token` 与 `read_lan_token` 一样只读：这里不会凭空造出凭据。**继承自 `keyring.rs` 的注意点**：钥匙串拒绝时会退化为内存存储，所以「记住」的 token 可能在重启后不在；调用方拿到的是钥匙串的回答，而不是期望。

## 71. host 模式是一个值，而八个接线命令无视它

**日期**：2026-09-25 ｜ **状态**：已定；随 v0.9.9「出」批落地

**决策**：`api/index.ts` 把实现存在**变量**里（`let current: SharedApi`），由新的 `setImpl(mode, url)` 在启动时定一次；每个数据面导出都是经由它的一行转发。**八个名字例外，永远指向本机**：`getNetwork`、`setNetwork`、`readLanToken`、`lanStatus`、`saveRemoteToken`、`readRemoteToken`、`clearRemoteToken`、`restartApp`。第二个谓词与第一个并列：`isTauriRuntime()`（我跑在什么里面）与 `isLocalHost()`（屏幕上的节点是不是本进程自己的）。

**理由**：4/N 已经清楚，加载时的 `const impl` 答不了「跟哪个 host 说话」——那是**配置**事实，不是环境事实。转发保住了 `const` 买来的性质：一个 `SharedApi` 类型在编译期把两个实现互相对钉，而某个实现缺某个名字时，它的转发根本编译不过（`probe-ui-remote.mjs` 数出 68 个转发，其中 60 个走模式）。真正承重的是那条例外：在远端模式下，被转发的 `getNetwork` 会去要求**远端服务器**改自己的接线——那正是没有、也永远不会有端点的东西——于是服务器不可达的窗口就再也回不来。给节点接线是本地行为；这就是为什么只有这八个名字无视模式。

**影响**：模式在**外壳挂载之前**定好（`App.tsx`），所以 store 现有的挂载拉取**就是**那次重读，会话中途无需重拉；改模式是一次**重启**，这也是 `restart_app` 存在的原因。凡是本意是 `isLocalHost()` 的地方，界面都不能再问 `isTauriRuntime()`：门、设置页的 tab 表和顶栏徽标；`DesktopOnly` / `WebOnly` 刻意保持旧义（「这个构建里有没有 Tauri 运行时」）。远端窗口走 HTTP，因此和浏览器一样是只读的——远端服务器自己那份控制实现也是一句话拒绝。

## 72. 一个节点拥有若干沙箱实例，而「切换」作用的是它自己那一个

**日期**：2026-09-27 ｜ **状态**：已定；随 v1.0 M2a-1（实例表）批落地

**决策**：`AppState` 的单一 VM 槽变成一张**实例表**（`instances: Mutex<HashMap<InstanceId, SandboxInstance>>`）加一个 `current_instance` 指针，而原先属于节点的状态——VM 槽、串口广播列表、串口累积文本与 VM 起始时刻——变成**每实例一份**。节点在构造时只创建一个实例：**它自己的那个**，永不删除，也正是「切换」与一次普通运行作用的对象。派生一个实例（`spawn_instance`）会在它自己的槽里起第二台 VM，且**不改**节点正在跑的东西。`InstanceId` 是 `<device>-<pid>-<seq>`（`agent::identity`），device 可设（默认 `local`；给节点命名是连接层的事，纲领 §4），而**一个计数器同时服务 agent 与实例**，于是两个空间永远不会铸出同一个字符串。三段不是路径语法：从右往左读（`rsplitn(3, '-')`），因为 device 名字里可能带 `-`。

**理由**：v0.9.9 的模型是一个节点一台 VM —— 槽、串口缓冲、起始时刻都是单例，它们让第二个客机**不可能**，而不只是不太可能（决策 §68 保留节点自己的 `Arc<AppState>` 正是为此）。而最省的正确改法已经建成了一半：`AgentLoop::with_vm` 收的就是 `Arc<Mutex<Option<VM>>>`，所以一个自带槽的实例可以**原样**交给 loop。节点自己的那个实例存在，是为了让任何 M2a 之前的路径都不必学会新含义 —— 切换仍然是在它里面换掉 VM，正如它当年换掉槽里的 VM —— 也是为了让「当前实例是谁」永远有答案（`current_instance` 会回落到它）。

**影响**：`vm_slot()` 现在是一个**方法**（当前实例的槽），因为字段无法给每实例的 `Arc` 起别名；`spawn_instance` 是派生路径、`stop_instance` 是回收路径（节点自己的那个实例只是被清空，从不被移除）。快照挪到 `snapshots/<device>/<instance_id>` —— 每实例一个目录 —— 而两种更旧的布局（按 agent、以及共享根）仍然**可读**，这正是从 v0.9.9 升级上来的节点需要的。端口从来不是障碍：`HELD_PORTS` 为每台 VM 租一对，所以同进程两个客机不会抢到对方的（决策 §65 的形状仍然成立）。审计链一字未动：实例身份走 `detail`，与 `agent_id` 当年作为一个「刻意不进哈希公式」的字段加进来是同一种做法。把这些接到外面的端点是 M2a-2，`Task.instance` 是 M2a-3；在那之前，这张表只能从宿主内部够到。

## 73. 实例路由是路径参数路由，而成员路径要同时带两半

**日期**：2026-09-27 ｜ **状态**：已定；随 v1.0 M2a-2 批落地

**决策**：实例模型的四条沙箱路由是**路径参数路由**，不是 `ROUTES` 的行 —— 表里比对的是字面路径，而 `{name}` 不是 —— 因此它们由提取器解析（集合与成员走 `sandbox_instance_path_from`，定义能力走 `sandbox_capabilities_from`）。`Resolution::Query` 的 `path_param` 从 `Option` 变成 **`Vec<(&'static str, String)>`**：成员路由要同时携带 `name` 与 `instance_id`，因为回收实例的处理器必须核对这个 id 属于路径点名的那个定义。`GET /v0/capabilities` 是本批新增的那一**行**—— 一条字面路径 —— 它回答**调用者**能做什么（`status.read`），与 `/v0/sandboxes/{name}/capabilities` 的「这个定义能做什么」（`sandbox.read`）是**刻意的两个不同问题**，不合并。

**理由**：派生出实例不是收养一个实例（决策 §72），所以创建端点既不占用切换「一次一个」的槽，也不受飞行中 run 的检查 —— 第二台客机不是一次接管 —— 而它的回答也如实如此：`201` 带新 id，而节点的 `current_sandbox` 原地不动。保留名表**不加长**：`instances` 与 `capabilities` 是第二段，所以定义叫这两个名字不会遮住任何东西；而 `requests` 是真正的第一段路由，仍然保留。一个 `Option` 参数装不下成员路径的两半，而把两半拼成一个字符串，等于让处理器重新解析路由已经知道的东西。

**影响**：`docs/control-plane-api.md` §5.1 为 **33**；工具 schema 的表多了五行、定义多了五条，于是 `patterns.len()` 的硬断言从 4 改为 **8**，`scripts/check-tool-schema.mjs` 的 `NAMED_PATTERN_ROUTES` 映射也要跟着改（那个检查器按机械规则推导名字，所以一个动词式的路径参数名要么在映射里，要么就是失败）。五个工具名是 `instance_list`、`instance_create`、`instance_delete`、`sandbox_capabilities` 与 `capabilities`。失败映射：不存在的定义 `404 cause "name"`；不能跑的定义 `503`（与切换对同一条件给的一致）；启动失败 `500 cause "sandbox_start_failed"`；不属于该定义的 id 是 `404 cause "instance"`。浏览器侧的 `SandboxInstanceView` 由 node-panel 探针逐字段核对宿主的 `InstanceView`；而把这些实例派给某个 run 的 `Task.instance` 随 M2a-3 到来。

## 74. 实例压过 sandbox 声明，而这一对要被校验

**日期**：2026-09-27 ｜ **状态**：已定；随 v1.0 M2a-3 批落地

**决策**：`Task` 在 `sandbox: Option<String>` 旁新增 `instance: Option<InstanceId>`（两个都带 `#[serde(default)]`），而点名了实例的运行就跑在**那个**实例的 VM 槽上 —— 更细一层的声明说了算。这一对**在动任何东西之前严格校验**：本节点不拥有的 id → `InstanceNotFound` → `404 cause "instance"`；而实例的定义不是任务同时点名的那个 sandbox → `InstanceConflict` → `409 cause "instance"`。规则住在 `task_instance_conflict` —— 与 F2d 的 `task_sandbox_conflict` 并排的纯函数 —— 所以不需要活实例就能钉住。`run_agent_for` 把 id 作为第四个参数，并由 `task_instance` 解析它；**`AgentLoop::with_vm` 一字未改** —— 它本来就收一个槽。

**理由**：两个声明不是二选一，而是同一句话的两层（*哪个定义*，以及*由它造出的哪个正在跑的东西*）；一个只认一个、静默丢掉另一个的运行，就是在无声地违背调用方要的东西。静默回退正是 F2d 对 sandbox 名字拒绝过的东西，所以实例拿到同一种待遇。路由形状是从现有代码长出来的，不是新抽象：`AgentHandle::run` 本来就收到整个 `Task`，`HostAgentHandle` 本来就持着能回答的 `Arc<AppState>`（它的表），而 loop 本来就收 `Arc<Mutex<Option<VM>>>` —— 于是「哪个实例」在 `run_agent_for` 里定下，它上面的东西形状不变。id 在**执行者跑的地方**被校验，绝不由调度器校验：stdio 执行者的实例属于**它自己**的表。

**影响**：`/v0/agent/run` 与 `/v0/tasks` 接受 `instance`（Tauri 的 `run_agent` 命令多了一个可选参数；前端 wrapper 也接上，而调用点一处未改）；id 原样走 stdio 协议，worker 拿它对自己的节点校验。agent 的 `start_vm` 工具把 `.mig` 写进**实例的**目录（`ToolContext.snapshot_dir`，由宿主经 `AgentLoop::set_snapshot_dir` 设），M2a-1 记下的那处不一致就此闭环。`run.start` 的 detail 现在带 `sandbox` 与 `instance`（一次运行两者都没有时为 `null`），由新的 `run_start_detail_with` 写入；更老的 detail 仍可解析，因为 `parse_run_start` 用 `get` 取每个键 —— 而 **`detail` 属于每条事件自己的哈希**，所以这两个键动的是**新**事件的哈希、旧的任何一行都不动；不动的是哈希**公式**。

## 75. LLM 配置按执行者落盘，而设置文件有了自己的版本号

**日期**：2026-09-27 ｜ **状态**：已定；随 v1.0 M2b-1 批落地

**决策**：一套模型配置里非机密的那一半（provider、endpoint、model）持久化在 `settings.json` 的 `llm_configs` 下，按**执行者 id** 归档 —— 本机用它自己的**设备名**，worker 用 `settings.executors[].label` —— 而 key 仍住在 OS 钥匙串，名为 `llm-api-key:<executor>:<provider>`。`SETTINGS_VERSION` 变为 **2**：`settings.json` 是第一个用 `docs/api-compatibility.md` §6 迁移规则的格式 —— 读文档声明的版本（缺失 = 最老格式，不是数字 = 坏文件），把更新的文件以 `data_too_new` 拒绝（不应用、不写入），把更旧的迁到当前格式，**只在迁移时**把迁移前的字节留作 `settings.json.bak`，把迁完的文档写回，并让拒绝**可见**（一条审计事件加 `AppState::settings_problem`）。

**理由**：一个每次重启都忘了自己配了哪个模型的节点，实际上是把配置存在环境变量里 —— 而一台机器上有好几个执行者时，「用哪个模型」是**每个执行者**的事实，不是每个节点的事实。key 留在钥匙串，因为那条规矩自 v0.4 就成立，而这个文件正是人们会拷贝、备份、粘进 issue 的那一个。本机执行者的键用**设备名**而不是它的 `AgentId`：AgentId 带 pid，用它做键的条目在它为之存在的那次重启之后就再也读不到。版本号上移是向前看的 —— v0.9.9 没有版本检查，拒不了任何东西 —— 它的价值在于：从此每个读者都有一个可推理的格式，而本构建会拒绝一个它不认识的格式，而不是只读它认得的那一半。

**影响**：`llm_configs` 形状上是增量的，但格式是 v2；v1 文件迁成一张空表，因为它**本来**就不带任何 LLM 配置（无从猜起）。`LlmConfigStatus` 在 `persisted` 旁新增 `config_persisted`，而前者的含义不变 —— 界面把它读作「你的 key 记住了」。钥匙串的读取把 v0.9.9 条目向前迁、**并把旧条目留在原地**，于是不需要重输任何 key，回退到旧构建也仍找得到；`clear_llm_config` 只删新名。端点的执行者维度、per-executor 会话切分与界面属 M2b-2/M2b-3：本批不落任何端点、会话或 UI 的变更。

## 76. 会话行写下自己的执行者，而老行保持未命名

**日期**：2026-09-27 ｜ **状态**：已定；随 v1.0 M2b-2 批落地

**决策**：`sessions` 新增 **`executor_id`** 列（迁移时幂等加上），而会话库的 schema 版本住在 SQLite 自己的 **`PRAGMA user_version`** —— 也就是 JSON 格式首字段标记的「随文件走」等价物。早于该列的文件在**打开时**迁移（迁移前字节留作 `sessions.db.bak`，且只有迁移会写它），而来自**更新**构建的文件以 `data_too_new` 被拒，而不是半读。现在每次会话调用都点名执行者：七个端点接受可选 `executor`，缺省本节点；`current_session_id` 是按执行者分表。早于该列的行保持 **`NULL`**，而查询把 `NULL` 读作**本节点自己的**；新行总是写自己的执行者，而 `rename` 绝不认领老行。

**理由**：把 `local` 写进老行，会让它们依赖于一个节点随时可以改掉的名字 —— 它给自己改名的那天，它自己的历史会从它自己的列表里消失，而那是静默的数据丢失。`NULL`（「没有点名执行者」）与「本节点自己」是两个不同的事实，只是今天碰巧后果相同；把它们分开，意味着一个还没有设备名的节点也仍然读得到自己的历史。SQLite 的 `user_version` 是不需要自建表、且先于一切被读出的版本标记，所以 `docs/api-compatibility.md` 那条规矩现在写的是 SQLite 实际提供的东西，而不再描述一张没人建过的元数据表。

**影响**：`/v0/sessions`、`/v0/sessions/current` 与五个会话控制接受 `executor?`；Tauri 命令传本节点自己，签名不变，所以本批不动 UI（选择器属 M2b-3）。`SessionMeta` 带 `executor_id` —— 未命名的行为 `null`，浏览器类型标为 `string | null`。`open_session` 改为按 **id** 直查、不再扫全表，`clear_all` 只清一个执行者（本节点那一个连未命名行一并清），而 `ensure_session` 会**修复陈旧指针** —— 另起一个新会话。`session_messages` 一字未动：一条消息只属于一个会话，join 已经说清楚了。

## 77. executor 是一个可选参数，而 `*` 是它唯一的通配

**日期**：2026-09-27 ｜ **状态**：已定；随 v1.0 M2b-3a 批落地

**决策**：LLM 与会话端点所扮演的执行者就是**一个可选参数**（`executor`），缺省即**本节点自己** —— 从不做第二个端点，也不做布尔开关。唯一的通配拼在它的**值**上：`/v0/sessions?executor=*` 用一张列表答出所有执行者的会话。而那些答案只关于**一个**执行者的端点，以 `400 bad_request`、`cause: "executor"` 拒绝 `*`：模型配置属于某一个执行者，「当前会话」也一样。

**理由**：这里只有一根轴 —— *我在说哪个执行者* —— 所以第二种拼法（`?all=true`）或第二条路由（`/v0/sessions/all`）就是同一根轴的第二个名字，还要自带一行端点表和一份要跟住的计数。把通配拼成**值**，端点表就不动：它是整个面上的一个记号，因此文档里也只需一句话。拒绝是同一条规矩反过来读：没有复数答案的问题不会得到通配的答案，它把调用方的参数名退回去。合并列表的 `limit` 是**行数**而不是「每执行者各几行」，因为存储做的就是一条语句加一个 `LIMIT` —— 「每执行者 N 行」要 N 次查询，而且会让这个数字随在册执行者数改变含义。

**影响**：`/v0/llm/config`、`/v0/llm/readiness`、`/v0/llm/stored-key`、三个 LLM 控制与五个会话控制接受 `executor?`；`/v0/sessions` 另认得 `*`。端点表计数（§5.1 的 33 / §5.2 的 36）不动，`every_query_endpoint_answers` 的 `cases.len() == 33` 也不动。Tauri 命令把 `executor` 带成可选参数，因此什么都不传的客户端语义不变；真正用它的是 M2b-3b 的 UI 选择器。

## 78. `local` 与 `*` 是保留的执行者 id

**日期**：2026-09-27 ｜ **状态**：已定；随 v1.0 M2b-3a 批落地

**决策**：执行者的 label 不得为 `"local"`（本节点自己的 id，直到节点给自己改名）或 `"*"`（会话通配）。带这两者的 settings 文件仍然**加载成功**，而那一项被**跳过**，并记一条 `host.executor.reserved` 审计事件。

**理由**：执行者 id 是一个键空间。它同时是 `settings.json` 里 `llm_configs` 的条目键、钥匙串账号的中间一词、以及 `executor` 参数的值 —— 所以一个叫 `local` 的 worker 会与本节点自己共用模型配置，而一个叫 `*` 的 worker 会跟通配本身撞上。选择「跳过」而非「拒绝」与 v1.0 M2b-1 对更新版设置文件的读法一致：让失败**可见**（这里一条审计事件，那里 `settings_problem`），而不是吞掉它，也不是让一个手改过的文件直接把程序搞死。文件保持人写下的字节不动。

## 79. 参考调度员以骨架形式发布，而它的边界是「写出来」而不是「修掉」

**日期**：2026-09-27 ｜ **状态**：已定；随 v1.0 M2c-1 批落地

**决策**：M 的参考实现落在 `examples/python/supervisor.py`，形态是**骨架**：那个循环（一次状态快照 → 决策 → 行动 → 报账）、动作表、一个用 `Last-Event-ID` 续订的事件读取器，以及一个返回 `None` 的 `decide()`。它 **import** `dispatch.py` —— 传输、`read_token`、错误分类 —— 而不自带第二份线格式。侦察找到的**五条边界**是**写出来**（文件 docstring、`examples/python/README.md` 与 handoff），**不是修掉**：M 在链上没有自己的身份、沙箱请求的决定不写链、实例表与待批槽住在内存里、审计读取没有窗口也没有分页、五个能力名只是词汇。保守行为是循环的**起点**：读失败会在写下任何东西之前终止这一轮，所以「安全的决定」与「默认的决定」是同一个。

**理由**：决策层是需要模型、提示词与使用者策略的那一半；把它一起发出去，示例就变成了产品，而它的行为就变成了别人的主张。能**离线自证**的是它周围的一切，所以本批证的就是那些 —— 用 E3 批已经立起来的假节点手法。选择 import 而不是复制是同一层思路往下一层（线格式只写一遍），代价只是多出一条值得记下的发现：本项目这个解释器跑在 `sys.flags.safe_path` 打开的状态下，所以脚本自己的目录**不在** `sys.path` 上，兄弟 import 需要两行说明此事。把边界写出来而不是修掉，让评审保持诚实：每一条都是今天这个表面的性质（token 客户端是谁、什么是耐久的、审计读取能表达什么），而每一条的修都另有归属批次 —— 在这里点名，正是为了不让它们日后作为意外被重新发现。

**影响**：`examples/python/` 多一个文件与一节双语 README；客户指南 §8 在 `dispatch.py` 旁边指向它；gate 多一个 Python 步骤（15 → 16），`have_python` 守卫会让它在没有解释器的机器上退化成一条打印出来的 skip。`dispatch.py` **一字未动** —— 只 import，从不编辑 —— 而 `docs/tool-schema-control-plane.md` 仍然是 M 的工具清单，所以不需要第三份 schema 文档（也不需要动 `check-tool-schema.mjs`）。

## 80. M 的决策层是一个有上限的工具循环，而它的模型不是节点的模型

**日期**：2026-09-27 ｜ **状态**：已定；随 v1.0 M2c-2 批落地

**决策**：参考调度员通过一个**有上限的工具调用循环**（`LLMDecider`）决策：节点的状态（一次快照）作为第一条 user 消息；控制平面自己的工具 schema 在启动时从 `docs/tool-schema-control-plane.md` **读出**，并过滤成调度员应有的**十八个**工具；一轮里最多 `--max-rounds` 次模型调用；而模型发出的每一次工具调用都在**循环内被执行**并回喂。那个模型是 M 自己的 —— `--llm-base-url`、`--llm-model`、`--llm-api-key-file` 或 `$RISCDOM_LLM_API_KEY` —— 从不取自节点的 `llm_configs`。不配模型时决策层就是 `OfflineDecider`：什么都不决定，那是默认而不是错误路径。`agent_run` 与 `events` 被**点名**排除；从未提供过的工具不会被执行；模型失败或不可达会以「不再发生任何控制请求」结束这一轮。

**理由**：工具 schema 已经存在，gate 已经在守着它与服务端路由表同步，所以**读**它就是少养一份真话 —— 而一份文档满足不了的白名单是**启动报错**，不是一条安静的弱化版调度员。那两条点名排除就是客户指南自己的铁律，写在代码所在的地方：`agent_run` 是执行者的循环（一个会跑回合的调度员就是第二个执行者），事件流是上下文而不是一个永不返回的请求。M 的模型与节点的模型是两份不同的活 —— 决定**哪个**任务 vs 跑**一个** —— 所以 M 带自己的地址、密钥与错误类型（`LLMTransportError` / `LLMApiError`，与控制平面的分开）：把它们混在一起会让调度员的故障看起来像节点的故障。循环必须有天花板，否则它就是一个可以被模型说服、永远跑下去的进程。而**策略刻意留在外面**：提示词是骨架 —— 角色、状态、边界、约束 —— 规则是你自己的，这正是它作为参考实现而不是一份主张的原因。

**影响**：`supervisor.py` 长出客户端、循环，以及 self-test 里一个按脚本作答的**假模型**（现在 45 个断言点），于是决策层可以离线自证；README 多出工具清单与「刻意不给什么」；客户指南 §8 写成 M **用**什么决策，而不再说它是桩；gate 的步骤数不动（16 —— 同样两条 Python 步骤）。真机那一半：对着一个活的 `riscdom-server`，M 的派发到达了真实 worker（它写了一个裸机 guest 并在 QEMU 里启动）、`instance_create` 与 `instance_delete` 派生并回收了一个真实实例、模型死掉时链**一字未变**（前后均 53 行）、而重启后的 M 从节点重建了上下文 —— 每一步的证据都在审计链上。

## 81. 每个 AI 监督者做的动作都留下一行、并写下它自己的名字

**日期**：2026-09-27 ｜ **状态**：已定；随 v1.0 缺口 2/N 批落地

**决策**：客户端可以用可选的 **`X-RiscDom-Agent`** header 给自己命名。带上它时，服务该请求的 `Actor` 以那个名字作为 `agent_id`、以 [`ActorKind::Supervisor`] 作为 kind —— 而**调度员能做的七个动作**会写下指名它的链行：`m.sandbox.spawn`、`m.sandbox.reap`、`m.sandbox.switch`、`m.request.ask`、`m.request.approve`、`m.request.reject`、`m.task.dispatch`。三个原本无帧的动作也各获得一帧，所以在 `/v0/events` 上的观察者能看到它们；而一次 **switch** 保留它唯一的 `sandbox:switch` 帧（F2b-2 的「每次尝试一帧，不论成败」—— 给同一次尝试再来一帧就是多一样要计数的东西），一次决定保留 `sandbox:request`，本批为这两个动作加的是**行**。身份走在 `AuditEvent.agent_id` —— 那个刻意**不在哈希公式里**的字段 —— 所以归因到位的代价是零：没有一行历史被移动。不带 header 就是凭据自己的身份（`operator`），也就是本批之前每个版本假定的那样；而四十多个**节点**事件（`host.theme.set` 等）仍走 `emit_host`、仍写节点 —— 主题变更跟调用者 header 毫无关系。

**理由**：M2c 的真机运行显示审计链对 **AI 的决定是盲的**：M 能做的七个动作里，`spawn`/`reap` 有行（但归为 `host`），而 switch、ask、approve、reject **一行都没有** —— 一次切换发了帧、什么都没记；一次决定只耐久在内存里那张队列上。`docs/roadmap-v1.0.md` §9 假定的是反面（「M 的状态住在 M 外面」），而 §36 自己的文字说一次决定「只改这条记录、别的什么都不做」—— 对，而这正是为什么那条记录必须住在能活过重启的地方。两个更小的决定随之而定：名字**有上限、要校验**（128 字符、不得含控制字符），而坏值**被忽略而不是被拒绝**，因为一个坏名字不是一次坏请求；以及 `.remote` 名字保留它们的本地半边（`auth.rs` 里的不变式），跨节点契约（纲领 §5）才有落地之处。

**影响**：`ReqMeta` 多出 `caller`；`Actor::named_caller` 是把它变成身份的唯一处；`AppState::emit_m_action` 是写这七行的唯一处；`host-core/src/events.rs` 的词汇从 **17 → 20**（新增 `m:request:ask`、`m:request:reject`、`m:task:dispatch`，而 M2a-1 声明过、从未发射的三个现在真的会发）。`docs/control-plane-events.md` §3 的表被拉回与代码同步 —— 它此前只列 14 而代码定义 17，这个漂移在本批一并收掉。API 文档 §3 记下这个 header。表面其余部分一律不动：**没有新路由、没有新 capability、哈希公式/触发器/历史行一个字不改**，而一条包含这些新行的链仍然验证为完好。

## 82. 实例的过去从链推导，不存在文件里

**日期**：2026-09-27 ｜ **状态**：已定；随 v1.0 缺口 3/N 批落地

**决策**：实例表**不**持久化。`SandboxInstance.vm_slot` 是活进程句柄 —— 一台 VM，不是数据 —— 而重启之后 guest 本来也就没了，所以「把表存起来」会是一个声称拥有事实上并不存在的 VM 的文件。取而代之，一个定义**曾经有过**的东西是被**推导**出来的：`GET /v0/sandboxes/{name}/instances/history` 把链上的 `m.sandbox.spawn` 与 `m.sandbox.reap` 行折成一张列表（`instance_id`、`definition`、`spawned_at_ms`、`reaped_at_ms`、`running`）—— 与 `audit::derive_runs_from` 重建 run 索引完全同一个手法。`running` 从活表读出（「**现在**在跑吗」），所以重启后每条记录都是 `false`；节点自己的实例以 `null` 起始时间列入，因为没有任何东西派生过它。

**理由**：§34 早已把节点**在跑什么**（运行时状态）与它**从什么启动**（配置）分开，而实例模型继承了这个区分：实例比它的 VM 活得久，而一张活句柄的表随进程一同死去。与之相对，链是只增且耐久的 —— 而自缺口 2/N 批起它还是**可归因**的（每一行都写下调用者），正是这一点让它能当**对账**的来源，而不是另一份可能与之矛盾的记账文件。推导也回答了那个诚实的问题：「派生过、从未回收的是什么」是对行的查询，而不是一个要人记得去更新的字段。

**影响**：`AppState::instance_history` 与 `ReconciledInstance` 视图；一条新查询路由 —— 它是**模式**，所以 §5.1 的标题（数的是表里静态的行，与 `server/src/routes.rs` 对校）不动，而文档的表与工具 schema 文档各多一行 —— 其 `history` 路径段是**保留字面量**：对它发成员动作是 `405`，不是回收。`docs/control-plane-api.zh-CN.md` §5.4、`docs/tool-schema-control-plane.zh-CN.md` §2 与其检查器的命名表都跟着改。审计窗口是本批的另一半：`EventFilter` 一直在 SQL 里应用的四个字段现在能从 HTTP 触达，写反的一对以 `400` 被拒且 `cause` 点名下界。**没有表、没有 schema、也没有链结构发生变化**，而参考调度员现在声明自己的名字 —— `--agent-id` 必填，因为「没有名字的调度员」正是 §81 要去修的东西。

## 83. 没有路由要求的能力名，不是能力

**日期**：2026-09-27 ｜ **状态**：已定；随 v1.0 缺口 3/N 的清理（批 C）落地

**决策**：词汇表去掉五个没有任何路由要求过的名字：`task.dispatch`、`task.dispatch.remote`、`sandbox.instantiate.remote`、`audit.read.remote` 与 `request.approve`。`Capability` 从 38 变体降到 33，`auth.rs` 里的守卫与端点的自答随之一同移动。仍有路由要的那一个 M2a-1 名字 `sandbox.instantiate` 保留：实例端点在它名下派生。

## 84. 队列是运行时状态；里面的申请从链推导，清理由调用方做

**日期**：2026-09-27 ｜ **状态**：已定；随 v1.0 缺口 3/N 批 D 的清理落地

**决策**：待批槽**不**持久化，也不搬进某个文件。`SandboxRequests` 仍是它本来的样子——`Mutex` 包着的 `Vec`——而重启后幸存的东西**从链推导**，与实例表的过去同一个手法（§82）：`derive_requests_from` 把 `m.request.ask` / `m.request.approve` / `m.request.reject` 行折成每个请求一条记录，进程启动时用那些仍然 **pending** 的行给活队列打底。已决的请求不会活着重来：它是历史，历史是链的。链上也多出队列唯一的清理动作——`DELETE /v0/sandboxes/requests/{id}`，门是 `sandbox.read`，答 `200` 带被移除的记录。它什么都不写：队列丢掉申请，链保留它。

**理由**：§9 说 M 的状态住在 M 之外——审计链、实例表与待批槽才是真相所在，M 的内存只是一份缓存。§82 已经用「推导」回答了实例表，因为活句柄无法持久化；队列是同一类问题而另有一个答案可选，而选**同一个**答案保住了同一条规矩：**这东西为什么能活过重启？因为链这么说**。写第二个文件会在链旁边放第二个真相源，正是 §82 要避免的那种漂移，而且它还得为自己的版本常量、自己的迁移、自己的「更新的文件」故事操心——就为一个链已经描述得清清楚楚的 `Vec`。链唯一不携带的是 `reason`（ask 行的 detail 一直是 `{id, action, sandbox}`），这一点被接受而不是打补丁：reason 是人的备注，不是一次决策所需的状态，而把它塞进 `m.request.ask` 的 detail 会往哈希公式覆盖的行里加一个字段——为一句话备注不值得冒这个险。关于 TTL：§36 说没有，本批保持。它加的是 §36 留下的**另一半**——显式清理——而区别在**机制**：没有任何东西会自己过期（无清扫器、无时钟），而一个用完一条申请的调用方自己把它拿走。这与「无 TTL」相容，不是推翻它。

**影响**：`host-core` 多出 `ReconciledRequest` 与纯函数 `derive_requests_from`、`SandboxRequests::restore`（对冲撞是**报告**而不是解决）与 `SandboxRequests::remove`；`AppState` 在构造器里给队列打底，尽力而为，且**只在真的恢复了东西或发生 id 冲撞时**写一行 `host.sandbox_request.restore`。`server` 多出一条路由——`/v0/sandboxes/requests/` 下的第三条路径，一个在定义名看见它之前就被匹配的**模式**，也是那里第一个 `DELETE`——加上 `Action::SandboxRequestDelete` 与一个分发分支。`docs/control-plane-api.zh-CN.md` §5.2 与 §5.4、`docs/tool-schema-control-plane.zh-CN.md` §2 与 §3.3 及其检查器的命名表（`sandbox_request_delete`）都跟着改。**没有哈希公式、审计事件常量、`m.*` 动作名或既有路由发生变化**；队列的流里没有「已移除」这种帧，因为为一个能直接重读队列的调用方发明新事件并不值得。

## 85. 审计读用一个游标翻页，而顺序是过滤器的一部分

**日期**：2026-09-28 ｜ **状态**：已定；随 v1.0 缺口 3/N 批 E 落地

**决策**：`GET /v0/audit/events` 多出一个可选参数 **`before_id`** —— 比它点名的 id **严格**更早的、最新的 `limit` 行 —— 而 `EventFilter` 多出一个**加法式**字段 `descending: bool`（默认 `false`），把存储的 `ORDER BY id ASC` 翻成 `DESC`。`limit` 保持必填、不变；`before_id` 与 `to_id` 同传是 `400` 且点名 `before_id`，而不是静默偏向其中一个。

**理由**：这个端点答的是 **newest-first**（`AppState::list_events` 把存储的链序反转），所以「下一页」是**更早**的行 —— 但 `LIMIT` 作用在扫描上，而升序扫描保留的是窗口里**最旧**的行。这就是缺口本身：`to_id` + `limit` 无论如何都表达不出「紧邻 X 之前那几行」，而调大 `limit` 只会把最旧那一端放宽。于是顺序必须成为调用方可以选择的东西。形状本有两个：`after_id`（升序已经能服务）或 `before_id`（需要另一端）。`after_id` 被否，因为它就是 `from_id` 换个名字 —— 而 `from_id` 已经在那儿、且是含下界，供「不能漏读」的读取方使用。游标的方向跟的是这个表面自己的顺序，不是存储的。机制上：翻序做成 `EventFilter` 的加法式字段，而不是第二个方法，因为一个字段就承载了全部含义（「`LIMIT` 保留哪一端」），而派生的 `Default` 让每个既有调用方逐字节不变；另加一个 `list_desc` 只会给同一条查询起第二个名字。`before_id` + `to_id` 的拒绝是刻意的：它们是同一个问题的两端，同时传就是自相矛盾，而静默选一个会把一次含糊的读取装作成功。

**影响**：`audit/src/store.rs`（`EventFilter.descending`、`list` 的 `ORDER BY`）；`host-core/src/state.rs`（`list_events` 只在调用方**没有**要另一端时才反转）；`server/src/routes.rs`（`audit_window` 读 `before_id`，映射为 `to_id = before_id - 1` + `descending`，并拒绝冲突）。`docs/control-plane-api.zh-CN.md` §5.1 与 §5.4、`docs/control-plane-client-guide.zh-CN.md`（它那句「v0.9 没有任何 offset 或游标」在写下时是真的，现在不再是）、`docs/tool-schema-control-plane.zh-CN.md` 与其定义块都跟着改。**没有哈希公式、审计事件常量、`m.*` 动作名、其他路由或 `limit` 语义发生变化** —— `limit=0` 仍然答空数组，`limit` 仍然必填。

## 89. 一条签名消息以一行走 TCP 传输，重放被一个「每同侪」窗口封顶

**日期**：2026-09-28 ｜ **状态**：已定；M4a 的 §3 开放项已关闭（未实现）

**决策**：[`docs/connection.md`](connection.zh-CN.md) 的 §3 留了两样东西，现在两样都以该文件的 **§3.1** 与 **§3.2** 冻结。**传输**：一条签名消息是**一行 JSON、走一条 TCP 连接** —— `worker` 与插件接口已经在用的纪律 —— **先直连**，失败则交给 **relay**，而 relay 是主路径；帧在**两条路径上逐字节相同**，这正是 relay 无状态的原因；连接是明文，它的完整来自签名，同侪之间不发 bearer token；以及**没有单独握手**，因为 `v` 是逐消息检查的。**重放防护**：向后**五分钟**、向前**一分钟**的窗口，用**每同侪、内存里的高水位 + 该水位上接受过的 body 哈希集合**执行，而推进水位即丢弃集合 —— 没有定时器、没有清扫器。记录**不持久化**，而它留下的暴露面 —— 仍在窗口内的一条消息可**跨重启重放一次** —— 被写下来而不是藏起来。

**理由**：两样都必须在**这里**关闭、而不是在 M4d，因为 M4b、M4c 与 M4d 都要交换签名消息，而一个没有传输的签名协议不是一个协议。两个选择都跟着**已经存在的缝**走。**TCP 与 JSON 行**：[decisions §7](decisions.zh-CN.md) 已经为派发点名了点对点 TCP，而一行一个对象正是 `worker` 与 [plugin-interface.md](plugin-interface.zh-CN.md) 解析的形式 —— 复用它，本项目就只有一套线上语法而不是两套。**两条路径上帧相同**：[roadmap §4](roadmap-v1.0.zh-CN.md) 说 relay 无状态，而签名是让它**真的**无状态的东西、而不是一句口号 —— 改写帧的 relay 会破坏签名，于是「无状态的桥」由密码学执行、而不是由承诺执行。**−5 / +1 分钟**：[decisions §33](decisions.zh-CN.md) 允许 30 s – 2 min 的静默重试才开始升级，所以更短的窗口会拒绝这个设计所依赖的那些重试；向前那一分钟是钟偏、仅此而已，因为更长的未来是一个藏伪造的地方。**高水位而不是一袋哈希**：它把记录封顶在「一个同侪在一个时间戳上的一批」，把清理变成丢弃而不是扫除，并且**天然挺过密钥轮换** —— 记录属于同侪，而 [decisions §13](decisions.zh-CN.md) 允许几把密钥同时有效。**不持久化它**是一个传输层防御诚实的选项：持久化它就意味着一个新盘上格式、一个版本标记与一次迁移，为的却是一个本来就只有五分钟宽的界限 —— 所以它保持开放，代价写在旁边。

**影响**：`docs/connection.md` 多出 §3.1 与 §3.2；它的 §1「未冻结」清单缩到端口号、超时、记录的数据结构、以及后批是否持久化它；而它的 §6（M4d）现在说 **relay 的*路由*** 才是 M4d 定的，传输不是 —— 传输在这里定死。`CHANGELOG.md` 与 `handoff.md` §1 跟着改。**没有源文件、依赖、新的持久化格式、capability 名、审计事件常量或哈希公式发生变化** —— 而 `partial`（错误模型五个分类之一）在这一层**刻意不用**，因为一帧是一条消息、不是一批。

## 90. 发现发的是地址；它发的不是信任

**日期**：2026-09-28 ｜ **状态**：已定；M4b 的协议已冻结（未实现）

**决策**：[`docs/connection.md`](connection.zh-CN.md) 的 §4 已写，于是发现就像 §3.1 那样被冻结：**两个来源**。**内网服务器** —— 一个带角色的节点，不是一种新进程 —— 下发一张表，**其条目恰好就是 `peers.json` 条目**，在启动时、重连时与变更时下发，并带一个 **generation**；下发是一个普通的签名帧、走 §3.1 的传输；而表是**来源、不是权威**（节点自己的 `peers.json` 仍然赢，冲突被**报告**）。**UDP 广播**是补充：**一个数据报携带一个签名帧**，其唯一被允许的效果是提供一个地址，而它是本协议里唯一走 UDP 的东西。房间隔离是一个**带安全默认的过滤器** —— 仅当报名的房间与接收方被配置的房间相交时才采纳，而没有配置任何房间的节点什么都不采纳。而保住 §9 的那条规矩是：**报名能刷新地址，无法引入密钥** —— 接收方还不认识的节点会被报告给部署者，只有内网服务器（其角色就是持有这张表）可以采纳。

**理由**：§3.1 冻结了帧怎么移动、把地址这个问题留着，而后面每一块（M4c、M4d、M4e）都需要它有个答案。三个选择值得记下来，因为每个都堵住一个别人本可以从旁边钻过去的洞。**「刷新地址、绝不引入密钥」**：§9 已经禁止首次使用即信任与按地址的信誉，而一个让未知节点凭自己一句话变成受信同侪的广播，会把这两个从一扇写着「发现」的侧门重新放进来。**表是来源、不是权威**：被下发的表是另一台机器的意见，而一个连通性取决于别人那份文件写对了的节点，会在那份文件没写对时失效；让节点自己的 `peers.json` 保持权威、把冲突*报告*出来，正是 [plugin-interface.md](plugin-interface.zh-CN.md) §6 已对 manifest 来源适用的规矩。**固定的广播端口**：它必须到达一个什么都还不知道的节点，因此它自己无法被发现；而一个可配置的端口会让同一链路上的两个节点静默地互相看不见。房间过滤器的**默认拒绝**跟着项目自己的习惯（[security-model.md](security-model.zh-CN.md) §4），而让过滤器去读一份**形状属 M4c** 的成员表，使本节不会吞掉下一节：M4b 定过滤器，M4c 定那个文件。

**影响**：`docs/connection.md` §4 多出 §4.1–§4.3；它的 §1 清单把发现从 *deferred* 移到 *frozen*；而 §5 的 deferred 说明现在写着「M4b 已定过滤器，而 M4c 定那个文件」。`CHANGELOG.md` 与 `handoff.md` §1 跟着改。**没有源文件、依赖、capability 名、审计事件常量、哈希公式、以及 —— 因为对等端口是既有设置文件里的一个字段 —— 新的持久化格式发生变化。** 传输自己的开放项（端口号、超时）留在 §3.1 放它们的地方；M4b 定的是那条**规矩**：节点的对等端口是配置，而广播端口是常量。

## 91. 一个房间是成员关系加规则，而成员关系从不引入密钥

**日期**：2026-09-28 ｜ **状态**：已定；M4c 的协议已冻结（未实现）

**决策**：[`docs/connection.md`](connection.zh-CN.md) 的 §5 已写。`rooms.json` 是**一个 JSON 文件**、`schema_version` 排第一 —— 即 [`node.key`](connection.zh-CN.md) 与 `peers.json` 已在用的形状 —— 装着若干房间，每个有 `name`、一串 `node_id` 的 `members[]` 与一个 `rules` 对象。规则就是 [roadmap §4](roadmap-v1.0.zh-CN.md) 的三条：**`rate`** = `{messages, window_seconds}`、**按成员**；**`mention`** = `"members"` 或 `"nobody"`、默认 `"nobody"`；以及 **`require_signature`**，它在 v1.0 里唯一合法的值是 `true`。`rooms.json` 与 `peers.json` 是**两个文件、两位作者** —— 房间说*谁*，`peers.json` 说一个节点*是什么*，两者互不覆盖。**成员关系是配置**：v1.0 没有加入协议。而发现过滤器那句「被配置为某个房间」现在有了定义：`rooms.json` 点名那个房间，**且**它的 `members[]` 列着本节点自己的 `node_id`。

**理由**：§4.2 冻结了一个读「房间集合」的过滤器、把文件留给本批，所以关闭它就意味着说清一个房间**是什么**。四个选择承担了分量。**成员是一个 `node_id`，而成员关系从不引入密钥**：[decisions §13](decisions.zh-CN.md) 已经把节点的密钥放在 `peers.json`，而第二个密钥可能的来源就是第二个可以授予信任的地方 —— 所以成员关系负责点名，`peers.json` 负责证明。**`require_signature` 不能降低 §3 的底线**：§3 让签名在对等路径上普遍成立，所以一个能放行无签名流量的房间开关会与一个已冻结的节矛盾；它被记录为 `true`，而 `false` 在**加载时被拒** —— 这既让 [roadmap §4](roadmap-v1.0.zh-CN.md) 的第三条规则保持可见，又不让一个配置文件把签名抹掉。**成员关系是配置，不是协议**：动态加入会是一个机制、带着它自己的权威问题 —— [decisions §33](decisions.zh-CN.md) 的领土 —— 在这里发明它，会顺手把一个属于中心的问题定下来。**`rate` 的拒绝映射到 `refused`**：这是第四个 —— [error-model.md](error-model.zh-CN.md) §4 已经把那个分类给了部署者的策略与队列已满，所以不出现第六个分类，它的邻居也保持原样。

**影响**：`docs/connection.md` §5 多出 §5.1–§5.3；它的 §1 清单把房间从 *deferred* 移到 *frozen*，于是 §6–§7 成为仅剩的 deferred 节；`docs/api-compatibility.md` §6 与 `docs/upgrade.md` §2 多一行 **`rooms.json`**；`CHANGELOG.md` 与 `handoff.md` §1 跟着改。**没有源文件、依赖、capability 名、审计事件常量或哈希公式发生变化** —— M4c 是一个文件形状与三条规则，而一个房间的成员由 §4.2 已冻结的同一个发现过滤器读取。

## 92. 跨区域服务器是部署者的部署，而它用签名授权

**日期**：2026-09-28 ｜ **状态**：已定；M4d 的协议已冻结（未实现）

**决策**：[`docs/connection.md`](connection.zh-CN.md) 的 §6 已写。跨区域服务器是**同一套软件的专用部署**、**由部署者运行** —— 从不由项目运行 —— 而它的四个角色与各自可以知道什么一并冻结：**signalling**（地址，从不是负载）、**relay**（搬一帧它无法改动的帧）、**management**（发布注册表与房间定义，作为**来源、不是权威** —— §4.1 的规矩往外推一层）、**audit aggregation**（只定角色的形状与位置；digest 属 §7 并等 M5）。**路由**按签名内的 `to`、且只按它；**授权就是 §3 模型** —— 服务器认识的 `node_id` + 验证通过的签名 —— **没有新凭证、没有新 capability**；一帧**只**转发给服务器同样认识的目的地；「无状态」说的是**内容**（谁在哪与 §3.2 的重放记录保留，两者都是传输事实）；直连把数据路径带离 relay；而服务器**从不拨向节点**，这就是不需打洞的原因。一个节点只通过**它自己的 `peers.json` 条目加上它网络设置里的一个字段**抵达它 —— 无新持久化格式。

**理由**：两条义务塑造了它。第一条是 [roadmap §1](roadmap-v1.0.zh-CN.md) 对「官方运营的服务」的红线：四个角色、尤其是 signalling 与 management，可能被读成「项目在运营一项服务」，所以 §6.5 **在文档里**回答那个问题、而不把它交给读者的善意 —— 运行者被写明、没有项目端点、每个角色都是机制且取舍留给部署者、注册表被压在*来源*而非*权威*上、服务器也不发放任何日后得收回的凭证。第二条是与前面各批已冻结内容的**一致性**。**用签名而不是用凭证授权**：§3 已经确立同侪不共享机密，所以一个想要 token 的 relay 会需要第二套平行的信任系统 —— 而每一个 capability 问题都已经有一个家（[security-model.md](security-model.zh-CN.md) §4）。**只按 `to` 路由，且只向已知目的地**：`to` 在签名之内，所以 relay 无法被骗到一个帧要去哪，而拒绝未知目的地正是让一个发送方的失误不变成所有人流量的东西。**注册表是来源**：§4.1 已经拒绝让下发的表压过节点自己的 `peers.json`，§5 已经让成员关系留在本地；一个带权威的 management 角色会同时与两者矛盾。**无新持久化格式**：服务器是一个同侪，所以它的密钥住在 `peers.json`、与每一把其他密钥住在一起，而只有那个*策略*选择 —— 「这条同侪是我的跨区域服务器」—— 需要一个设置字段。

**影响**：`docs/connection.md` §6 多出 §6.1–§6.5；它的 §1 清单把跨区域服务器从 *deferred* 移到 *frozen*，于是 §7 成为仅剩的 deferred 节；`CHANGELOG.md` 与 `handoff.md` §1 跟着改。**没有源文件、依赖、capability 名、审计事件常量、哈希公式或新的持久化格式发生变化** —— M4d 是一个部署形状、四个角色与一条路由规则，而它日后收集的 digest 仍然是 M4e 要写的。

## 93. 连接层的代码从一个「依赖链、而非被链依赖」的 crate 开始

**日期**：2026-09-28 ｜ **状态**：已定；第一块已实现（身份落盘）

**决策**：连接层在一个**新 crate `net/`** 里实现，而它的第一块 —— [connection.md](connection.zh-CN.md) §2，节点身份 —— 已在盘上。`net` 依赖 **`audit`**，不依赖本工作区里任何别的东西；将来是 `host-core` 依赖 `net`。已落地：一个版本化 JSON 加载器（`Versioned` trait、`VersionedLoad` 四种结果、以及「更新的文件被**拒绝**而不是半读」）与 `NodeKey` —— 那个 JWK 文件（`schema_version` 排第一，`kty`/`crv`，`x`/`d` 是 32 字节 base64url），用 `getrandom` 在**首次配置了联网的启动**时铸出，以 `create_new` + 仅属主方式写下，且**读绝不生成**。新依赖：**`ed25519-dalek` 2**、**`base64` 0.22**、**`getrandom` 0.4**（工作区已有，bearer token 在用）。`audit::canonical_json` 与 `audit::fingerprint` 是**借用**的、不是重写的，用于公钥指纹。

**理由**：有三个选择是真正的备选。**crate 依赖 `audit`、不依赖 `host-core`**：签名覆盖的规范字节是链自己的定义，所以 `net` 必须在宿主**之下** —— 而一旦宿主想在启动时加载 `node.key`，依赖 `host-core` 就会闭上一个环。**版本规则只实现一次、且是通用的**：§2 要求 `node.key` 的 `schema_version` 排第一，§5.1 对 `peers.json` 与 `rooms.json` 提同样的要求；一个加载器就意味着那些规矩只有一种读法，而它的 `Missing`/`Current`/`Migrated`/`TooNew` 形状来自 `LocalSettings` —— 那是项目已经用一次真迁移实操过的形状。**读绝不生成，而生成是仅属主的、且用 `create_new`**：后半句拦住两个进程抢着铸钥、其中一个静默获胜；前半句是 §2 说下的规矩 —— 没配置联网的节点根本没有密钥，所以在一台从不加入网络的机器上什么也不会被创建。另有两件小事值得记下，因为它们是**解读**而非复述。**文件里没有 `node_id`**：§2 把密钥对与*设备名*分开，而文件装的是密钥材料 —— 一个 `node_id` 成员会成为 §2 没有冻结的第六个 JWK 成员。**两半在加载时互校**：`x` 由 `d` 重新导出并比对，所以被拼接或手改过的密钥文件在**读**的时候就被拒绝，而不是等到第一次拿它签名时。

**影响**：`net/` 是一个新 crate（`Cargo.toml`；`src/{lib,versioned,identity}.rs`；一个带 `--self-test` 的 `identity` example；集成测试；双语 README）；工作区的 `members` 加它；gate 多一步（`cargo run -p net --example identity -- --self-test`），与既有的 example 证明并列，并且 `net` 也加入了 `cargo clippy` 名单 —— 否则它会静默溜过去。`docs/README.md` 的 crate 表多一行。**没有既有源文件的逻辑被改动，也没有哈希公式、路由、capability 名或审计事件常量被碰**：`net` 读链的规范 JSON 并哈希它，写自己的文件。签名、传输、发现、房间与跨区域服务器是接下来的几块，每块都在它实现的那一节冻结之后。

## 94. 一条签名消息按冻结的顺序验证，而它的拒绝携带错误模型的分类

**日期**：2026-09-28 ｜ **状态**：已定；M4a 的签名与重放防护已实现

**决策**：[connection.md §3](connection.zh-CN.md) 与其 §3.2 已在 `net/` 实现。`SignedMessage` 是 `{v, from, to, ts, body}` 加上 `sig`，而**被签的是那五个成员的规范 JSON** —— `audit::canonical_json` 的字节，不是第二套序列化。`verify` 按冻结顺序跑六步 —— 认识发送方、验签、`v` 可说、`to` 是本节点、`ts` 在窗口内、非重放 —— 而每次失败都以错误模型的一个分类作答：**`refused`** 给未知发送方或重放，**`invalid`** 给坏签名、不支持的版本或寻址到别处的消息，**`network`** 给过旧或来自未来的时间戳。重放记录是 `net` 的 `ReplayGuard`：按同侪、在内存、一个高水位加上在该水位上见过的负载哈希，窗口 **−5 min / +1 min**，推进水位即丢弃集合。

**理由**：三处是真正的备选。**版本在被签的字节里。** §3 在第 3 步、也就是**验签之后**检查 `v` —— 而这是唯一能把「版本不对」与「伪造」分开的顺序：先查版本的话，对一个谎言与对一条来自更新构建的真消息，会给出同样的回答。测试把这点说得很明白：一条**以 v2 签出**的消息被当作版本拒绝，而把 v2 **改**进一条 v1 消息里则被当作签名拒绝。**`to` 是 `invalid`，而 §3 没有这么说。** 那句冻结的句子点名了三个映射、把第 4 步落下了；它以 `invalid` 补齐，因为一条寻址到另一个节点的消息是**错误输入**、而不是策略拒绝 —— 而这个缺口记在这里，不是悄悄选的。**记录按同侪、绝不按密钥。** §3.2 说轮换不得重置它，而实现不可能偶然弄错：那张映射是 `from → 记录`，而密钥住在另一个结构里（`PeerKeys`，每同侪一个**集合**，于是灰度期的几把密钥都能验）。测试用唯一要紧的方式证明它：一条由**新**密钥签出、时间戳为旧的消息被当作**重放**拒绝 —— 不是未知发送方，也不是坏签名。

**影响**：`net/` 多出 `src/message.rs`（帧与规范字节）、`src/sign.rs`（六步、`PeerKeys`、`VerifyError` 到 `Category` 的映射）与 `src/replay.rs`（`ReplayGuard`），一个带 `--self-test` 的 `sign` example，以及十三条集成测试；gate 多出它的第二个 `net` 步骤。`net/README.md` 把 §3 从「还不在这里」移到「在这里」。**没有既有源文件被改动，也没有哈希公式、路由、capability 名或审计事件常量被碰** —— 而且授权刻意缺席：本批回答的是*谁发的*，而那个节点可不可以做这件事仍是 capability 模型的问题（[security-model.md](security-model.zh-CN.md) §4），所以这里没有一处是权限检查。

## 95. 传输是 std TCP、一消息一行 JSON，而 relay 是一道缝

**日期**：2026-09-28 ｜ **状态**：已定；直连路径已实现

**决策**：[connection.md §3.1](connection.zh-CN.md) 在 `net` 里用 **`std::net`** 实现 —— 不引 async 运行时。`Connection` 与 `Listener` **一消息一行 JSON** 地收发；帧只序列化**一次**（`SignedMessage::to_line`），所以直连与经 relay 两条路径携带逐字节相同的字节；而 `deliver` **先**试同侪自己的地址，失败便把帧交给 `Relay` 这道缝。relay 的*路由*是 M4d 的：本批定下那个 trait（`fn forward(&self, frame: &str)`）、一个诚实的「什么都没接」实现（`NoRelay`），以及直连路径。端口与超时不被 §3.1 冻结，住在 `TransportConfig` 里。失败严格按 §3.1 的表映射到错误模型：连接被拒或超时、被截断的帧、过长的行、缺失的 relay 都是 **`network`**；一条完整但解析不了的帧是 **`invalid`**；而 **`partial` 不用**，因为一帧是一条消息、不是一批。

**理由**：三个选择。**`std` 而非运行时**：`sandbox/relay.rs` 已经在 std socket 上跑一个带帧协议，所以运行时会是每个调用方都要为它付钱、却很少有人用的调度器 —— 而插件接口的传输是 stdio、不是 TCP，所以也无可与 async 栈共享之处。**一个编码器**：§3.1 要求的逐字节相同在这里不是约定、而是代码的事实 —— 把消息变成帧的函数**只有一个**，而 relay 收到的就是它的输出原文；测试断言直连路径写出的字节等于交到 relay 手里的字节。**是一个 trait，而不是一个能编译却撒谎的桩**：路由归 M4d，所以 `Relay` 只有一个方法宽，而 `NoRelay` 答 `RelayUnavailable`（`network`），而不是假装帧去了某处。两个更小的注记：`receive` 会拒绝超出一道可配置上限的行，而不是无界分配，而这个拒绝是 `network`（一次没把帧送达的传输）而不是 `invalid`，因为上限是本构建的限制、不是协议规则；读超时在 Unix 上是 `WouldBlock`、在 Windows 上是 `TimedOut`，所以两种都被匹配 —— 而单个平台上的测试只能证明一半。

**影响**：`net/` 多出 `src/transport.rs`、一个带 `--self-test` 的 `transport` example、十条集成测试，以及 `src/error.rs`（错误模型的五个分类，从 `sign.rs` 移出，好让验证器与传输映射到同一个定义）；gate 多出它的第三个 `net` 步骤。`net/README.md` 把 §3.1 从「还不在这里」移到「在这里」，并列出 M4d 作为仍然缺的东西。**没有既有源文件被改动、没有新增依赖，也没有哈希公式、路由、capability 名或审计事件常量被碰** —— 而 relay 是刻意静止的：本批没有任何东西把帧转发到任何地方。

## 96. 发现发的是地址：一份说了算的 peer 文件、一张只是来源的表、一个不引入密钥的信标

**日期**：2026-09-28 ｜ **状态**：已定；M4b 已实现

**决策**：[connection.md §4](connection.zh-CN.md) 已在 `net` 实现。`peers.json` 是版本化 JSON 文件（版本 1），其条目恰好就是下发一张表所携带的 `{node_id, addresses[], public_key, capabilities, rooms[]}` 形状，而它对**拥有它的节点**具有权威；一个携带 `d`（私钥）的 `PeerEntry` 被点名拒绝，因为 peer 表是一个会在机器之间被拷贝的文件。下发的表（`NodeTable`）作为普通签名帧旅行、带一个 **generation**，并作为**来源**被合并：`merge_table` 答出合并后的视图加一份 `MergeReport`，其 `conflicts` 点名两边 —— 本地赢，且什么都不静默解决。信标是一个数据报携带一个签名帧，其效果是提供一个地址：`consider_announcement` 对已知节点答 `RefreshedAddresses`，对未知节点答 `ReportedUnknown`，而报名的房间与接收方不相交时答 `IgnoredOutOfRoom`。房间过滤器是 **`RoomFilter`** —— 一个带**默认拒绝**的相交测试，读一组房间名（`rooms.json` **文件**属 M4c）。广播端口是**协议常量**（`BROADCAST_PORT = 47821`），不是配置。

**理由**：§4.2 写下的三条规矩是有意思的部分，而三条都是关于「不要再长出一条信任旁路」。**文件赢、表只是来源**：一张被下发的表是另一台机器的意见，所以合并它不得改变一个节点对它**被配置过**的同侪的看法 —— 因此合并是**报告**而不是解决，即 [plugin-interface.md](plugin-interface.zh-CN.md) §6 已对 manifest 来源适用的那条规矩。**报名能刷新地址、无法引入密钥**：§9 禁止首次使用即信任，而链路上任何人都能发一个数据报 —— 签名证明的是**谁写的**，不是「接收方该不该理会」—— 所以未知节点的信标被报告给部署者、不被任何人采纳。`Adoption::introduced_a_key()` 是一个只能返回 `false` 的方法，而这正是要点：这个类型让那条不变式在**将来某次改动必须与它辩驳的地方**变得可见。**端口是常量**：广播必须到达一个什么都还不知道的节点，因此它无法被发现，而可配置的端口会让同一链路上的两个节点静默地互相看不见。信标本身是「本协议里唯一走 UDP 的东西」，而这一点由「恰好一个函数发它、一个函数收它」保持诚实，两者都复用 §3 的帧。

**影响**：`net/` 多出 `src/peers.rs`（文件、条目、以及拒绝 `d` 的公钥 JWK 规则）、`src/discovery.rs`（表、合并与它的冲突报告、信标与 `RoomFilter`）、一个带 `--self-test` 的 `discovery` example，以及十七条测试；gate 多出它的第四个 `net` 步骤。`net/README.md` 把 §4 从「还不在这里」移到「在这里」，留下 §5 与 §6。**没有既有源文件被改动、没有新增依赖，也没有任何持久化格式表行被移动** —— `peers.json` 的行在格式落地时（M4a-impl-1）就加过了，而本批只读写那一行所描述的东西。`rooms.json` 的文件、relay 的路由与跨区域服务器分别是 M4c 与 M4d 的。

## 97. 房间说「谁」；`peers.json` 说一个节点「是什么」 —— 而过滤器读的是成员关系

**日期**：2026-09-28 ｜ **状态**：已定；M4c 已实现

**决策**：[connection.md §5](connection.zh-CN.md) 已在 `net` 实现。`rooms.json` 是版本化 JSON 文件（版本 1），其中每个房间是 `{name, members[], rules}`，成员是 **`node_id`**，规则是 §5.2 的三条：`rate` = `{messages, window_seconds}` **按成员**、`mention` = `"members"` | `"nobody"`（**默认 `"nobody"`**）、以及 `require_signature`，其唯一合法值是 `true`。加载会**点名**拒绝 `false`、拒绝「零消息」或「零秒窗口」的速率、拒绝两个同名房间、拒绝空成员。`RateCounters` 把「按成员、按房间」的预算保留在**内存**，超限时以 `Refused` 作答。`Room::allows_mention_from` 是先看成员关系、再看设置。而 `RoomFilter::from_rooms(&RoomsFile, this_node_id)` 正是 M4b 的过滤器遇到本文件的地方：文件**点名**、且其 `members[]` **列出本节点**的那些房间。

**理由**：两条规矩承担了分量，而两条都是关于「不让第二个真相源出现」。**成员是一个 `node_id`，而 `rooms.json` 与 `peers.json` 是两个文件、两位作者。** §5.1 说房间的 `members[]` 是部署者的说法，而 `peers.json` 条目的 `rooms[]` 是那个节点*关于自己的宣告* —— 所以房间持有成员关系、绝不持有身份，两个文件也互不覆盖。这也正是成员关系**从不引入密钥**的原因：这里的一个名字就是一个名字，密钥在 `peers.json` 说的那个地方。**签名开关不能降低 §3 的底线。** §3 让签名在对等路径上普遍成立，所以一个可加载的 `require_signature: false` 会是一个配置文件悄悄抹掉一条已冻结的条款；在加载时**拒绝它**（而不是忽略它）正是让这个字段保持诚实的东西，且拒绝会点名该字段，好让运维看清原因。两个更小的选择：**速率预算是按成员的**，因为房间级预算会让一个成员把其他成员饿死；而超限是 `Refused`，因为 [error-model.md](error-model.zh-CN.md) §4 已经把那个词给了部署者的策略，所以不出现第六个分类；以及**成员关系是配置**、没有加入协议，因为动态加入会是一个带自身权威问题的机制（[decisions §33](decisions.zh-CN.md)），而本批不得顺手把它定下来。

**影响**：`net/` 多出 `src/rooms.rs`、一个带 `--self-test` 的 `rooms` example，以及七条集成测试；`RoomFilter::from_rooms` 合上了 M4b 留下的那个环，于是信标过滤器现在读的是部署者的文件、而不是测试递给它的一组名字；gate 多出它的第五个 `net` 步骤；而 `docs/api-compatibility.md` §6 与 `docs/upgrade.md` §2 各多一行 **`rooms.json`**。**没有既有源文件被改动、没有新增依赖，也没有哈希公式、路由、capability 名或审计事件常量被碰** —— 授权也仍然缺席，与每个 `net` 批次一样：本 crate 回答*谁发的*与*房间允许什么*，而一个节点可不可以做某件事仍是 capability 模型的问题。

## 98. relay 把一帧沿目的地的会话交下去，因为服务器从不拨向节点

**日期**：2026-09-28 ｜ **状态**：已定；M4d 的 relay 已实现

**决策**：[connection.md §6](connection.zh-CN.md) 的 **relay** 角色连同它所需的会话在 `net` 里实现了。`RelayServer` 解析一帧、用自己那份 `peers.json` 认证发送者 —— §3 的第 1–3 步与 §3.2 的记录，**没有**第 4 步 —— 只按签名内的 `to` 路由，并按**到达时的那些字节**把帧沿目的地的会话交下去。发给服务器自己的帧是 `Routed::Local`（signalling 与 management 两个角色的，下一批）；服务器放不下的目的地被拒绝而不广播；而被认识却**没有拨入**的目的地同样被拒绝，因为 §6.3 要服务器等着被拨、**从不拨向节点**。`SessionTable` 就是那份知识 —— `node_id → 它拨入所用的那条 socket` —— 即 §6.3 的「谁在哪」，读作一个传输事实。`RelaySession` / `RelayClient` 是节点那一半，而 `hello_body()` 是本批唯一发明的线上形状：一个发给服务器自己的普通签名帧，带协议版本，会话借它说出自己是谁，而一个暂时无话可发的节点也借此能被找到。`src/bin/riscdom-relay.rs` 是部署者的程序 —— `--data-dir`、`--bind` 与 `--node-id`，没有默认地址，横幅写明运行者、存储规则与「从不拨出」的规则。**hello 不消耗发送者的 §3.2 记录**，这是规则而不是疏忽。

**理由**：四个选择承担重量。**会话，而不是回拨**：§6.3 说服务器从不拨向节点、「两边都拨出去」，所以一个按目的地 `addresses[]` 去够的 relay 会与那句话矛盾，并把「不需打洞」所依赖的入站路径问题请回来；目的地把连接开着，帧就沿它下去。**只丢第 4 步，且只丢它**：§6.3 点名第 1、2 步，而经 relay 的帧按设计就是发给别人的 —— 于是 relay 与接收方现在共用 `check_identity`（第 1–3 步），而不是彼此调用，两者的差别恰好是一个问题，且写在回答它的地方。**一条记录看不见的 hello**：会话是在它所承载的那帧**签名之后**才开的 —— 会话之所以存在，正因为刚失败的是直连 —— 所以一个被 hello 推进过的记录会让 relay 拒绝掉它刚刚接手的那一帧，理由仅仅是它比带它来的 hello 更旧。这是被一个失败的测试找出来的，而不是被审阅找出来的，这本身就是「记录应当是一条带测试的规则、而不是一行代码」的论据。而 **§6.5 的答案在程序里变得可检验**：横幅写明由部署者运行、`--bind` 必填所以软件不点名任何地址、且不存任何消息；另外两条由测试守住 —— 未知发送者拿不到会话，而一个地址活着、可达却没有拨入的目的地什么都听不到。

**影响**：`net/` 多出 `src/relay.rs`（`RelayServer`、`SessionTable`、`Forwarder`、`RelayError`、`route`、`RelaySession`、`RelayClient`）、`src/bin/riscdom-relay.rs`、一个带 `--self-test` 的 `relay` example，以及十七条测试；`sign.rs` 多出 `check_identity`（第 1–3 步，共用）与 `authenticate_forwarded`（第 1–3 步加 §3.2，无第 4 步），`transport.rs` 多出 `frame_bytes` 与 `Connection::writer_clone` / `set_read_timeout` —— 都是对 §3、§3.1 语义无改动的重构；gate 多出它在 `net` 上的第六步。`net/README.md` 把 §6 的 relay 从「还不在这里」移到「在这里」。**没有新依赖、没有新的持久化格式、没有碰任何 capability 名、审计事件常量、哈希公式或路由** —— 服务器不存消息、其权威取自 §3 且不发放任何凭证，而 signalling、management 与 §7 的摘要仍未写。

## 99. 服务器回答一个节点在哪、以及它发布什么 —— 而那个答案是来源，不是权威

**日期**：2026-09-28 ｜ **状态**：已定；M4d 的 signalling 与 management 已实现

**决策**：[connection.md §6.2](connection.zh-CN.md) 的另两个角色在 `net` 里实现了，落在 relay 用的同一台服务器、同一条会话上。发给服务器自己的帧现在被 `Local::of` 读成三种问题之一：**hello**（绑定 socket，什么都不答）、**地址查询**（`{"query": "<node_id>"}`）或**注册表请求**（`{"registry": 1}`）；其余一律 `Unrecognised`，对它什么都不答。**signalling** 答 `{"addresses": [...]}` —— 先是节点拨入所用的地址（它的活会话），再是它 `peers.json` 条目里的地址，去重 —— 而服务器放不下的节点被答以**空表**而不是被拒。**management** 答一个 `Registry`：§4.1 的 `{generation, peers}` 下发表加上旁边的房间定义，由服务器自己的密钥签名（§6.4 让它是一个同侪）。节点把它们读回成 `Answer` 并应用 `Registry::merge` —— M4b 的 `merge_table` 规则用在同侪上，`merge_rooms` 是同一规则用在房间名上 —— 于是节点自己的 `peers.json` 与 `rooms.json` 赢，而每一处分歧都被**报告**。服务器的注册表一变（`set_peers`、`set_rooms`），generation 就前进。两个答案都是 §3 帧，所以节点用它本来就持有的密钥验证；授权在两个方向上都是 §3 的模型：零新凭证、零新 capability。

**理由**：四个选择承担重量。**答案的形状是本批的，而 §6 把这件事留给了实现**：§6 冻结的是角色、路由规则与每个角色可知什么 —— 不是字节 —— 所以 `{"query"}`、`{"registry"}`、`{"addresses"}` 记在这里而不是被假定，正如 §98 记下 hello。**signalling 报两个地址，两个都是传输事实**：§6.2 说 signalling 回答一个 `node_id`「能被够到……据各节点告诉它的」，而服务器知道的两件事正是部署者写下的条目、与那个节点刚刚拨入所用的 socket。活地址在前，因为它是更近的那个；列表去重；而越界的只有地址 —— 「从不是负载」由「答案体恰好一个成员」守住。**未知节点是被回答、不是被拒**：问题本身良构且已认证，所以「我不知道它在哪」是诚实的答案，而 §6.3 的 `refused` 是给「你不可以问」而不是「我不知道」的。**发布的注册表是来源**：§6.2 这么说，而实现让它成为结构性的 —— `merge` 从不替换本地条目，不同的房间保留本地定义，而发布的房间集合被按 `rooms.json` 自己的检查要求，一份实现、两个报告者（读文件说 `Shape`，读发布集合说 `RoomsError::Room`），所以来源无法携带一个文件会拒的房间。表是按请求组装而不是存起来的，所以发布的东西无法与服务器路由所依据的那张表漂移。

**影响**：`net/` 多出 `src/registry.rs`（`Registry`、`Merged`、`registry_request_body`、`registry_category`），`src/relay.rs` 多出 signalling（`address_query_body`、`address_answer_body`、`Local`、`LocalReply`、`Answer`）与 `serve_connection` 里的本地分派，并且 —— 因为回答须签名 —— `RelayServer` 上多出**密钥**与**房间集**（`new` 两者都要，`set_rooms` 发布，generation 前进）；`src/rooms.rs` 多出 `merge_rooms`、`RoomConflict`、`RoomMergeReport`、`Room::summary` 与 `RoomsFile::check`（加载规则，可单独调用）；`src/bin/riscdom-relay.rs` 会铸或读 `<data-dir>/node.key` 并发布 `rooms.json`；`relay` example 多四条检查（共十三条），`tests/server.rs` 新增八条集成测试。**没有新依赖、没有新的持久化格式、没有碰任何 capability 名、审计事件常量、哈希公式或路由** —— 服务器仍不存消息、其权威取自 §3 且不发放任何凭证，而 §7 的摘要仍未写。

## 100. 宿主加载连接层的文件 —— 条件是网络设置说了算

**日期**：2026-09-28 ｜ **状态**：已定；接线已落地（V-1）

**决策**：`host-core` 依赖 `net`，并在启动时加载连接层的三个文件：`<data-dir>/node.key`（[connection.md §2](connection.zh-CN.md)）、`<data-dir>/peers.json`（§4）与 `<data-dir>/rooms.json`（§5）。是否碰它们由**一个条件**决定 —— **`settings.network.is_some()`** —— 而未配置的节点什么都不读、**也不长密钥**，这正是 §2 要求的、也是本批之前每个版本的行为。宿主把加载到的东西留在 `AppState` 上（`node_key()`、`peers()`、`rooms()`，都返回 clone），外加 `connection_problem()`（拿出第一次拒绝，形状与 `settings_problem()` 一致）。**缺** `peers.json` 或 `rooms.json` 是正常的（节点可以谁都不认识、不在任何房间）；来自**更新**构建的文件被拒绝、且**不被覆写**；其余情况都上报。两个名字进入审计词表：**`host.connection.key_minted`**（`{node_id, fingerprint}`）与 **`host.connection.data_too_new`**（`{file, found, supported}`）。`net` 自身一字未改。

**缘由**：三个选择承担重量。**条件是设置，而且只有一行。** §2 把密钥系在「首次配置了联网的启动」上，而设置里本来就写着这件事：`NetworkSettings` 是 `Option`，所以 `is_some()` *就是*「本节点在一个网络上」。没有新的持久化格式，`SETTINGS_VERSION` 不动，而从不加入网络的节点根本没有可泄的密钥文件。**格式知识留在 `net`，策略留在这里。** 每一次读都走 `net` 自己的加载器 —— 版本规则、四种结果、对更新文件的拒绝 —— 而本批只决定*何时*读、*说什么*；这正是 [§93](decisions.zh-CN.md) 的方向上移一层，也是宿主不生长解析器的原因。值得一提的是：`net` 的 `load_or_create_in` 答出的是**密钥**，不是「读还是铸」—— 所以“文件先前是否存在”才告诉宿主发生过一次铸造；而太新的密钥与损坏的走同一条错误通道，所以拒绝会被再读一次来确定是哪一种。**拒绝是可见的，而两种拒绝各有其名。** 铸造写一行 —— 一个静默生成的密钥是部署者无法填进别的节点 `peers.json` 的密钥 —— 而太新的文件写一行，点名文件与两个版本，形状与 `host.settings.data_too_new` 一致。其他原因不可用的文件（**被拼接的 JWK、带私钥的 peer 条目、把 §3 底线降下去的房间**）进日志、可经 `connection_problem()` 读到，但刻意**不**记在 too-new 名下：一个事件名承载两种意思，比一个名字加一条诚实的日志更糟。这里没有什么是致命的，理由与 keyring 的静默降级相同：一个因为 peer 表畸形就不启动的宿主，是一个无法被修好的宿主。

**影响**：`host-core/Cargo.toml` 多出 `net = { path = "../net" }`（零新包 —— 锁文件只多一行边，前后都是 534 个包）；`src/connection.rs` 是新的（加载器、三个 `ConnectionFile` 名、`ConnectionProblem`、`ConnectionFiles` 与三条单测）；`src/state.rs` 多出四个字段、四个访问器与 `load_connection_files()` —— 由 `AppState::new` 与 `AppState::with_data_dir` 在 `load_settings()` 之后调用，而刻意**不**由 `AppState::in_memory` 调用（后者持进程级默认数据目录，绝不应往里铸密钥）—— 它也是那两行被写下的地方；`src/lib.rs` 再导出新类型；`tests/connection.rs` 新增七条集成测试（未配置、只铸一次、文件能加载、太新的 `peers.json` / `rooms.json` / `node.key`，以及一个*不*被当作 too-new 上报的不可用表）；`host-core/README.md` 多出模块与约束。**没有哈希公式、路由、capability 名或**既有**审计事件常量被改动，`net` 的逻辑一字未动，也没有新增什么持久化** —— 那两个新名字住的地方就是 `host.settings.data_too_new` 住的地方（本文、`CHANGELOG.md` 与 `docs/handoff.md`），而**不**是 `docs/control-plane-events.md`：那份文档的二十个名字是它归一的**流事件**，其数量连那份文档与它的守卫测试都断言过。V-2（跨区域指针与客户端）与 V-3（上层暴露）仍待做。

## 101. 节点向上注册并持续心跳：两个层级、一种形状

**日期**：2026-09-28 ｜ **状态**：已定；协议已冻结（V-proto-1），未实现

**决策**：[connection.md §6.6](connection.zh-CN.md) 已写。节点向**它被配置的那台服务器**注册 —— 一个普通的、发给服务器自己的 §3 帧，按 §3 的六步验证，体为 `{"register": 1, "addresses": [...], "capabilities": [...], "rooms": [...]}` —— 然后每 **15 秒**用最小的那个帧 `{"heartbeat": 1}` 心跳一次。服务器为它认识的每个节点保留一张**在线状态表**：`node_id`、节点最后一次报的地址、`last_heartbeat_ms`，以及一个 `state` —— 当 `now − last_heartbeat_ms ≤ 45 s` 时为 `online`，之后为 `offline`。一行由注册创建、由心跳刷新，且**永不**因离线被删除。同一套帧服务**两个层级** —— 节点→内网服务器，内网服务器→上层的跨区域服务器 —— 而内网服务器注册的是**它自己**，不是它自己加下面的节点。加入是**配置**：管理员先把节点加进服务器的 `peers.json`，它才可能注册，**没有自动审批**。这把 §6.2 的模型在第二个方向上补完：**management 是服务器向下发，§6.6 是节点向上报**，部署者的文件仍是权威，而节点报上来的是**来源**。

**缘由**：四个选择承担重量。**注册是 §3 帧，所以它不需要许可。** §6.3 已经写了「谁可以问」—— 服务器认识的节点 + 验证通过的签名 —— 而注册就是同一个问题上移一层：它做认证、不授权，也不添任何 capability。这也让「密钥无法经帧到来」成为**结构性的**而非承诺：服务器只可能接受一个它已在 `peers.json` 里持有密钥的节点的注册，于是 §4.2 与 §9 的规矩是自动成立的。**心跳不是会话开启帧。** `{"hello": 1}` 绑定 socket；心跳说的是一个节点还*在* —— 两个不同的问题，而节点可以握着会话却已经不在 —— 所以把两者绑在一起，会让传输去回答一个存在性问题，而活性那个批次（V-proto-2）会继承它。**15 秒与 45 秒是照着 §3.2 选的，不是图舒服**：后向窗口是五分钟，所以迟到的拍仍是拍、不是 `stale`；15 秒也不至于快到让一支部队的心跳占满链路；而它是离线阈值的三分之一 —— 这正是「错过三拍即离线」得以成立的原因。**倍数关系**被冻结，数值是 v1.0 的默认值，与 §3.1 的超时同类。**内网服务器只报自己**，而第一个理由是算术而不是政策：上层服务器只能验证它持有密钥的那些帧，所以一个点名下层节点的帧会要求它去信任「经消息到来的身份」—— §4.2 禁止的事 —— 且它一个都验不了。下面的地址也是局域网地址，对远端同侪毫无用处；而身份在本文别处也都来自配置（§5.2 的成员关系、§6.4 的服务器条目）。一条规矩，再用一次。

**影响**：`docs/connection.md` 多出 **§6.6** —— 它的十个 H2 节仍是**十个**（§6 保留 §6.1–§6.5，所以既有的对 §6.x 与 §7 的引用全部指向原处）—— 外加引言里一句、§6 收尾摘要里两处；`CHANGELOG.md` 与 `docs/handoff.md` §1 相随，双语的。**没有源文件、没有依赖、没有 capability 名、没有审计事件常量、没有哈希公式、没有路由、也没有新的持久化格式被改动** —— 这是冻结之后为一份已冻结的文档补写的一节。V-proto-2（活性：集体确认、内网服务器察觉自身失联、以及判定之后的动作）与 V-2（指针与客户端）是接下来要用它的批次。

## 102. 一个节点只有在「剩下的见证者全体一致」时才算不在

**日期**：2026-09-28 ｜ **状态**：已定；协议已冻结（V-proto-2），未实现

**决策**：[connection.md §6.7](connection.zh-CN.md) 已写。**一个节点的同级就是它自己的 workgroup**，每个节点用普通 §3 帧**探测**它们 —— `{"probe": 1}`，被答以 `{"alive": 1}`，先直连、失败经 relay，**每 15 秒**一次，而**连续三拍无应答（45 秒）**使探测者把该同侪记为*不可达*。探测者向上**报告**它的视图 —— `{"unreachable": "<node_id>"}` / `{"reachable": "<node_id>"}`，视图不变期间每拍重发、只在新鲜期内计 —— 而内网服务器**判定**：当**至少有一个见证者**（它认识的另一个节点、它自己可达、且不是被判定者）且**每个见证者都报了不可达**时，该节点不在。一个「活着」的见证者一票否决，而**独自**在一个 workgroup 里的节点永不被判。**内网服务器自身的失联由它的兄弟确认** —— 其它内网服务器，把同样两个体报给跨区域服务器，由它按同一条规则判定 —— 而它下面的节点做不到，因为**它们与它共用同一个 LAN 与同一条供电**。判定之后那一行多出 **`judged_at_ms`**（关于可达性的事实，与 §6.6 基于心跳的 `state` 分开保留），判定服务器写 **`host.connection.peer_offline`**（`{peer, witnesses, reports}`）或 **`host.connection.peer_recovered`**（`{peer, method}`）。**什么都不被移除**：协议不定义踢、不定义驱逐、不定义丢弃。

**缘由**：五个选择承担重量。**判定不是沉默。** §6.6 的 `offline` 是一个观察者的沉默；判定是「所有还能碰到它的人」的一致 —— 只有后者强到可以据此行动，所以它们是两个字段，而不是同一个字段的两个值。**全体一致，不是多数。** 失败有清白的解释、成功没有，所以「活着」的见证者一票否决、规则只能是失败者全体一致；而多数会在最要紧的情形里出错 —— 分区：半个 workgroup 能碰到某节点、另一半不能，多数会把一个**活着的**节点判成不在。**见证者集合是它诚实的原因。** 自己挂掉的节点报不了，自己不可达的节点不能作证，所以门槛是*还能说话的人*里全体一致 —— 这也正是独自的节点永不被判（没人能作证）、以及问题不是「多少人报了」的原因。**是兄弟，不是下级。** 内网服务器下面的节点与它共 LAN 与供电，所以一次把见证者也包括在内的沉默不是证据：确认必须来自「可期待在它倒下后仍活着」的同侪。同一套机制上移一层，也不需要新角色 —— 跨区域服务器只**汇总**，因为 §6.3「服务器从不拨出」也约束它。**机制，不是策略。** 内核记下判定（那一行、那个事件），并**完全不定义移除**：被判定的节点保留它的密钥、它的 `peers.json` 条目与它那一行；部署拿它做什么是部署者的策略（[roadmap §1](roadmap-v1.0.zh-CN.md) 的红线，也是 §5.2 与 §6.6 对「加入」已守的那条规矩）。两个更小的结论值得写明：**探测者不写任何链行** —— 怀疑不是事实，每节点一行会让一次分区在半个链上写下*「X 不在了」*；以及**恢复是被听到、不是被重新接纳**，因为什么都没被拿走。

**影响**：`docs/connection.md` 多出 **§6.7** —— 十个 H2 节仍是**十个**，§6 保留 §6.1–§6.5 的编号，所以既有的引用全部仍指向原处 —— 外加 §6 收尾摘要里一处、以及 §6.6 的未冻结清单里一处（它原先把这件事指向 V-proto-2）。`CHANGELOG.md` 与 `docs/handoff.md` §1 相随，双语。**没有源文件、没有依赖、没有 capability 名、没有既有审计事件常量、没有哈希公式、没有路由、也没有新的持久化格式被改动** —— 那两个新名字是对审计词表的**新增**，记在 `host.connection.*` 这族已经住的地方（本文、`CHANGELOG.md`、`docs/handoff.md`），**不**是 `docs/control-plane-events.md`（它的二十个名字是**流**事件）。接下来是 V-2（指针与客户端）与 V-3（踢的 API 会落在那里）。

## 103. 指针是一个设置、客户端是惰性的、心跳是一条线程

**日期**：2026-09-28 ｜ **状态**：已定；V-2 已落地

**决策**：节点能到达它的跨区域服务器了。`NetworkSettings` 多出 **`cross_region_server: Option<String>`** —— 一个 `node_id`，必须出现在该节点自己的 `peers.json` 里（§6.4），加法式、`SETTINGS_VERSION` 不动 —— 而 `host-core` 接上它点名的东西：`RelayClient::new` **不拨号**就被造出，会话在首次需要时打开（`connect`、心跳循环，或后续批次的 `forward`），而一条**注册 + 心跳线程**每条会话注册一次、随后每 **15 秒**（§6.6 的间隔）心跳一次，直到被停。服务端侧 `net` 多出两种帧与那张表：`Local::Register` / `Local::Heartbeat`、一个 **`OnlineTable`**（`node_id → {addresses[], capabilities[], rooms[], last_heartbeat_ms, state}`，在 **45 秒**内为 `online`、之后为 `offline`，行永不因离线被删）、注册被答以 `{"registered": 1}`、而心跳**什么都不答**。指针指向一个本节点并不持有的同侪时，**被拒绝**并说明（`connection_problem`，V-1 就有的那个槽）。线程是 `std::thread` + 一个 channel，而**本批不写任何链行**。

**缘由**：四个选择承担重量。**指针是一个设置，而且是节点自己能检查的设置。** §6.4 让服务器成为一个密钥住在 `peers.json` 里的同侪；指针指向本节点并不持有的同侪，只会产出它验证不了的帧，所以在加载时就拒绝，部署就那么没有广域那条道地跑着 —— 正是 §6.1 描述的诚实状态。它是加法式的、不动版本，和旁边每个字段一样。**构造时就拨号的客户端，是一个可能阻塞启动的客户端。** 会话由第一个需要它的人打开，所以一台挂了、慢、或还没部署的服务器，是「一拍没落地」，而不是「宿主起不来」—— 而没落地的一拍没有代价，因为下一拍在 15 秒后。**线程是 std 的，停止信号是 channel。** `net` 没有 async 依赖，而这个 crate 不会为一个 sleep 加一次 socket 写给它加一个；而用 channel 而不是标志位，意味着丢掉句柄会**立刻**唤醒线程，所以停止心跳的宿主在一个节拍内就停，而不是等到它碰巧正在睡的那个间隔。线程持有的是**客户端**，绝不是 `Arc<AppState>`：持有 state 的线程会形成一个环，让它在心跳期间一直活着 —— 而这正是一个宿主被丢弃时绝不应发生的事。**心跳是陈述，不是问题。** 服务器回答注册（一个节点应该知道它的行存在），而用心跳回答的是「无」：给心跳一个回答，会让一支部队的帧数翻倍去说那张表已经说了的事，而会话开着本身就是传输自己的证据。两种形状只差**一个字母**：`register` 是节点*告诉*服务器的，`registry` 是它*向*服务器*要*的，所以 `Local::of` 按这个顺序测，并有测试钉住。

**影响**：`net` 多出 `Registration`、`OnlineTable` / `OnlineEntry` / `Online`、六个体助手（`register_body`、`is_register`、`heartbeat_body`、`is_heartbeat`、`registered_body`、`is_registered`）、`HEARTBEAT_INTERVAL` 与 `ONLINE_WINDOW_MS`、本地帧 `Local::Register` / `Local::Heartbeat` 与 `LocalReply::{Registered, Beat, Unplaced}`、`answer_local` 的 `now` 参数、`RelayServer::{online, online_at, online_table}`，以及 `RelayClient::{connect, register, heartbeat}` 与 `RelaySession` 的两个发送方法；`host-core` 多出那个设置字段、`connection_client` 槽、`Heartbeat` 循环（`std::thread` + `mpsc`）、`connect_cross_region`，与 `AppState::{connection_client, start_connection_heartbeat, stop_connection_heartbeat}`。新测试：`net/tests/registration.rs`（五条）与 `host-core/tests/connection.rs` 里两条（悬挂指针被拒；以及对着真服务器的整个客户端半边 —— 注册、心跳、看那一行推进、停循环、看它冻结）；`relay` example 长到 **16** 条检查。**没有哈希公式、路由、capability 名、审计事件常量或持久化格式被改动，也没有写任何链行** —— 那张表是运行时状态（§6.6），而 V-proto-2 的 `peer_offline` / `peer_recovered` 行属于 **V-3**，探测与集体判定也落在那批。今天发出的宣告只有节点的 **rooms**：本可携带地址的对等端口是 §4.3 点名过而尚无批次落地的设置，而服务器本来就在自己那份 `peers.json` 里持有本节点被配置的地址 —— 所以 `addresses` 是**空**，而不是错的。

## 104. 一个节点由同侪的全体一致判为不在，而服务器把转换交出去

**日期**：2026-09-28 ｜ **状态**：已定；V-3a 已实现（§6.7 的节点层半边）

**决策**：[connection.md §6.7](connection.zh-CN.md) 已在 `net` 实现，并接进 `host-core`，**只在节点层**。新的 `net` 模块（`liveness`）装三块：探测（`{"probe": 1}` / `{"alive": 1}`）、探测者自己的**视图**（`Prober`：每同侪的最后应答、连失拍数与是否持有可达；只在内存、不写链），以及服务器的**见证者表**（`WitnessTable`）与其规则 —— 当**至少有一个见证者**存在、且**每个**仍存在的见证者都报了不可达时判为不在；见证者只有**新鲜**（45 秒内）、**自身在线**、且**不是被判定者**时才作数，而一个新鲜的「活着」见证者**一票否决**。服务器的 `Local` 多出两种帧（`UnreachableReport` / `ReachableReport`）；`OnlineTable` 那一行多出 **`judged_at_ms`**，与 §6.6 基于心跳的 `state` 分开；而判定经一个**转换 sink** 交出去，而不是由 `net` 写 —— `host-core` 装上 `AppState::connection_judgement_sink`，经 `emit_host` 写 **`host.connection.peer_offline`**（`{peer, witnesses, reports}`）与 **`host.connection.peer_recovered`**（`{peer, method}`，`heartbeat` 或 `probe`）。`host-core` 在心跳线程旁跑一条**探测线程** —— 一条独立的 `std::thread`，共用节点**唯一**一条会话 —— 它探测本节点的 **workgroup**（除自己与跨区域服务器外的同侪），回答发给它的探测，每拍把视图脉冲上去。**恢复是被听到**：一次心跳或一份 reachable 报告清掉 `judged_at_ms`、把那一行送回 `online`，并触发恢复转换。**不定义移除**：协议不定义踢。**兄弟确认属 V-3b**，等 V-4 把节点之上的面接好。

**缘由**：四个选择承担重量。**事件由 host-core 经 sink 写下。** §6.7 说**判定服务器**写那两行，而 v1.0 里服务器是一个 `net` 部署 —— 但链是 `host-core` 的，`net` 不得向上够。`TransitionSink` 以诚实的方式合上这个缺口：`net` 记下判定并把转换交出去，而一个在链旁边跑服务器的部署装上 `AppState` 的 sink，于是行落在 `host.connection.*` 这族本就住着的地方 —— 而**不是** `control-plane-events.md`，它的二十个名字是**流**事件。**探测线程共用心跳的会话，但它是自己的线程。** 再开一条到服务器的会话会替换本节点在服务器 `SessionTable` 里的条目并让第一条搁浅；而心跳只*发*，探测者必须*读*（接一个 `alive`、答一个 `probe`），所以一条线程兼做两件事会让它们互相等对方的读。它们共用一个 client —— `net` 的会话本就把 reader 与 writer 分开加锁 —— 而探测者持有的是 **client**、绝不是 `Arc<AppState>`，理由与 §103 的心跳相同。**视图从乐观开始，第三拍是分界线。** 探测者在连失三拍（§6.7 的 45 秒）之前对同侪没有不利证据，所以同侪一开始是*可达*；而判定只置**一次**（`judged_at_ms` 不会被重复盖上），所以一个在那一行已被判定时仍持续脉冲的报告不是第二次转换。**恢复会刷新那一行。** §6.7 说一次心跳或一次被答的探测「把 `state` 送回 `online`」，所以一份 reachable 报告既清掉判定、又刷新 `last_heartbeat_ms` —— 否则同一句话的两半会自相矛盾。

**影响**：`net` 多出 `src/liveness.rs`（体、`Report`、`Prober`、`PeerView`、`Judgement`、`WitnessTable`、`Transition` / `RecoverMethod` / `TransitionSink`，以及探测者用的 `PROBE_INTERVAL` / `PROBE_MISSES` / `REPORT_WINDOW_MS`）；`src/relay.rs` 多出两种 `Local` 帧、`OnlineTable` 的 `judged_at_ms` 与其 `is_online` / `mark_judged` / `clear_judged` / `heard_from`、转换 sink、`judge`，以及 `RelayClient` / `RelaySession` 的发送方法（`probe` / `answer_alive` / `report`）；`net/tests/liveness.rs` 新增七条集成测试，`src/liveness.rs` 五条单测；`relay` example 长到 **20** 条检查。`host-core` 多出 `Probe` 线程、`AppState::{start_connection_probe, stop_connection_probe}`、`connection_judgement_sink` / `record_connection_transition`、探测者轮询用的短**连接读超时**，以及 `tests/connection.rs` 两条测试（一次判定经 sink 写下两个事件；探测线程只在有 workgroup 时启动并能停）。**没有哈希公式、路由、capability 名、审计事件常量、既有 `net` 逻辑或持久化格式被改动** —— 那两个名字是对 `host.connection.*` 词表的**新增**。**V-3b —— 兄弟确认，以及按同一规则判定的跨区域服务器 —— 接在后**，等 V-4 把节点之上的面接好。

## 105. 桌面可以读取节点的连接状态

**日期**：2026-09-28 ｜ **状态**：已定；V-4 的第一面（批 AD / AC-1）已落地

**决策**：`host-tauri` 多出四个**只读**命令，`ui/src-tauri` 的 `generate_handler!` 登记它们：`get_node_key`（`Option<NodeKeyView>`）、`list_peers`（`Vec<net::PeerEntry>`）、`list_rooms`（`Vec<net::Room>`）与 `connection_status`（`ConnectionStatusView`）。每一个都是对**既有** `AppState` 方法的薄包装 —— `node_key()`、`peers()`、`rooms()`、`network()`、`connection_client()`、`connection_problem()` —— 且都不写任何东西：设置仍作决定、接线仍照办。`NodeKeyView` 是**视图、不是密钥**：`net::NodeKey` **本身**就 `Serialize`（它就是那个 JWK 文件），但它的 `d` 成员是私钥半边，所以视图只带 `node_id`（设备名）、`public_jwk`、`fingerprint` 与 `short_fingerprint`，别无其他。`ConnectionStatusView` 把三个事实分开：`configured`（`network().cross_region_server.is_some()`）、`connected`（`connection_client().map(RelayClient::is_connected)`，而会话是惰性打开的，所以在有人需要它之前是 `false`），以及 `problem`（V-1/V-2 记下的东西）。**上层拆成几批**：AC-1（本批）是桌面；**AC-2** 是 server 路由（它会挪动 `docs/control-plane-api.md` §5.1/§5.2 的计数与 tool-schema 表）、**AC-3** 是 CLI、**AC-4** 是服务端角色面 —— 那才是 V-3b 真正需要的。这里没有碰路由表、capability 词表、审计事件常量、哈希公式、`net`、`host-core`、`server` 或 `cli`。

**缘由**：三点承担重量。**视图，因为密钥不是线上形状。** 本批的前提是「`NodeKey` 非 `Serialize`」；真相相反、也更危险 —— 它*就是* `Serialize`，因为它*就是*那个 JWK 文件，而它的 `d` 是私钥。所以规则不是「为一个不透明类型写序列化器」，而是「绝不把密钥本身交出去」：`NodeKeyView` 是唯一那个只带公钥半边（`public_jwk`、指纹）而把 `d` 留下的形状。**`configured` 是设置事实，不是客户端事实。** 一个指向本节点并不持有的同侪的指针既不会产出客户端、又会设下 `connection_problem`，所以「有没有客户端？」会把一个**配错**的节点报成未配置；读 `network().cross_region_server` 才回答部署者问的那个问题。**`connected` 多数时候诚实地是 `false`。** 会话是惰性打开的（§103），所以一个心跳循环尚未跑过的节点是 `configured: true, connected: false`（循环一跳便成 `true`）—— 这正是 §103 选的状态，照实报告而不是抹平。

**影响**：`host-tauri/Cargo.toml` 多出两条依赖边 —— `net = { path = "../net" }`（为了 `PeerEntry` / `Room` / `NodeKey`，`host-core` 未再导出它们）与 `serde = { version = "1", features = ["derive"] }`（为了那两个视图；`host-tauri` 此前两者皆无）—— **不新增包**（锁文件只多边）；`host-tauri/src/commands.rs` 多出四个命令与两个视图；`ui/src-tauri/src/lib.rs` 登记四个名字。**不加任何测试**：`host-tauri` 按设计没有自己的测试（`Cargo.toml`：「this crate has no tests of its own」；那 39 条集成测试住在 `host-core/tests`），而一个 `#[tauri::command]` 要调用就得有活的 Tauri `State`，所以本批靠编译、`clippy -D warnings` 与 gate 验证。**没有哈希公式、审计事件常量、路由定义、capability 名、`net`/`host-core`/`server`/`cli` 文件或持久化格式被改动。** 接在后的是 AC-2（server 路由）、AC-3（CLI）与 AC-4（服务端角色）。

## 106. 连接层经 HTTP 被读取，而一个不认识任何人的节点答空列表

## 107. 服务端角色是节点自己的一种部署形态，写在设置里、用自己的文件启动

**日期**：2026-09-28 ｜ **状态**：已定；已实现（批 AF / AC-4）

**决策**：一个节点现在可以**就是那张网络的服务器**。`NetworkSettings` 多出 **`server_role: Option<ServerRoleSettings>`**（加法式、`#[serde(default)]`、`SETTINGS_VERSION` 不动），它只有一个字段 **`bind`** —— 必填，且**刻意没有默认值**。它一出现，`AppState::load_connection_files` 就用本节点自己的 `node.key` / `peers.json` / `rooms.json` 起一个 **`RelayServer`**，**同步**绑定 `network.server_role.bind`（绑不上会记进 `connection_problem`，而不是留给一条悄悄死掉的线程），再在一条线程上服务。`AppState::server_role_addr()` 报它绑在哪，`AppState::server_role()` 交出句柄，于是带链的部署可以把 §6.7 的 `AppState::connection_judgement_sink` 装上。没有配置过的节点，什么都不会起。

**缘由**：三点承担重量。**角色是配置，不是程序。** §6.1 让服务器成为**部署者运行**的部署，而 §33 的细胞分化让「带角色的节点」是一种形态、不是第二个二进制，所以 §6.5 的内网服务器就是独立 `riscdom-relay` 跑的那个**同一个** `RelayServer` —— 一套机制、两种部署形态 —— 而节点用它已经加载的文件（自己的密钥、自己的同伴表、自己的房间）把它起起来。**`bind` 故意没有默认值。** 一个默认地址就是项目在指定服务器在哪，正是 §6.1 禁止的；地址由部署者写，和 `riscdom-relay` 要求 `--bind` 一样。**先绑，再服务。** 在 `load_connection_files` 里同步绑定，把「端口被占」变成节点照常运行时的一条已报告问题，而不是一个悄悄没起来的角色。

**影响**：`host-core/src/settings.rs` 多出 `ServerRoleSettings` 与 `server_role` 字段；`host-core/src/state.rs` 多出两个字段、`start_server_role`、`note_connection_problem`、`server_role_addr` 与 `server_role`，并在 `load_connection_files` 里调用启动器；`host-core/tests/connection.rs` 新增三条测试（角色绑定成功、且有节点注册并心跳进去；没有角色的节点谁也不服务；绑不上会被报告），`host-core/tests/settings.rs` 一条（字段有/无都被正确读出，且版本不动）；`net/README.md` 及其译文写明该角色现在也能跑在节点里、不只是独立部署。**`net` 的代码未改** —— `RelayServer`、`Listener` 与 §6.6 的处理本来就能服务它 —— 也没有哈希公式、路由、capability 名、审计事件常量或持久化格式被改动。§6.7 的**兄弟确认** —— 第二层、服务器自身失联由兄弟经跨区域服务器判定 —— 是 **V-3b**，而本批暴露的那个 sink 正是它要装的钩子。

## 108. 服务器在注册里声明自己，兄弟集从宣告里读出

**日期**：2026-09-29 ｜ **状态**：已定；仅协议正文（批 AH / V-3b-proto）

**决策**：`docs/connection.md` §6.7 冻结的那句说，服务器的兄弟是「注册到同一台跨区域服务器的其它内网服务器，从上层的注册表得知」，但 §6.6 与 §6.7 都没说**怎么把一台服务器和一个节点区分开** —— `RelayServer::registry()` 是 `peers.json` 派生、不带任何这样的标记，而注册的 `capabilities` 从未被用过。协议现在把它说清：**内网服务器在它 §6.6 注册的 `capabilities` 列表里声明普通宣告 `"server"`**，服务器的那一行保留注册带来的宣告，而**跨区域服务器的兄弟集 = 宣告里含 `"server"` 的那些行**。`"server"` 是一条**宣告，不是 capability**：它是宣告列表里的一个字符串，**不是**控制平面词表的成员，不给任何词表加词，声明它不授予任何权威 —— 只意味着该节点**被当作兄弟来探**，而如果它不再应答，就由兄弟们的全体一致来判定。

**缘由**：三点。**零形状变更。** 这条宣告走 §6.6 已有的注册体，服务器本来就保留注册的宣告，而汇总那半边（见证者表、全体一致、一票否决）已是 V-3a 的 —— 所以修的是**一句话**，不是帧、字段或格式。**是宣告不是 capability，而这个区分是承重的。** 控制平面的 capability 词表（decisions §83）是权威的来源；节点绝不能靠声明什么来给它加词。§6.6 早已定下宣告的位阶 —— 宣告是「声明，不是事实」，是**来源**，服务器自己的文件仍在其上权威 —— 本批不加例外。**虚假声明在结构上无害。** 写上 `"server"` 只买到一件事：被探测。谎称的节点只是招来它不会应答的探测，最坏结果是关于它自己的一次判定，而那已由 §6.7 的规则管着（且判定不碰身份、不碰成员关系、不碰密钥）。

**影响**：`docs/connection.md` §6.6 多出一条（那一行保留注册的宣告：`capabilities`、`rooms`），其**冻结**摘要改为点出表里的字段、不再只说「四个字段」；§6.7 的「谁判定谁」条目现在说明服务器怎么表明自己是服务器，另加一条把 `"server"` 钉为「宣告而非 capability」，而「兄弟怎么知道」一条改指那条宣告、不再说「注册表」，§6.7 的**冻结**清单也加上这一点。译文同步。**没有源文件、依赖、`Capability` 变体、审计事件常量、哈希公式、路由或持久化格式被改动。** 实现 —— 服务器角色启动时声明该宣告、并从跨区域服务器的表里取兄弟集 —— 是 **V-3b-1/V-3b-2**，而 V-3a 的汇总半边已经就位。

## 109. 探测者的兄弟来自它自己的 peers.json，而任何探测都不再无限等待

**日期**：2026-09-29 ｜ **状态**：已定；已实现（批 AJ / V-3b-1）

**决策**：两件事。**（1）兄弟集是配置。** 跑服务器角色的节点从**它自己的 `peers.json`** 探 §6.7 的第二层：声明 `"server"` 的条目就是它的兄弟，而同一批条目带着它们的**公钥**。`net` 多出 `PeerEntry::is_server`、`PeersFile::servers` / `server_keys` 与常量 `SERVER_CLAIM`；`host-core` 在 V-3a 那条探测线程旁起**第二条 `Probe` 线程** —— 同一个 client（跨区域的那个）、不同的 peer 集、不同的密钥 —— 由 `start_server_role` 启动，且只在有跨区域指针且至少有一个兄弟时启动。报告就是 V-3a 的两个体，经节点自己的 client 向上发。**（2）没有工具探测再无限等待。** `host-core` 的 `exec_retrying` 现在带 deadline（**60 秒**）spawn 并等待，超时 kill 子进程并返回 `TimedOut` —— 调用方本来就把错误读作「该程序不可用」。

**缘由**：两条理由，其中一条正是批 AI 停下的理由。**密钥从不由帧到来。** §4.2 与 §6.6 让这是结构性的，所以探测者只能探它持有公钥的同侪 —— 而它持有它们的唯一地方就是它自己的 `peers.json`。批 AI 的初读（从跨区域服务器的 `OnlineTable` 取兄弟集）走不通：没有任何帧把那张表交给节点，而且即便拿到 id 也无法验证。从同一个文件读那条声明，一次合上两个缺口，且**不是新机制** —— §6.6 早就说身份来自配置，而那条声明就是 §6.6 注册与 §4 条目都携带的普通 `capabilities` 字符串。**无限等待的探测不是探测。** `Command::output()` 会阻塞在一个永不应答的子进程上 —— 一个卡住的 `qemu-system-riscv64 --version` 正是这样四次拖住 gate —— 而经同一个助手去探 QEMU、gcc、zig、rustc 的宿主会一起挂住。deadline 把它变成代码早就会给的答案：不可用。

**影响**：`net/src/peers.rs` 多出 `SERVER_CLAIM`、`PeerEntry::is_server`、`PeersFile::servers` 与 `PeersFile::server_keys`（另加一条单测），`net/src/lib.rs` 重导出该常量；`host-core/src/state.rs` 多出兄弟探测线程字段、`start_sibling_probe`、它的公开起/停对、以及在 `start_server_role` 里的调用，而 `exec_retrying` 改走 `run_bounded` / `wait_bounded`（带那条 deadline 单测）；`host-core/tests/connection.rs` 多出兄弟探测者测试；`docs/connection.md` §6.7 写明探测者从哪里找到兄弟（它自己的 `peers.json`），译文同步。**没有哈希公式、路由、capability 名、审计事件常量或持久化格式被改动，且 `"server"` 不是 `Capability` 变体** —— 它是宣告列表里的一个字符串。§6.7 的**汇总**半边 —— 跨区域服务器拿那些报告做什么、以及装上判定 sink —— 是 **V-3b-2**。

## 110. 部署方在拿得到 Arc 的地方装上判定 sink，而服务器只写自己的链

**日期**：2026-09-29 ｜ **状态**：已定；已实现（批 AK / V-3b-2）

**决策**：`AppState` 多出 **`install_connection_sink(self: &Arc<Self>) -> bool`**：它把 `connection_judgement_sink` 装到**本节点自己的** `server_role()` 上，并回答有没有可装的 server role。三个部署方在拿得到 `Arc` 的地方调用它 —— `ui/src-tauri` 的 setup、`server/src/main.rs`、`cli/src/client.rs` 的内嵌模式 —— 因为构造器交回的是 `Self` 而不是 `Arc`，而 sink 必须持有一个。**汇总**半边**无需**改动 `net`：服务器本就会记下一个兄弟的报告并判定（§6.7、V-3a 的 `answer_local`），而独立的 `riscdom-relay` 仍不装 sink —— 它没有链。

**缘由**：两点。**sink 属于那台判定的服务器，而那台服务器就是本节点。** §6.7 说判定服务器写那两行，而一个进程拥有的唯一 `RelayServer` 就是它自己的 server role 启动的那个；跨区域侧要么是独立 relay（无链）、要么是另一个节点，而那个节点自己的部署会装自己的 sink。所以只装在 `server_role()` 上、别处不装 —— 服务器从不写别的节点的链。**安装点就是那个 `Arc`，而只有部署方持有。** `start_server_role` 跑在 `load_connection_files(&self)` 里，那里还没有 `Arc`，而 sink 需要一个来让状态活到判定到来为止。与其重塑构造器（每个测试与 `host-tauri` 都经它们建状态），不如让那个把状态包进 `Arc`、也正是运行服务器的一方调一个方法。

**影响**：`host-core/src/state.rs` 多出 `install_connection_sink`；`ui/src-tauri/src/lib.rs`、`server/src/main.rs` 与 `cli/src/client.rs` 各自在造出 `Arc` 的地方调一次；`host-core/tests/connection.rs` 多出一条测试：把 sink 装到节点自己的 server role 上、经它驱动一次判定、并从**该**节点的链上读出 `host.connection.peer_offline` / `peer_recovered`（外加反面：没有 server role 的节点答 `false`）。两条旧的 server-role 测试收紧为会播种 `rooms.json`，于是「绑不上」测试如今真的失败在**绑定**上、而不是缺一个文件。`net/README.md` 及其译文写明 §6.7 已完成。**没有哈希公式、路由、capability 名、审计事件常量或持久化格式被改动，且 `net` 的逻辑未动。** §6.7 的**兄弟**确认至此完成：V-3b-1 探测与上报，本批接上 sink。

## 111. CLI 的四条连接读取就是四条一个词的命令

**日期**：2026-09-29 ｜ **状态**：已定；已实现（批 AL / AC-3）

**决策**：`riscdom` 多出四条只读命令 —— **`identity`**、**`peers`**、**`rooms`** 与 **`connection`** —— 与 AC-2 放上线的四条路由一一对应（`GET /v0/identity`、`/v0/peers`、`/v0/rooms`、`/v0/connection`）。每条是一个单元 `Command`、一条 GET 路径、一个 `parse_command` 分支、一行 `USAGE` 与一个渲染器；人类模式给 `identity` 与 `connection` 打印键值行、给 `peers` 与 `rooms` 打印小表，且**把三个 `null` 用文字说出来** —— `no identity: the connection layer is not configured`、`no peer table: this node has no peers.json`、`no rooms: this node has no rooms.json`。`--json` 仍原样透传线上形状。`docs/control-plane-client-guide.md` §7 与 `cli/README.md` 各多四行。

**缘由**：两点。**一个词，不是两个。** 其它点到资源的读取带子命令（`executors list`、`audit status`），但一个连接项不是「一个集合里的一项」：这四个各自恰指一件事，所以读起来最好的形状就是读得最少的那个 —— 而且它让 CLI 的词表与路由的词表平行（一条路由、一条命令）。**`null` 要用文字说出来。** AC-2 对缺失的连接数据答 `null`，而一个把空形状打印出来的渲染器，会把「该层未配置」弄得像「读取成功、只是没东西」—— 而那正是这些路由存在要区分的那一件事。上面三句话就是那个区分，而 `--json` 为偏好机器可读者保留 `null`。

**影响**：`cli/src/args.rs` 多出四个变体、使用说明行、解析分支、GET 路径与 `method()` 分支，以及两条既有 parse/path 测试里的断言；`cli/src/render.rs` 多出四个渲染器与其 `human()` 分支；`cli/tests/read_only.rs` 对着内嵌服务器驱动这四条命令（新节点答 `null`，且 `--json identity` 在线上是 `null`）；`docs/control-plane-client-guide.md` §7 与两份 `cli/README.md` 各多四行。**没有 server 路由、`net`、`host-core` 或 `host-tauri` 文件被改动，也没有哈希公式、路由定义、capability 名、审计事件常量或持久化格式被改动** —— CLI 是 HTTP 客户端，且一直如此。**V-4 收尾**：AC-1 桌面、AC-2 路由、AC-3 CLI、AC-4 服务端角色。

## 112. 死掉的 QEMU 会被点名、同一文件里的两条起客户机测试串行、而孤儿清理需要一个 OS 设施

**日期**：2026-09-29 ｜ **状态**：已定；(c) 与 (b) 已实现，孤儿修在它的安全阀处停下（批 AN）

**决策**：批 AM 三条修里的两条落地。**（c）死掉的 QEMU 会被点名。** `sandbox/src/vm.rs` 在 QMP 操作失败时检查 QEMU 子进程：已退出则错误变成 **「QEMU exited with code N during <op>（原始错误：…）」** —— socket 错误被留在退出信息旁边 —— 而 QEMU 仍在跑时保留原错误，因为「进程还活着、socket 却死了」是另一个事实。**（b）`snapshot_commands.rs` 里两条起客户机的测试一次只跑一条**：该文件内一个 `static SERIAL: Mutex<()>`，两台客户机永不一起启动，且**不动 gate 的全局并行**。**（c2）孤儿清理在它的安全阀处停下**：当父进程被 *force-kill* 时要连带杀死 QEMU 子进程，需要一个 OS 设施 —— Windows **Job Object**（`windows-sys`）或 Unix `setsid`+`PR_SET_PDEATHSIG`（`libc`）—— 而 `sandbox` 恰好只有三个依赖、整个工作区没有任何 FFI，所以本批两者都没加。

**缘由**：**那个错误是真的、但没用。** `os error 10054` 说的是 *socket* 做了什么；部署者需要知道的是 *QEMU* 做了什么。点名退出（并留下 socket 错误）把五分钟的谜题变成一眼可读，代价只是一次 `try_wait`。**flake 是共享资源，所以串行化是靶向修理。** 端口交接窗口是整机范围的，进程内唯一能拓宽它的办法是不让*我们自己的*客户机互相抢；文件内的互斥锁做到这一点，又不让每次 gate 变慢 —— 而全局 `--test-threads=1` 会。**孤儿修到了工具链的边界。** 本次观察到的孤儿（`qemu-system-riscv64 --version`，从它那次挂起一直活到现在）之所以存活，是因为*父进程被 force-kill*；`std` 里没有任何东西能在父进程死时杀死子进程，而两条真路子都是 OS API。给一个只有三个依赖的 crate 加 `windows-sys`/`libc` —— 并写下工作区的第一处 FFI —— 是 owner 的决定，不是一次 flake 修的副作用（依赖是一个承诺）。

**影响**：`sandbox/src/vm.rs` 多出 `explain_qmp`、自由函数 `qmp_failure`、三处已包装的调用点（QMP connect、`migrate`、`query-status`），以及一条对着真实退出状态校文字的测试；`host-core/tests/snapshot_commands.rs` 多出 `SERIAL` 互斥锁与两条守卫。**批 AJ 的 60 秒界是另一个根因、保留不动**：它把永不退出的 `--version` 探针变成「不可用」，`read_only` 的挂起因此消失；本批处理的是 *失败* 的 QEMU，那种情况那个界从来没见过。**没有哈希公式、路由、capability 名、审计事件常量或持久化格式被改动。** 孤儿清理（Job Object / `PR_SET_PDEATHSIG`）**仍开放**，两个选项如上。
